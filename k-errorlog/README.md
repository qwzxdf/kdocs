# K-ErrorLog

Visual Studio 2022 / 2026 用の拡張です。C++ のビルドエラーを、**色つきの専用ログ窓**に整理して出します。「出力」ウィンドウのとなりにタブで並びます。

特に、リンカーの **LNK2019（未解決の外部シンボル）** を、原因ごとにまとめて、「何をすれば直るか」まで書きます。`std::unique_ptr<…, std::default_delete<…>>` のような長い型名も、人間が書く形に直して表示します。

> 状態: コンパイルは通りますが、Visual Studio に入れての動作確認と、テストはしていません（作者の指示で省略）。表示がおかしいときは、`%LOCALAPPDATA%\K-ErrorLog\vsix.log` に記録が出ます。

## 機能

### 未解決の外部シンボルを、原因ごとにまとめる

ビルド出力の `LNK2019` / `LNK2001` を全部読み、同じシンボルを 1 つにまとめます。そのうえで、次の順に原因を判定します。

1. **起動関数がない**（`main` / `WinMain`）: サブシステムの設定と、プロジェクトの種類を確かめるよう案内する
2. **`.lib` に実体がある**: ソリューションの下の `.lib` を読み（シンボルの索引だけを読むので速い）、どの `.lib` に入っているかを示す。リンカー入力に足りないだけなら、追加の方法を出す
    - ビット数（x86 / x64）が違う `.lib` なら、そう指摘する
    - 静的ライブラリなのに、ヘッダーが `dllimport` で宣言している（`__imp_` が付く）なら、そう指摘する
3. **Windows / DirectX の関数**: `user32.lib`、`d3d11.lib`、`d3dcompiler.lib`、`dxguid.lib` など、必要な `.lib` を示す
4. **vtable がない**: 仮想関数の定義漏れ
5. **static メンバー変数・グローバル変数の定義がない**
6. **定義はソースにあるのに、リンクされていない**: ソースを文字列で検索して、定義らしい行を示す
7. **`dllimport` で参照しているが、実体がどこにもない**: 提供元の import lib のリンク漏れ
8. **テンプレートのインスタンスがない**、**メンバー関数の定義がない**、**関数の定義がない**

同じ名前空間のシンボルが並んでいれば、「`.lib` が丸ごと足りない」可能性が高い、と書きます。リンカーの集計（LNK1120）の件数も出ます。

参照元の関数も読みやすくします。ラムダは「`ラムダ #1 in pe_engine_resize(…)`」、`scalar deleting destructor` は「デストラクターのラッパー」と表示します。

### そのほかのリンカー エラー

- `LNK2005`（二重定義）: シンボルと、定義が重なった 2 つの `.obj` を出す
- `LNK2038`（`RuntimeLibrary` や `_ITERATOR_DEBUG_LEVEL` の不一致）: 値を `/MTd (静的リンク・Debug)` のように読み替えて、並べて出す
- `LNK1104`、`LNK1181`、`LNK1112`、`LNK1168`、`LNK1561` など: 日本語の見出しと対処

### テンプレートのエラーを読みやすくする

- 型名を短くする: `std::basic_string<char, …>` → `std::string`、`std::vector<T, std::allocator<T>>` → `std::vector<T>`、`std::unique_ptr<T, std::default_delete<T>>` → `std::unique_ptr<T>`、`std::map` / `std::unordered_map` / `std::set` の既定の引数、`std::_Vector_iterator<…>` → `std::vector<T>::iterator` など
- `X const &` を `const X&` に直し、`class` / `struct` / `__cdecl` を消す
- **渡した型**と**期待する型**を、2 行に並べる（`C2664` の「引数 N を … に変換できません」、`C2440`）
- **テンプレート引数**（`with [ _Ty=… ]`）を、1 行ずつに分ける
- **原因の場所**: エラーが `<memory>` の中で出ていても、自分のコードの呼び出し行を探して、リンクにする
- **経路**: 「see reference to function template instantiation … being compiled」の連なりを、自分のコードの行は強調し、ライブラリの中の段は畳む（「経路を全部表示」で展開）
- **候補**: オーバーロードの候補と、落ちた理由を並べる（`C2672`、`C2784`、`C2893` など）
- 主な 80 個ほどのエラー コード（`C2065`、`C2664`、`C1083`、`LNK2019` …）に、日本語の見出しとヒントを付ける
- 日本語版と英語版の、どちらの Visual Studio の出力も読む。GCC / Clang の形式も読む

### 窓の使い方

- ビルドが終わると、エラーがあるときだけ、窓が前に出る（入力の邪魔はしない）
- 色は、Visual Studio のテーマ（ダーク / ライト）に合わせて変わる。コードの色は、Dark+ / Light+ に合わせてある
- ファイルの場所（青い文字）を押すと、その行へ飛ぶ。シンボルの横の「宣言を検索」で、ソリューション全体から探して、「検索結果 1」に出す
- 窓の上のチェックボックス
    - **原文**: 整理せずに、ビルド出力をそのまま、色だけ付けて出す
    - **警告も表示**
    - **経路を全部表示**
    - **原文を併記**: 整理した各項目の下に、元のメッセージも出す
- **コピー**: 表示している内容を、文字でコピーする。**原文をコピー**: ビルド出力をそのままコピーする（AI や質問に貼る用）
- 文字は選択して `Ctrl+C` でコピーできる
- 拡張機能 メニューの「K-ErrorLog (エラーログ)を開く」から、いつでも開ける

## K-CppErr との違い

[K-CppErr](../k-cpperr/README.md) は、テンプレートのエラーを、自分のコードの場所つきで**一覧にする**拡張です（ツリー表示）。K-ErrorLog は、出力ウィンドウのような**文字の窓**に、色をつけて並べます。未解決のシンボルの原因判定と、型名の短縮は、K-ErrorLog だけの機能です。両方を入れても、ぶつかりません。

## しくみ

ビルドが終わった時点で、「出力」ウィンドウの「ビルド」欄の文字を読み、解析します。リンカーの 1 行は、`"読みやすい名前" (装飾された名前)` の形で、両方が書かれています。その読みやすい名前を、宣言として分解します（アクセス指定、戻り値、名前空間、クラス、引数、`const`）。

`.lib` の探索は、COFF アーカイブの先頭にある「リンカー メンバー」（シンボル名の索引）だけを読みます。ソリューションのフォルダーの下を、最大 800 個、6 秒まで調べます。ソースの探索は、`Class::Name(` が、定義らしい行（代入や `return` を含まず、`;` で終わらない行）にあるかどうかの、文字列の検索です。**推測**なので、見つからなくても、ソリューションの外にソースがあるかもしれません。

## 限界

- ビルド欄の文字を読むので、ビルドのあとで「出力」を消すと、「再読み込み」で何も出ません
- `.lib` の探索は、ソリューションのフォルダーの下だけです。Windows SDK や vcpkg の外の `.lib` は探しません（Windows の関数は、名前の表で判定します）
- 原因の判定は、手がかりからの推測です。外れることがあるので、「原文」表示と見比べてください
- MSVC の日本語・英語の出力で作りました。ほかの言語の出力は、読めない部分があります

## インストール

`bin\K-ErrorLog.vsix` をダブルクリックして、Visual Studio を再起動します。

## ビルド

```powershell
.\build.ps1
```

事前に、Visual Studio の「Visual Studio extension development」ワークロードが要ります。
