# ネットワーク（UDP・同期・ラグ補正）

2 人で遊ぶゲームを作るとき、「相手の位置をネットワークで送ればいい」と考えます。送ること自体はできても、遊べるようにするのは別の話です。通信には遅れが出る。パケットは順番が入れ替わったり、消えたりする。2 台のゲームで状態がずれていく。何もしないと、相手のキャラクターがカクカク動いたり、自分が当てたはずの攻撃が外れたりします。

ネットワーク ゲームの設計は、<strong>通信が遅く、不確かなことを前提にそれでも同じゲーム世界に見せる工夫</strong>の集まりです。

!!! tip "ポイント"
    - ゲームの通信は、UDP が基本。TCP は、遅れた 1 つのパケットが後ろ全部を止めるので、動きの同期に向かない
    - UDP は届く保証も順番の保証もないので、必要な分だけ自分で作る（番号付け、再送）
    - 同期の方式は 2 つ。状態を送る（サーバーが正）と、入力を送る（ロックステップ）
    - 遅れの隠し方は、予測（自分の動きをすぐ反映）、補間（相手の動きを滑らかに）、ラグ補正（当たり判定を過去に戻す）
    - 最初に決めるのは、サーバー権威かどうか。不正への強さと、反応の速さの釣り合い

## TCP と UDP {#tcp-udp}

TCP は、データが必ず届き、順番も守られます。そのために、途中でパケットが失われると、再送されるまで、後ろのデータを全部止めます。ゲームの位置情報のように、古いデータは捨てて新しいものだけ欲しい場合、止まるのは害になります。

UDP は、届く保証も順番の保証もありません。そのかわり、止まりません。ゲームの動きの同期は、UDP で送り、必要なものだけ自分で信頼性を足すのが定石です。

| 項目 | TCP | UDP |
| --- | --- | --- |
| 届く保証 | あり | なし |
| 順番の保証 | あり | なし |
| 遅れの揺れ | 大きい（再送待ち） | 小さい |
| 向く用途 | ログイン、チャット、ファイル | 位置、入力、射撃 |

ゲームの実装では、UDP の上に番号付けと確認応答を載せた小さなプロトコルを自作するか、ENet や GameNetworkingSockets のようなライブラリを使います。UDP を直接扱うのは、ソケットの学習には良いですが、商用では車輪の再発明になりがちです。

## 同期の方式 {#sync}

### 状態同期（サーバーが正） {#state-sync}

サーバーがゲームを進めて、世界の状態（位置、体力など）をクライアントに送ります。クライアントは、送られた状態を表示するだけです。

サーバーが正しいので、不正（チート）に強く、クライアントの数が変わっても、一貫性が保てます。FPS やアクション ゲームの多くが、この形です。一方、状態の量が多いと、通信量が増えます。

### ロックステップ（入力を送る） {#lockstep}

全員が同じ初期状態から、同じ入力を同じタイミングで適用して、同じ結果になることを期待します。送るのは入力だけなので、通信量が小さいです。RTS や格闘ゲームで使われます。

ただし、全員のゲームが<strong>完全に同じ結果</strong>を出す必要があります（決定性）。浮動小数点の計算が CPU やコンパイラで少しでも違うと、ずれていきます。全員の入力が揃うまで進めないので、一番遅い人に合わせる、という弱点もあります。

## 遅れを隠す工夫 {#lag}

通信には、数十〜数百ミリ秒の遅れがあります。何もしないと、操作してから動くまで、遅れを感じます。

### クライアント予測 {#prediction}

自分の操作は、サーバーの返事を待たず、手元ですぐに反映します。後から、サーバーの結果が届いたとき、手元の予測と違っていれば、サーバーの結果に合わせて直します。入力に番号を付けておくと、「サーバーが処理した最後の入力」以降の入力をやり直して、自然に補正できます。

### 補間 {#interpolation}

他のキャラクターの位置は、1 秒に 20 回程度しか届きません。そのまま表示すると、カクカクします。届いた 2 つの位置の間を滑らかに補間して表示します。補間のために、わざと少し過去（100 ms 程度）の状態を表示します。常に、2 つの位置の間にいられるからです。

### ラグ補正（当たり判定の巻き戻し） {#lag-compensation}

遅れがあると、プレイヤーが見ていた画面と、サーバーの現在の状態は違います。プレイヤーが狙って撃ったとき、サーバーでは、敵はもう動いています。そのまま判定すると、当てたはずが外れます。

ラグ補正は、サーバーが過去の位置を記録しておき、撃った人の遅れ分だけ巻き戻して、当たり判定をします。撃った人にとって公平になる一方、撃たれた人は、物陰に入ったのに当たる、という不満が出ることがあります。

## 通信量を減らす {#bandwidth}

位置を毎回 `float` 3 つ（12 バイト）で送るより、必要な精度に量子化します。範囲が決まっていれば、16 ビットの整数で足ります。変化した部分だけを送る（差分）、重要度の低いものは頻度を下げる、なども有効です。

パケットのヘッダー（IP と UDP で 28 バイト）が中身より大きいこともあります。小さいデータを 1 つのパケットにまとめて送ります。

## 最初の一歩 {#start}

いきなりネットワーク ゲームを作ると挫折しやすいので、段階を踏みます。

1. ローカルで 2 人用を作り、ゲームの更新と描画を分けておく
2. 入力を毎フレーム 1 つの構造体にまとめる（ネットワークで送るのが楽になる）
3. 同じ PC 上で、サーバーとクライアントの 2 つのプロセスにして、ローカル ホストで通信する
4. わざと遅延と損失を入れて（テスト用の遅延機能）動かす

遅延と損失のテストは、手元だけの通信（ほぼ遅れなし）では見つからない問題を見つけます。

## よくあるミス {#mistakes}

??? failure "手元ではちゃんと動くのに、インターネット越しだと壊れる"
    遅れと損失を入れたテストをしていません。遅延を 100 ms、損失を 5% にして動かします。

??? failure "TCP で位置を送って、遅れが蓄積する"
    パケット損失で、後ろがすべて止まります。位置は UDP で送ります。

??? failure "クライアントを信用して、体力や位置をそのまま受け取った"
    クライアントは改ざんできます。重要な判定はサーバーで行います。

## これだけ覚える {#summary}

- ゲームの同期は UDP が基本。必要な信頼性は自分で足す
- 状態同期はサーバーが正、ロックステップは入力だけを送る
- 遅れは、予測、補間、ラグ補正で隠す。遅延と損失を入れてテストする
