# パッケージ管理の比較（vcpkg と Conan）

外部ライブラリを使うたびに、ソースをダウンロードして、ビルドして、パスを通す。これを手作業でやると、ライブラリが 5 個になった時点で嫌になります。しかも、ライブラリ同士が別のライブラリに依存していて、バージョンが合わないと動きません。

パッケージ マネージャーは、<strong>ライブラリの名前を書くだけで、ダウンロード、ビルド、依存関係の解決までやってくれる</strong>道具です。C++ では、vcpkg と Conan が代表的です。このページは、2 つの違いと、どちらを選ぶかを説明します。

!!! tip "ポイント"
    - 迷ったら vcpkg。Visual Studio との統合が最も手軽で、学生のゲーム制作に向く
    - vcpkg は、ソースからビルドするのが基本（キャッシュで高速化できる）。Conan はビルド済みのバイナリを配る
    - どちらも、プロジェクトのマニフェスト（`vcpkg.json` / `conanfile.txt`）に依存を書き、リポジトリに入れる
    - 設定の細かさと柔軟性は Conan が上。そのぶん、設定を学ぶ手間が増える
    - 1 つのプロジェクトで、両方は使わない。どちらかに決める

## 2 つの考え方 {#concept}

### vcpkg {#vcpkg}

Microsoft が作った、ライブラリのレシピ集です。レシピは、「このライブラリをこのバージョンで、このようにビルドする」という手順で、vcpkg が実際にソースを取得してビルドします。

Visual Studio には、vcpkg が組み込まれていて、`vcpkg integrate install` を 1 回実行すれば、プロジェクトのフォルダーに `vcpkg.json` を置くだけで、ビルド時に自動で入ります。

```json
{
  "dependencies": ["fmt", "nlohmann-json", "sol2"]
}
```

ビルドの設定（Debug/Release、x64、ランタイム ライブラリ）は、トリプレットという名前で選びます。ソースからビルドするので、プロジェクトの設定とそろえやすい反面、最初のビルドには時間がかかります。

### Conan {#conan}

Conan は、バイナリを配る仕組みが中心です。パッケージは、コンパイラ、バージョン、ビルドの種類の組み合わせごとに、ビルド済みのファイルを持っています。一致するものがあれば、ダウンロードするだけで済みます。なければ、ソースからビルドします。

```text title="conanfile.txt"
[requires]
fmt/10.2.1
nlohmann_json/3.11.3

[generators]
CMakeDeps
CMakeToolchain
```

```bash
conan install . --build=missing
```

実行すると、CMake から使える設定ファイルが生成されます。環境の設定は「プロファイル」に書き、それを切り替えて、Debug/Release や、別のコンパイラ用にビルドします。

## 比較 {#compare}

| 観点 | vcpkg | Conan |
| --- | --- | --- |
| Visual Studio との統合 | 組み込み。ほぼ設定なし | CMake 経由が基本 |
| 配り方 | ソースからビルド（バイナリ キャッシュあり） | ビルド済みバイナリ |
| 設定 | トリプレット（わりと単純） | プロファイル（柔軟だが多い） |
| バージョン固定 | `builtin-baseline` でカタログの版を固定 | パッケージごとに版を指定 |
| 自分のライブラリを配る | ポートを書く | レシピを書く |
| 学習のしやすさ | やさしい | やや難しい |

## どちらを選ぶか {#choose}

Visual Studio で、DirectX と数個のライブラリを使うゲームを作る学生なら、vcpkg です。`vcpkg.json` に名前を書けば動き、困ったときの情報も多いです。

次のような場合は、Conan を検討します。

- チームが Linux や macOS でもビルドし、環境ごとに細かく設定を変えたい
- 社内にビルド済みバイナリを配るサーバーを用意したい
- ライブラリのバージョンを細かく固定したい

## バージョンを固定する（vcpkg） {#baseline}

`vcpkg.json` に何も書かないと、vcpkg のカタログのその時点の版が使われます。人によって取得した日が違うと、ライブラリの版が違い、挙動がずれます。`builtin-baseline` にカタログのコミットを書いて固定します。

```json
{
  "builtin-baseline": "0123456789abcdef0123456789abcdef01234567",
  "dependencies": ["fmt", "nlohmann-json"]
}
```

`vcpkg x-update-baseline --add-initial-baseline` を実行すると、現在のカタログのコミットが書き込まれます。チームで共有すると、全員が同じ版を使えます。

## ビルドを速くする {#cache}

vcpkg は、ビルド結果をバイナリ キャッシュとして保存します。既定で個人の PC に保存されますが、チームや CI で共有する設定もできます。[GitHub Actions](github-actions.md) では、このキャッシュを保存して、2 回目以降のビルドを速くします。

## よくあるミス {#mistakes}

??? failure "ライブラリを入れたのに、ビルドが通らない"
    プロジェクトの構成（x64 / Debug）と、トリプレットが合っていません。x64-windows で入れたのに、Win32 でビルドしている場合などです。

??? failure "自分の PC では動くが、他の人は動かない"
    ライブラリの版が違います。`builtin-baseline` を固定して、リポジトリに入れます。

??? failure "vcpkg と Conan の両方を入れて、パスがぶつかる"
    1 つのプロジェクトでは、どちらか一方にします。

## これだけ覚える {#summary}

- 迷ったら vcpkg。`vcpkg.json` に名前を書いて、`builtin-baseline` で版を固定する
- Conan は、設定の柔軟さとバイナリ配布が強み。環境が多様なチーム向き
- 構成とトリプレットを合わせる。チームで同じ版を使う
