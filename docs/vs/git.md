# Git の基礎（履歴を残して、巻き戻す）

ゲームを作っていると、「昨日まで動いていたのに、いま動かない」が必ず起きます。フォルダーを `MyGame_最終`、`MyGame_最終2`、`MyGame_本当に最終` とコピーして逃げる方法は、すぐに破綻します。どれが新しいのか分からなくなりますし、チームで作るなら、同じファイルを 2 人が別々に直して、片方が消えてしまいます。

Git は、<strong>ファイルの変更を履歴として残し、好きな時点に戻せる</strong>道具です。複数人が別々に直した内容をあとから合体させる仕組みも持っています。このページでは、ゲーム制作で最初に必要になる範囲（記録する、枝を分ける、合体する、衝突を直す、記録しないファイルを決める）に絞って説明します。

!!! tip "ポイント"
    - Git の仕事は 3 つ。変更を記録する（コミット）、並行して作業する（ブランチ）、あとで合体する（マージ）
    - 記録は 2 段階。まず `add` で「次の記録に入れるもの」を選び、`commit` で確定する
    - コミットはいつでも戻れる安全な地点。小さく、こまめに作る
    - `.gitignore` に、`.vs/` や `x64/` などのビルド生成物を書く。入れてはいけないものを入れると、リポジトリが重くなる
    - 自分のコンピューターの記録（ローカル）と、GitHub などの共有場所（リモート）は別物。`push` するまで、他人には見えない

    - [Visual Studio の準備](setup.md)（Visual Studio の Git 機能は、インストール時に選ぶ項目の 1 つ）
    - [.editorconfig](editorconfig.md)（改行や文字コードの食い違いで、差分が汚れるのを防ぐ）

## 最初に知っておく言葉 {#terms}

Git の説明は、言葉でつまずきがちです。先に、よく出る 6 つを押さえます。

| 言葉 | 意味 |
| --- | --- |
| リポジトリ | プロジェクトのフォルダーと、その履歴を丸ごと入れた入れ物。フォルダー内の `.git` に履歴が入っている |
| コミット | ある時点の状態を 1 つ記録したもの。メッセージと、作った人と、日時が付く |
| ブランチ | 履歴の枝。`main` から枝を分けて作業し、終わったら戻す |
| マージ | 別々の枝の変更を 1 つに合体すること |
| リモート | GitHub などの共有場所にあるリポジトリ。ふつう `origin` という名前で呼ぶ |
| HEAD | 「いま自分がいる場所」を指す目印。ふつうはブランチの先頭を指している |

コミットは、ファイルの「差分」ではなく、<strong>その時点のプロジェクト全体の写真</strong>だと考えると分かりやすくなります。実際には変更のない部分を使い回すので、容量は小さく済みます。

## 記録する：add と commit {#commit}

Git は、記録を 2 段階に分けています。作業フォルダーで直したファイルのうち、「今回の記録に入れるもの」を選んで置く場所（ステージ）を挟みます。

```bash
git init                          # このフォルダーをリポジトリにする（最初の 1 回）
git status                        # 何が変わったかを見る
git add Player.cpp Player.h       # 記録に入れるファイルを選ぶ
git commit -m "プレイヤーの移動を追加"
```

`git init` は、いまいるフォルダーに `.git` を作ります。これで、そのフォルダーが履歴の管理対象になります。すでに GitHub にあるプロジェクトを持ってくるなら、`git init` の代わりに `git clone <URL>` を使います。

`git add` で、ファイルをステージに置きます。ここを挟む理由は、「ついでに直した 3 つの別件を 1 つのコミットに混ぜない」ためです。1 つのコミットは 1 つの目的にそろえておくと、あとで「この変更だけ戻したい」ができます。

`git commit` で、ステージにあるものを確定します。`-m` の後ろがコミットメッセージで、<strong>何をしたかを一行で書きます</strong>。「修正」「更新」だけだと、半年後に履歴を読んでも何も分かりません。

履歴は `git log --oneline` で見られます。

```text title="git log --oneline の例"
a3f9c21 プレイヤーの移動を追加
7be0d54 ウィンドウを表示する
1c8a002 最初のコミット
```

先頭の英数字がコミットの ID で、戻る・比べるときの住所になります。

### 間違えたときの戻し方 {#undo}

| やりたいこと | コマンド |
| --- | --- |
| まだ add していない変更を元に戻す | `git restore Player.cpp` |
| add したものをステージから外す | `git restore --staged Player.cpp` |
| 直前のコミットのメッセージを直す（まだ push 前） | `git commit --amend` |
| 過ぎたコミットを打ち消す記録を作る | `git revert a3f9c21` |

`git restore` は、<strong>保存していない変更を捨てます</strong>。元に戻せないので、実行する前に `git status` で対象を確かめてください。`git revert` は履歴を消さず、「あのコミットの逆を行う」新しいコミットを足します。push したあとでも安全に使える方法です。

## 枝を分ける：ブランチ {#branch}

新しい機能を作っている途中で、別の不具合を直したくなることがあります。同じ場所で両方を進めると、どちらも中途半端な状態で混ざります。そこで、<strong>機能ごとに枝を分けて</strong>作業します。

```bash
git switch -c feature/enemy       # 新しい枝を作って、そこに移る
# …ファイルを直して add / commit を繰り返す…
git switch main                   # main に戻る
git merge feature/enemy           # 枝の変更を main に合体する
git branch -d feature/enemy       # 役目を終えた枝を消す
```

`git switch -c` は、いまの場所から枝を作って移ります。`-c` を付けないと、既にある枝への移動だけです。枝を移ると、作業フォルダーのファイルがその枝の状態に切り替わります。`main` に戻れば、`feature/enemy` で作ったファイルは見えなくなり、`feature/enemy` に戻れば、また現れます。

`git merge` は、いまいる枝に指定した枝の変更を取り込みます。つまり、`main` に取り込みたければ、先に `main` に移ってから実行します。順序を逆にすると、取り込む向きが逆になります。

枝の名前は、`feature/enemy`、`fix/crash-on-load` のように、種類と中身が分かるようにしておくと、一覧で読めます。

## 共有する：リモートと push / pull {#remote}

ここまでは、自分のコンピューターの中だけの話です。他の人と共有するには、GitHub などのリモートと記録をやり取りします。

```bash
git remote add origin https://github.com/ユーザー名/MyGame.git   # 共有場所を登録（clone したなら不要）
git push -u origin main           # 自分の記録を送る
git pull                          # 他の人の記録を受け取る
```

`git push` は、ローカルのコミットをリモートへ送ります。<strong>push するまでは、他人には何も見えません</strong>。`-u` は「今後、この枝は `origin/main` と組にする」という指定で、最初の 1 回だけ付ければ、次からは `git push` だけで済みます。

`git pull` は、リモートの新しいコミットを取り込みます。作業を始める前に必ず 1 回実行する習慣を付けると、他の人の変更を知らずに作業を進めてしまう事故が減ります。

push が `rejected`（拒否）で失敗したら、リモートに自分が持っていないコミットがあるということです。慌てて強制的に上書き（`--force`）せず、先に `git pull` で取り込んでから、もう一度 push します。

## 衝突を直す：コンフリクト {#conflict}

同じファイルの同じ行を 2 人が別々に直すと、マージのときに Git は、どちらが正しいか決められません。これがコンフリクト（衝突）です。慌てなくて大丈夫で、Git は、衝突した場所に目印を書き込んで、人間に決めてもらうだけです。

```cpp
<<<<<<< HEAD
int speed = 5;
=======
int speed = 8;
>>>>>>> feature/enemy
```

`<<<<<<< HEAD` から `=======` までが、いま自分がいる枝の内容です。`=======` から `>>>>>>>` までが、取り込もうとしている枝の内容です。どちらを残すか（あるいは両方を混ぜるか）を決め、<strong>目印の 3 種類の行を全部消して</strong>、保存します。

```bash
git add Player.cpp                # 直したことを Git に伝える
git commit                        # マージを完了する（メッセージは自動で入る）
```

目印の行を消し忘れると、そのままコンパイルエラーになります。逆に言えば、ビルドが通らなければ消し忘れに気づけます。やり方に迷ったら、`git merge --abort` でマージ前の状態に戻せます。

衝突を減らすには、枝を長く放置しないことが一番効きます。数日おきに `main` を取り込み、機能は小さい単位で `main` に戻します。

## 記録しないファイルを決める：.gitignore {#gitignore}

ビルドで生成されるファイルや、個人の設定ファイルは、リポジトリに入れません。サイズが大きく、他の人の環境では意味がなく、毎回差分に出て邪魔だからです。入れないものは、リポジトリ直下の `.gitignore` に並べます。

```gitignore
# Visual Studio
.vs/
*.user
*.suo

# ビルドの出力
x64/
Debug/
Release/
out/
build/

# vcpkg
vcpkg_installed/
```

行は、フォルダー名やパターンです。末尾が `/` なら、フォルダーを指します。`*` は任意の文字列です。

Visual Studio でプロジェクトを作るとき、「Git リポジトリを作成」を選ぶと、C++ 用の `.gitignore` が自動で置かれます。手作業で `git init` したなら、GitHub が配っている `VisualStudio.gitignore` を元にするのが手早い方法です。

!!! warning ".gitignore は、すでに記録したファイルには効かない"
    すでにコミットしてしまったファイルは、あとから `.gitignore` に書いても追跡され続けます。`git rm --cached x64/Debug/MyGame.exe` で追跡だけを外してから、コミットします。ファイルそのものは消えません。

## Visual Studio から使う {#vs}

コマンドを打たなくても、Visual Studio の画面から同じことができます。

- 右下のステータス バーの「↑ 発行」から、リポジトリを作って GitHub に載せられる
- 「Git の変更」ウィンドウに変更したファイルが並ぶ。ファイルの横の「+」が `add`、メッセージ欄と「コミット」ボタンが `commit`
- 右下のブランチ名をクリックすると、枝の切り替えと新規作成ができる
- コンフリクトは、「マージ エディター」が 3 画面（自分、相手、結果）で表示してくれる

どの方法を使っても、中身は同じ Git です。ただ、困ったときに `git status` で状態を見る癖があると、画面の表示が何を意味しているか読み取れます。

## ゲームの制作で効く習慣 {#game}

- <strong>動く状態でコミットする</strong>。ビルドが通らない状態を `main` に置くと、他の人の作業が止まる
- 画像・モデル・音声などの大きなバイナリは、履歴が膨らみやすい。同じファイルを何度も更新するなら、Git LFS を検討する
- `.sln` や `.vcxproj` は、衝突したときに手で直すのが難しい。ファイルを追加するたびにこまめにコミットして、同時に触る人を減らす
- コミットの前に `git status` と `git diff` を見る。意図しないファイルが入っていないかを最後に確かめる

## よくあるミス {#mistakes}

??? failure "ビルド生成物を入れてしまい、リポジトリが重くなった"
    `x64/` や `.vs/` を `.gitignore` に書く前にコミットすると、数百 MB が履歴に残ります。履歴から完全に消すのは難しいので、最初のコミットの前に `.gitignore` を置いてください。

??? failure "`git add .` で、入れたくないものまで入った"
    `.` は「全部」です。`git status` で確かめずに実行すると、パスワードを書いた設定ファイルなどが混ざります。`git add` のあとで `git status` を見る習慣にしてください。

??? failure "`git push --force` で、他の人のコミットを消した"
    `--force` は、リモートの履歴を自分のもので上書きします。共有している枝（特に `main`）には使いません。どうしても必要なら、安全側の `--force-with-lease` を使い、事前に相手へ伝えます。

??? failure "どこにも属さない状態（detached HEAD）になった"
    コミットの ID を指定して移動すると、枝の上にいない状態になります。そこで作ったコミットは、枝に戻ると見失います。残したければ、その場で `git switch -c 新しい枝名` を実行して、枝にしてください。

## これだけ覚える {#summary}

- 作業の流れは `git pull` → 直す → `git add` → `git commit` → `git push`
- 機能ごとに枝を分け、小さくこまめにコミットして、早めにマージする
- コンフリクトの目印（`<<<<<<<` `=======` `>>>>>>>`）を消して、`add` と `commit` で完了する
- `.gitignore` は、最初のコミットの前に置く
- `--force` と `restore` は、取り消せない。実行する前に `git status` で確かめる
