# ビルド（コンパイルとリンク）

ビルドは <strong>ソースコードを実行できるファイルにする作業全体</strong>です。F5 や Ctrl + Shift + B を押した裏側で、「前処理 → コンパイル → リンク」が順に動き `.exe` ができます。エラーがどの段階で出たのかが分かると、直し方の見当がつきます。

!!! tip "ポイント"
    - ビルドは <strong>前処理 → コンパイル → リンク</strong>の順。`.cpp` ごとに `.obj` を作り最後に 1 つにつなぐ
    - エラーの番号で段階が分かる。`C` で始まるのはコンパイル、`LNK` で始まるのはリンク
    - Visual Studio のビルドは、MSBuild が動かしている。変更のあったファイルだけを作り直す
    - 全部が毎回ビルドされるならヘッダーの依存とプリコンパイル済みヘッダー（`pch.h`）を疑う
    - コマンド ラインでも同じビルドができる（`cl`、`msbuild`）

## ビルドの流れ {#flow}

`main.cpp` と `game.cpp` の 2 つがあるプロジェクトで、`Game.exe` ができるまでを見ます。

```text
main.cpp ──前処理──► 展開されたソース ──コンパイル──► main.obj ─┐
                                                                ├─リンク─► Game.exe（と Game.pdb）
game.cpp ──前処理──► 展開されたソース ──コンパイル──► game.obj ─┘
                                           ↑
                              ライブラリ（.lib）も、リンクのときに入る
```

| 段階 | 道具 | 入力 → 出力 | やること |
| --- | --- | --- | --- |
| ① 前処理 | `cl.exe` | `.cpp` → 展開されたソース | `#include` を中身で置き換える。`#define` を展開する。`#if` で使わない部分を捨てる |
| ② コンパイル | `cl.exe` | 展開されたソース → `.obj` | C++ の文法を調べて、機械語にする。型の間違いや宣言の抜けはここで見つかる |
| ③ リンク | `link.exe` | `.obj` と `.lib` → `.exe` または `.dll` | 別々の `.obj` にある関数や変数をつなぎ合わせる。見つからない関数はここで見つかる |

### 前処理：ヘッダーがまるごと取り込まれる

`#include <print>` は `print` というヘッダーの中身を**そのままその場所にコピーする**命令です。標準ライブラリのヘッダーは展開すると、数万行にもなります。`.cpp` が 100 個あれば 100 回、同じヘッダーを読み込んでいることになります。ビルドが遅くなる最大の原因はここです（[プリコンパイル済みヘッダー](#pch)）。

展開した結果は次のコマンドで確認できます。

```bash
cl /std:c++latest /EHsc /P main.cpp
```

`main.i` ができます。`/P` は「前処理だけしてファイルに出す」オプションです。

### コンパイル：1 つの `.cpp` ごとに別々に

コンパイルは`.cpp` を 1 つずつ別々に行います。このとき、コンパイラはほかの `.cpp` を見ません。見えているのは `#include` で取り込んだ宣言だけです。

だから、関数を宣言（`void Update();`）しただけで本体（定義）が別の `.cpp` にあっても、コンパイルは通ります。実際に本体が見つからないことはリンクで初めて分かります。

### リンク：バラバラの部品をつなぐ

リンカーは `.obj` ファイルの中にある「この関数を呼びたい」「この関数を持っている」という名簿を突き合わせます。呼ばれているのに持っている人がいなければ、エラーです。

| エラー | 意味 | よくある原因 |
| --- | --- | --- |
| `LNK2019`（外部シンボルを解決できません） | 呼ばれた関数の本体がどこにもない | `.cpp` をプロジェクトに入れ忘れた。`.lib` をリンクしていない |
| `LNK2005`（すでに定義されています） | 同じ関数や変数が 2 か所にある | ヘッダーに関数の本体を書いた（`inline` を付けていない） |
| `LNK1104`（ファイルを開けません） | リンクする `.lib` が見つからない | `追加のライブラリ ディレクトリ` が、間違っている |
| `LNK2038`（不一致が検出されました） | ランタイム ライブラリ（`/MD` と `/MDd`）などが違う | 構成が違うライブラリを混ぜた |

## エラーの番号の見方 {#error}

出力ウィンドウやエラー一覧に出るコードで、段階が分かります。

| コード | 段階 | 例 |
| --- | --- | --- |
| `C1xxx` | コンパイラの前処理・内部の問題 | `C1083`：ヘッダーが開けない（`#include` の名前、またはインクルード パスの間違い） |
| `C2xxx` | コンパイラの文法・型のエラー | `C2065`：宣言されていない識別子 |
| `C4xxx` | コンパイラの警告 | `C4819`：文字コードの警告 |
| `LNKxxxx` | リンカー | `LNK2019`、`LNK1104` |
| `MSBxxxx` | MSBuild | `MSB8020`：ツールセットが見つからない |
| `D8xxx` | コマンド ラインの指定の問題 | `D8016`：オプションが同時に使えない |

エラーの文章を読むのは最初の 1 つだけにします。**最初のエラーが次のエラーを何個も連れてきている**ことが多いからです。

## Visual Studio のビルドのメニュー {#menu}

| 操作 | 内容 |
| --- | --- |
| ビルド（Ctrl + B） | 現在のプロジェクトを**変更があった分だけ**ビルド |
| ソリューションのビルド（Ctrl + Shift + B） | ソリューション全体を変更があった分だけビルド |
| リビルド | 先にクリーンしてから、すべてビルドし直す |
| クリーン | 中間ファイルと成果物を消す |
| コンパイル（Ctrl + F7） | いま開いている 1 つの `.cpp` だけをコンパイル（リンクはしない） |
| F5 | ビルドしてデバッグ実行 |
| Ctrl + F5 | ビルドして、デバッグなしで実行 |

困ったときはクリーンしてからビルド（またはリビルド）します。古い中間ファイルが残っていて、変なエラーが出るときこれで直ることがあります。

## 作られるファイル {#output}

ビルドすると次のようなファイルができます。

| 拡張子 | 内容 | 場所 |
| --- | --- | --- |
| `.obj` | 1 つの `.cpp` をコンパイルした結果 | 中間ディレクトリ（`x64\Debug\` など） |
| `.exe` | 実行ファイル | 出力ディレクトリ |
| `.dll` | 動的ライブラリ | 出力ディレクトリ |
| `.lib` | 静的ライブラリ。または、DLL を使うための目録（インポート ライブラリ） | 出力ディレクトリ |
| `.pdb` | デバッグ情報（変数名・行番号・型の情報） | 出力ディレクトリ |
| `.ilk` | 増分リンクの作業用データ | 出力ディレクトリ |
| `.exp` | DLL のエクスポート情報（リンクの途中でできる） | 出力ディレクトリ |
| `.pch` | プリコンパイル済みヘッダー | 中間ディレクトリ |
| `.tlog` | どのファイルを読んで、何を作ったかの記録 | 中間ディレクトリの `*.tlog` フォルダー |

`.pdb` は `.exe` とセットで保管します。クラッシュのダンプを解析したりデバッグを行ったりするときにこのファイルが無いと、変数名や行番号が見えなくなります。配布する `.exe` と同じビルドで作られた `.pdb` を残しておきます。

## 変更があった分だけ作る仕組み（増分ビルド） {#incremental}

Visual Studio は毎回、全部を作り直すわけではありません。**どのファイルを読んで何を作ったか**を `.tlog` というファイルに記録しています。次のビルドのときに読んだファイルの更新時刻が成果物より新しいものだけを作り直します。

| 変えたもの | 作り直されるもの |
| --- | --- |
| `game.cpp` | `game.cpp` だけをコンパイルして、リンクし直す |
| `game.h`（それを `#include` している `.cpp` が 10 個） | その 10 個の `.cpp` をコンパイルして、リンクし直す |
| `pch.h`（全員が使う） | すべての `.cpp` |
| プロパティ（コンパイラのオプション） | すべての `.cpp` |

ヘッダーを 1 行変えただけで、数十個の `.cpp` が作り直されることがあります。ビルドを速くするにはヘッダーの `#include` を減らすのが、一番効きます。

- ヘッダーには `#include` ではなく、前方宣言（`class Player;`）で済ませられるものは、前方宣言にする
- 大きなヘッダー（`<windows.h>`、`<d3d11.h>`）を `.h` の中で読み込まず `.cpp` の中に書く
- 変更の多いヘッダーとほとんど変わらないヘッダーを分ける

## プリコンパイル済みヘッダー（pch） {#pch}

標準ライブラリや `<windows.h>` のようなほとんど変わらないヘッダーを <strong>一度だけ解析して、結果を保存しておく</strong>仕組みです。これで `.cpp` ごとに数万行を読み直す手間が省けます。

### 使い方

1. `pch.h` を作って変わらないヘッダーを書く

```cpp
// pch.h
#pragma once

#include <algorithm>
#include <cstdint>
#include <memory>
#include <print>
#include <string>
#include <vector>

#include <d3d11.h>
```

2. `pch.cpp` を作って `pch.h` だけを書く

```cpp
// pch.cpp
#include "pch.h"
```

3. プロジェクトのプロパティ → C/C++ → プリコンパイル済みヘッダーを設定する

| 対象 | 設定 | 値 |
| --- | --- | --- |
| プロジェクト全体 | プリコンパイル済みヘッダー | 使用する（`/Yu`） |
| プロジェクト全体 | プリコンパイル済みヘッダー ファイル | `pch.h` |
| `pch.cpp` だけ | プリコンパイル済みヘッダー | 作成する（`/Yc`） |

4. すべての `.cpp` の一行目に `#include "pch.h"` を書く

!!! warning "pch.h は、`.cpp` の一番最初に書く"
    `/Yu` を使うと`#include "pch.h"` より前にあるものは、すべて無視されます。一行目より前に `#include <vector>` などを書くとその行が消えたように扱われ不思議なエラーになります。

### 向かないもの

`pch.h` には「ほとんど変わらないもの」だけを入れます。自分のゲームのヘッダーを入れると、そのヘッダーを変えるたびにすべての `.cpp` を作り直すことになります。逆効果です。

## 並列ビルド {#parallel}

| 設定 | 場所 | 効果 |
| --- | --- | --- |
| `/MP` | C/C++ → 全般 → 複数プロセッサによるコンパイル | **1 つのプロジェクトの中の** `.cpp` をコアの数だけ並列にコンパイルする |
| プロジェクトの並列ビルド | ツール → オプション → プロジェクトおよびソリューション → ビルドして実行 → 並列プロジェクト ビルドの最大数 | プロジェクト同士を並列に作る |

この 2 つは別の設定です。両方を有効にしておきます。`/MP` は `/Gm`（最小リビルド）と同時には使えません。新しいプロジェクトでは `/Gm` は既定で無効になっています。

## コマンド ラインでビルドする {#cli}

IDE を使わずコマンド ラインでもビルドできます。**CI や自動ビルドで使います。** 準備として Visual Studio の Developer Command Prompt（スタート メニューの「x64 Native Tools Command Prompt for VS」）を開きます。ここで開くと `cl.exe` などへのパスが設定済みです。

### cl で直接ビルドする

```bash
cl /std:c++latest /EHsc /utf-8 /W4 /O2 main.cpp game.cpp /Fe:Game.exe
```

| オプション | 意味 |
| --- | --- |
| `/std:c++latest` | 最新の C++ の機能を有効にする（[C++23 を使えるようにする設定](../settings.md)） |
| `/EHsc` | C++ の例外処理を有効にする。付けないと警告が出る |
| `/utf-8` | ソースと実行時の文字コードを UTF-8 にする（[文字コードを UTF-8 にしよう](../utf8.md)） |
| `/W4` | 警告レベル 4 |
| `/O2` | 速度を優先して最適化する |
| `/Fe:Game.exe` | 出力する実行ファイルの名前 |
| `/c` | コンパイルだけ行う（リンクしない）。`.obj` ができる |
| `/Zi` | デバッグ情報（`.pdb`）を作る |
| `/MD` | ランタイム ライブラリを DLL で使う |
| `/I パス` | インクルード ディレクトリを追加する |
| `/D 名前` | マクロを定義する（`/DNDEBUG` など） |
| `/link ...` | これ以降をリンカーに渡す |

`cl` に `.cpp` を複数渡すと前処理・コンパイル・リンクを続けて行います。`/c` を付けて `link` を別に呼ぶと段階を分けて実行できます。

```bash
# 段階を分けて実行する
cl /c /std:c++latest /EHsc /utf-8 main.cpp game.cpp
link main.obj game.obj /OUT:Game.exe
```

### msbuild でソリューションをビルドする

```bash
msbuild MyGame.sln /p:Configuration=Release /p:Platform=x64 /m /v:minimal
```

| 引数 | 意味 |
| --- | --- |
| `/p:Configuration=Release` | 構成（[構成](configuration.md#cli)） |
| `/p:Platform=x64` | プラットフォーム |
| `/m` | プロジェクトを並列にビルドする |
| `/v:minimal` | 出力の詳しさ（`quiet`、`minimal`、`normal`、`detailed`、`diagnostic`） |
| `/t:Rebuild` | リビルドする（`Build`、`Clean`、`Rebuild`） |

`msbuild` が `'msbuild' は、内部コマンドまたは外部コマンド…として認識されていません` と言うときは Developer Command Prompt で開いていません。

## ビルドの出力を詳しく見る {#log}

ビルドがうまくいかないとき出力ウィンドウの詳しさを上げると、**実際にコンパイラに渡されたコマンド**が見えます。

1. ツール → オプション → プロジェクトおよびソリューション → ビルドして実行
2. 「MSBuild プロジェクトのビルド出力の詳細度」を 詳細（または、診断）にする

出力には `cl.exe` に渡されたすべてのオプションが出ます。プロパティ画面の設定が本当にコマンドに反映されているか確認できます。

ヘッダーの読み込み状況を調べるときは、`/showIncludes` を使います。どのヘッダーが何から読み込まれているか一覧で見えます。

```text
C/C++ → コマンド ライン → 追加のオプション:  /showIncludes
```

## よくあるミス

??? failure "ビルドは通るのに、実行すると古い動作をする"
    ビルドが失敗していることに気づいていません。**出力ウィンドウで「ビルド: 1 正常終了、0 失敗」を確認します。** エラーがあるのに「実行しますか？」と聞かれて、古い `.exe` を起動することがあります。

??? failure "ヘッダーを変えたのに、反映されない"
    ヘッダーの更新時刻が未来の日付になっていると増分ビルドが「変更なし」と判断することがあります。クリーンしてビルドし直します。ネットワーク ドライブや時計のずれた環境で起きます。

??? failure "リンク エラーの `LNK2019` が出る"
    関数の宣言はあるが定義（本体）がありません。次を順に確認します。
    ① 本体を書いた `.cpp` が、プロジェクトに入っているか
    ② 外部ライブラリの `.lib` をリンカーの入力に書いたか
    ③ `extern "C"` の有無、名前空間、`const` の違いなど宣言と定義が本当に同じか

??? failure "毎回、ビルドが長い"
    `pch.h` を使っていない `/MP` が無効、ヘッダーに余計な `#include` がある、などを疑います。ビルドの時間は `/Bt+` ではなく Visual Studio の「ビルド インサイト」（Build Insights）などのツールで測ると、どのヘッダーが重いか分かります。
