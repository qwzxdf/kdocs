# チーム開発の進め方

一人で作っているうちは、どこをどう直しても自分しか困りません。人数が 2 人、3 人と増えると、「同じファイルを同時に直して衝突する」「誰かが壊したビルドで全員の作業が止まる」「コードの書き方が人によって違って読みにくい」といった問題が一気に出てきます。

これらは、ツールと決まりごとで、かなり減らせます。このページは、ブランチの切り方、プルリクエスト、レビュー、書き方の自動整形をまとめます。

!!! tip "ポイント"
    - `main` は、いつでも動く状態に保つ。作業は枝を切って行い、プルリクエストで `main` に入れる
    - 枝は短く、プルリクエストは小さく。大きいと、レビューも衝突の解決も重くなる
    - レビューの目的は、誰かのミスを探すことより、チーム全員がコードを知っている状態を作ること
    - 書き方の議論は人間がせず、`.editorconfig` と `clang-format` に任せる

!!! info "このページを読む前に"
    - [Git の基礎](git.md)（ブランチ、マージ、コンフリクト）
    - [.editorconfig](editorconfig.md)（改行や字下げをそろえる）

## ブランチの切り方 {#branch}

もっとも単純で、小さなチームで扱いやすい方法は、`main` と、機能ごとの短い枝だけを使うやり方です。

```text title="枝の流れ"
main      ●───●───────●───────●
               \     /         \
feature/enemy   ●───●           \
                                 ●───● feature/ui
```

1. `main` を最新にする（`git pull`）
2. `feature/enemy` のような枝を切る
3. 作業して、こまめにコミットする
4. 終わったら push して、プルリクエストを作る
5. レビューが通ったら、`main` に入れる。枝は消す

枝の寿命は、長くても数日にします。1 か月続いた枝は、`main` とのずれが大きくなり、マージのコンフリクトを解く手間のほうが、機能を作る手間を超えがちです。大きな機能は、「ステージ 1 だけ」のように分けて、段階的に `main` に入れます。

## プルリクエスト {#pr}

プルリクエスト（PR）は、「この枝の変更を `main` に入れてください」というお願いです。GitHub 上で、変更の差分を見て、コメントを付けて、承認してから合体します。

PR には、次の 3 つを書きます。

- 何を変えたか（1〜3 行）
- なぜ変えたか（バグの再現手順や、機能の目的）
- どう確認したか（動かして見た画面や、手順）

PR は<strong>小さく</strong>保ちます。目安は、変更ファイル数が 10 前後、差分が数百行までです。1,000 行を超える差分は、レビューする側が実際には読まなくなります。

`main` への直接の push を GitHub の設定で禁止する（ブランチ保護）と、PR 経由に強制でき、うっかり壊す事故が減ります。

## レビュー {#review}

レビューで見るのは、主に次の点です。

| 観点 | 見ること |
| --- | --- |
| 動作 | 意図した動きになるか。境界の値（0、最大、空）で壊れないか |
| 読みやすさ | 名前が内容に合っているか。コメントが必要な所にあるか |
| 設計 | 既存の構造に沿っているか。同じ処理が他にないか |
| 安全 | メモリの解放や、ぬるぽ（`nullptr`）の確認が抜けていないか |

書式（字下げ、空白）は、レビューで指摘しません。自動整形に任せます。指摘は<strong>コードに対して</strong>書き、人には向けません。「この書き方だと〜が起きそうです」のように、理由を添えると、受け取る側も直しやすくなります。

## 書き方の自動整形 {#format}

「波括弧を改行するか」のような好みの違いは、議論しても結論が出ません。決めてしまって、ツールに守らせます。

- `.editorconfig`: 文字コード、改行、字下げの幅。エディターが読む
- `.clang-format`: 波括弧の位置、行の長さ、`#include` の順番。`clang-format` が整形する

```yaml title=".clang-format"
BasedOnStyle: Google
ColumnLimit: 100
```

Visual Studio は `.clang-format` を読みます。「ツール → オプション → テキスト エディター → C/C++ → コード スタイル → 書式設定」で `clang-format` のサポートを有効にします。保存時に整形する設定にしておけば、人が気にしなくてもそろいます。

整形の差分と機能の差分を 1 つのコミットに混ぜないでください。整形だけのコミットを別に作ると、PR の差分が読みやすくなります。

## 衝突を減らす工夫 {#conflict}

- `.sln` と `.vcxproj` は、ファイルを追加するたびに触られて、衝突しやすい。ファイルを足したら、すぐ PR を出して `main` に入れる
- 同じファイルを複数人が直しそうなときは、先に声をかける
- 毎日、始めに `main` を取り込む（`git pull`、枝の上なら `git merge main`）。ずれが小さいうちは、衝突も小さい
- 巨大な 1 ファイルに機能を詰め込まない（分けておけば、同時に触りにくい）

## よくあるミス {#mistakes}

??? failure "`main` が壊れたまま放置された"
    ビルドが通らないコミットが `main` に入ると、全員の作業が止まります。まず元に戻す（`git revert`）ことを優先し、原因の調査はあとで行います。自動ビルドの [GitHub Actions](github-actions.md) で、PR のビルドを確認すると防げます。

??? failure "PR が大きすぎて、誰も見ない"
    機能を分けて、小さい PR を複数出します。「まず下準備だけの PR」「次に機能の本体の PR」と段階を踏むと読みやすくなります。

## これだけ覚える {#summary}

- `main` は常に動く。作業は短い枝で、PR 経由で入れる
- PR は小さく、理由と確認方法を書く
- 書き方は人が議論せず、`.editorconfig` と `clang-format` に任せる
