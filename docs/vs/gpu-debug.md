# GPU デバッグの流れ（真っ黒・一部だけ消える）

描画のプログラムは、間違えても、エラーを出さずに黒い画面を返すことがほとんどです。原因の候補は、バッファの中身、行列、シェーダー、ステート、リソースの状態と数十個あり、闇雲に探すと半日が消えます。

効率のよい探し方は、<strong>症状から原因の範囲を絞り、疑いの強いものから 1 つずつ潰す</strong>ことです。このページは、よくある症状ごとの絞り込み方をまとめます。

!!! tip "ポイント"
    - 最初に、デバッグ レイヤー（DX11 は `D3D11_CREATE_DEVICE_DEBUG`、DX12 は `ID3D12Debug`）を有効にして、警告とエラーを読む
    - 次に、フレームを捕まえて（[RenderDoc / PIX](renderdoc-pix.md)）、描画呼び出しが実際に発行されているか見る
    - 「入力が正しいか」「シェーダーが正しいか」「出力先が正しいか」の 3 段で切り分ける
    - 単純化が最強の手。シェーダーの出力を定数色にする、行列を単位行列にする、と 1 つずつ外す

!!! info "このページを読む前に"
    - [RenderDoc と PIX](renderdoc-pix.md)（フレームのキャプチャ）

## 最初にやること {#first}

症状が何であれ、次の順に確認します。

1. <strong>デバッグ レイヤーのメッセージを読む</strong>。DX11 も DX12 も、API の誤用をほぼ文章で教えてくれる。出力ウィンドウに出る
2. <strong>`HRESULT` を確認する</strong>。`CreateXxx` が失敗していて、`nullptr` のまま描いていないか
3. <strong>フレームをキャプチャして、Draw が発行されているか見る</strong>。ゼロなら、描画の呼び出しまで届いていない

この 3 つで、原因の半分は見つかります。

## 症状別の絞り込み {#symptoms}

### 画面が真っ黒 {#black}

何も描かれていない可能性と、描かれたが見えていない可能性があります。

| 確認 | 見る場所 |
| --- | --- |
| クリアの色を変えてみる（赤にするなど） | 赤くならないなら、スワップチェーンの Present か、レンダーターゲットの設定が違う |
| Draw が発行されているか | キャプチャで、Event Browser に Draw があるか |
| 頂点が画面に入っているか | Mesh Viewer で、頂点シェーダーの出力位置が `-1〜1` の範囲にあるか |
| ビューポートとシザー矩形 | 幅や高さが 0 になっていないか |
| カリング | 面の向きが逆（巻き順）で、全部が裏として消えていないか |
| 深度 | 深度テストで全部が落ちていないか（クリア値や比較関数） |

ここでよく起きるのが、<strong>行列の掛け順や転置の間違い</strong>です。頂点シェーダーの出力を行列抜きの定数にして見えれば、行列が原因と分かります。

### 一部だけ消える {#partial}

全体は出るが、一部のオブジェクトが出ない場合です。

- そのオブジェクトの Draw はあるか。ない場合は、描画対象の判定（カリング、可視判定）を疑う
- Draw があるのに見えない場合は、頂点の位置、ワールド行列、近い面・遠い面で切られていないか（クリップ）を見る
- 巻き順が違う面だけ消える場合は、[ラスタライザー](../directx/dx11/rasterizer-state.md) のカリング設定を疑う
- 半透明が消える場合は、描く順番と、深度の書き込みを疑う

### 色や模様がおかしい {#color}

- 真っ白・真っ黒の場合は、テクスチャが読めていない。SRV にテクスチャが入っているか、UV が 0〜1 の範囲か
- 色が暗い・明るい場合は、ガンマ（sRGB フォーマットの扱い）が合っていない
- ノイズやちらつきの場合は、リソースを GPU が使っている最中に CPU が書き換えている（同期の不足）
- 縞模様の場合は、法線が逆、または深度の精度が不足している

### 図形が歪む・引き伸ばされる {#distort}

- 頂点バッファのストライド（1 頂点のバイト数）と、入力レイアウトが合っていない
- 行列の転置を間違えた（HLSL は列優先がすでに既定。CPU 側が行優先ならば、転置が必要になる）
- 定数バッファのパディング（16 バイト境界）が合っていない

### GPU がクラッシュする（デバイスロスト） {#device-lost}

DX12 では、`DXGI_ERROR_DEVICE_REMOVED` が返ります。原因は、不正なリソースの参照、バリアの不足、無限ループなどです。`GetDeviceRemovedReason()` で理由を読み、PIX の GPU Capture か、DRED（Device Removed Extended Data）で、最後に動いていた命令を調べます。

## 単純化して切り分ける {#simplify}

原因が見えないとき、機能を 1 つずつ外します。

1. ピクセルシェーダーの出力を `return float4(1, 0, 0, 1);` にする。赤く出れば、ジオメトリとステートは正しく、シェーダーの内容に原因がある
2. 頂点シェーダーに、行列を掛けずに、座標をそのまま出す。三角形が出れば、行列の問題
3. 法線を色として出す（`return float4(normal * 0.5 + 0.5, 1);`）。向きの確認ができる
4. UV を色として出す。テクスチャ座標の確認ができる

値を色として出すのは、シェーダーの printf デバッグです。どの値がおかしいかが、画面で分かります。

## よくあるミス {#mistakes}

??? failure "デバッグ レイヤーを切ったまま、何時間も探した"
    最初に有効にしてください。誤用の大半は、メッセージ 1 行で分かります。

??? failure "Release ビルドでだけ壊れる"
    未初期化の変数や、最適化で顕在化するタイミングの問題が多いです。デバッグ情報つきの Release でキャプチャを取り、比べます。

??? failure "変更を一度にたくさん入れて、原因が絞れなくなった"
    1 つ直しては確認する、を繰り返します。うまく動いたら、コミットします（[Git の基礎](git.md)）。

## これだけ覚える {#summary}

- 最初に、デバッグ レイヤーを有効にして、メッセージを読む
- キャプチャして、Draw があるか、入力・シェーダー・出力のどれが違うか分ける
- シェーダーの出力を定数や、値の色表示にして、単純化して切り分ける
