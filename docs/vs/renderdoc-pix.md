# RenderDoc と PIX（フレームを捕まえて調べる）

画面が真っ黒、モデルが出ない、色がおかしい。描画の不具合は、C++ のデバッガーで止めても、原因が見えません。CPU 側の変数は正しく見えても、GPU に何が渡って、何が描かれたのかは、デバッガーからは分からないからです。

RenderDoc と PIX は、<strong>1 フレーム分の描画命令を丸ごと記録し、あとから 1 つずつ再生しながら、そのときの状態を調べられる</strong>ツールです。どの描画呼び出しで何が変わったか、テクスチャの中身、定数バッファの値、シェーダーの入出力まで見えます。

!!! tip "ポイント"
    - RenderDoc は無料で、DX11・DX12・Vulkan・OpenGL に対応。PIX は Microsoft 製で、DX12 向け（DX11 は未対応）
    - 使い方は共通で、起動 → 実行 → キャプチャ → 描画呼び出しを 1 つずつ辿る
    - 描画呼び出しの前後で、レンダーターゲットが変わる様子を見ると、どこで壊れたか分かる
    - シェーダーのデバッグ情報を付けて（`/Zi`）ビルドすると、HLSL のソースで見られる

## 2 つのツールの使い分け {#choose}

RenderDoc は、DX11 を使うなら、最初の選択肢です。軽く、使い方の情報も多いです。DX12 では、RenderDoc も PIX も使えます。PIX は DX12 の機能（バリア、ディスクリプタ、GPU の計測）に詳しく、パフォーマンスの計測も得意です。

どちらを使うかを悩む必要はありません。症状が見えにくければ、もう片方でも開いてみます。同じ現象が片方でだけ見つけやすいことがあります。

## RenderDoc の使い方 {#renderdoc}

### 起動してキャプチャする {#renderdoc-capture}

1. RenderDoc を起動し、「Launch Application」タブを開く
2. 「Executable Path」にゲームの `.exe` を指定する（Debug ビルドで構いません）
3. 「Launch」を押すと、ゲームが起動する
4. ゲーム画面の上に出る表示を見ながら、F12 キーを押すと、そのフレームが記録される
5. RenderDoc に戻ると、キャプチャが一覧に追加されている。ダブルクリックで開く

記録するのは 1 フレームです。不具合が出ている瞬間に押してください。画面が止まる、動きが速すぎるときは、ゲーム側にポーズ機能があると便利です。

### 画面の見方 {#renderdoc-ui}

| 画面 | 見えるもの |
| --- | --- |
| Event Browser | フレームの描画命令（`Draw`、`Dispatch`、`Clear` など）が順番に並ぶ。クリックした時点の状態に移る |
| Texture Viewer | その時点のテクスチャとレンダーターゲット。入力と出力の画像を見る |
| Pipeline State | シェーダー、ブレンド、深度、ラスタライザーなど、パイプラインの設定 |
| Mesh Viewer | 頂点データと、頂点シェーダーを通った後の位置 |
| Pixel History | 1 ピクセルにどの描画がどう書き込んだかの履歴 |

不具合の調べ方は、Event Browser で下から上へまたは上から下へ `Draw` を 1 つずつ選び、Texture Viewer の出力が変わる所を探すことです。「この Draw の前は正しい、この Draw の後におかしくなった」と分かれば、その描画の設定やシェーダーを疑えます。

### 1 ピクセルの原因を調べる {#renderdoc-pixel}

Texture Viewer で、おかしな色のピクセルを右クリックして「Pixel Context」を選ぶと、そのピクセルを見られます。「History」を押すと、そのピクセルに書き込んだ描画が時間順に並び、深度テスト、ブレンド、シェーダー出力のどこで落ちたか分かります。

そこから「Debug this Pixel」で、ピクセルシェーダーを 1 行ずつ追えます。シェーダーを `/Zi` 付きでコンパイルしておくと、HLSL のソースが見えます。

## PIX の使い方 {#pix}

PIX は Microsoft Store か、公式サイトから入れます。DX12 のゲームを起動して、「GPU Capture」を使います。

1. PIX を起動し、「Home」→「Select target process」→「Launch Win32」で `.exe` を指定する
2. 「GPU Capture」を選び、起動する
3. ゲームの画面が出たら、PIX のカメラのアイコンを押して 1 フレームを記録する
4. 記録後、「Start Analysis」を押して解析する

解析が終わると、イベントの一覧（Events）、パイプラインの状態（Pipeline）、リソースの一覧（Resources）などが見られます。RenderDoc と違い、各描画呼び出しの GPU での実行時間（タイミング）も出せます。

## 見やすくする準備 {#prepare}

どちらのツールも、デバッグしやすいように準備すると、見え方が大きく変わります。

- <strong>リソースに名前を付ける</strong>: DX12 の `SetName`、DX11 の `SetPrivateData(WKPDID_D3DDebugObjectName, …)` で名前を付ける。ないと `Resource 1234` のように表示される
- <strong>描画をグループにする</strong>: `PIXBeginEvent` / `PIXEndEvent` で囲むと、イベント一覧が「シャドウ」「G バッファ」のような塊になる
- <strong>シェーダーのデバッグ情報</strong>: `/Zi /Od` 付きでコンパイルし、`.pdb` を残す。ソースで見られる

最初の 2 つは、描画の構造が大きくなるほど効きます。名前のないリソースが数百個並ぶ画面は、読むのがつらくなります。

## よくあるミス {#mistakes}

??? failure "キャプチャが空で、何も記録されない"
    ゲームが別のウィンドウで描画していたり、RenderDoc に未対応の機能を使っていたりします。DX12 では、デバッグレイヤーが有効だとうまくいかない場合があるので、切って試します。

??? failure "シェーダーのソースが見えず、アセンブリになる"
    `/Zi` が付いていません。`/Od`（最適化なし）も付けると、変数の値が消えずに追えます。

??? failure "キャプチャのときだけ、描画が違う"
    ツールがリソースの状態を再生するときの前提と違うことがあります。キャプチャ時の API のエラーを確認し、[デバッグ レイヤー](../directx/dx12/debug-layer.md) の警告が出ていないか見ます。

## これだけ覚える {#summary}

- 描画の不具合は、フレームを捕まえて、描画呼び出しを 1 つずつ辿って調べる
- RenderDoc は DX11・DX12 向けで無料。PIX は DX12 向けで、計測にも強い
- リソースの名前、イベントのグループ、シェーダーの `/Zi` を準備すると、見やすい
