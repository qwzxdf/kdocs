# コンパイラの最適化

C++ のコンパイラは、**ソースコードを速く動く機械語に変換する**とき、非常に多くの最適化を**自動で**行います。`i++` と `++i` の違いを気にしたり、小さな関数を手で `inline` にしたりする必要は、ほとんどありません。コンパイラがやってくれます。このページは**コンパイラに最適化してもらうためのオプション**と、**コンパイラが何をしてくれるか・何はしてくれないか**を知り、手で直す前に**コンパイラに任せられるところを任せる**ための知識をまとめます。

!!! tip "ポイント"
    - 速さを測るのは<strong>Release（最適化あり）</strong>。MSVC なら <strong>`/O2`</strong>（速度優先）。
    - 製品版は<strong>`/GL`（全体最適化）+ `/LTCG`</strong> も検討する。ビルドは遅くなるが速くなる。
    - 小さな書き方の工夫（`++i`、`inline`、ビット演算に直す）は、<strong>コンパイラがやるので不要</strong>。
    - コンパイラが<strong>できないこと</strong>は、アルゴリズム・メモリの並び・確保・コピー。ここは自分で直す。
    - <strong>`constexpr`</strong> で、コンパイル時に計算させられる。実行時の計算がなくなる。
    - 最適化されたコードで<strong>バグが出る</strong>なら、多くは未定義動作か、初期化されていない変数。

## 最適化レベル

| MSVC | 意味 | 使う場面 |
| --- | --- | --- |
| **`/Od`** | **最適化なし** | Debug。デバッグしやすい（変数が消えない） |
| **`/O1`** | サイズ優先 | 小さく作りたいとき（組み込み、モバイル） |
| **`/O2`** | **速度優先** | **Release の標準** |
| `/Ox` | 最大の最適化（`/O2` に近い） | 通常は `/O2` で十分 |
| `/Os` / `/Ot` | サイズ優先 / 速度優先（個別） | `/O1` / `/O2` に含まれる |

| GCC / Clang | MSVC に近いもの |
| --- | --- |
| `-O0` | `/Od` |
| `-O1`、`-Os` | `/O1` |
| `-O2` | `/O2` |
| `-O3` | `/O2` より積極的（ベクトル化、ループ展開が増える）。常に速いとは限らない |

プロパティ: **C/C++ → 最適化 → 最適化**（`/O2` を選ぶ）。Visual Studio の既定では、Debug は `/Od`、Release は `/O2` です。

## 製品版に効く追加オプション

### 全体最適化（LTO / LTCG）

通常は**ソースファイル（`.cpp`）ごと**にコンパイルするので、別のファイルの関数は、中身を見られません（インライン化できない）。**全体最適化**を使うと**リンク時に全ファイルを見渡して最適化**します。

| 設定（MSVC） | 意味 |
| --- | --- |
| **C/C++ → 最適化 → 全プログラムの最適化**: はい（**`/GL`**） | コンパイラが中間コードを残す |
| **リンカー → 最適化 → リンク時コード生成**: 使用（**`/LTCG`**） | リンク時に全体を最適化する |

- 別のファイルの関数も、インライン化できる。不要な関数の除去も効果的に
- **ビルドが遅くなる**ので、開発中の Release ではなく、**製品版ビルドで使う**ことも多い
- GCC / Clang では **`-flto`**

### プロファイル ガイド付き最適化（PGO）

**実際にゲームを動かして、どこが何回呼ばれたかを記録**し、その情報を使って、もう一度ビルドする方法です。よく通る分岐を優先して配置するなど、**5〜20% 速く**なることがあります。手順が複雑なので製品版の最後の仕上げに使います（MSVC: `/GENPROFILE` → 実行 → `/USEPROFILE`）。

### その他のオプション

| オプション（MSVC） | 意味 | 注意 |
| --- | --- | --- |
| **`/arch:AVX2`** | AVX2 命令を使ってよい | AVX2 非対応の CPU で動かなくなる（[SIMD](simd.md)） |
| **`/fp:fast`** | 浮動小数点の計算を厳密でなく速く | 結果が少し変わる。決定的なシミュレーションには不向き |
| `/fp:precise`（既定） | 厳密と速さのバランス | 通常はこれ |
| **`/Gy`**（関数レベルのリンク） + **`/OPT:REF`** | 使われていない関数を除去 | Release の既定で有効 |
| **`/Zc:inline`** | 使われていないインライン関数を、除去 | |
| `/GS-` | スタックの安全チェック（バッファ オーバーラン検出）を外す | 小さく速くなるがセキュリティが下がる。外さない |
| `/RTC`（ランタイム チェック） | **Debug だけ**。Release では使えない | |

## コンパイラがやってくれること

自分で書き換えなくてよい例です。

| 最適化 | 内容 |
| --- | --- |
| **インライン展開** | 小さな関数の呼び出しを、本体で置き換える（呼び出しのコストなし）。`inline` は、ヒント程度 |
| **定数畳み込み** | `3 * 4` をコンパイル時に `12` にする |
| **不要なコードの除去** | 使われない変数・到達しないコードを消す |
| **ループの最適化** | ループの外に出せる計算を出す、ループ展開、自動ベクトル化（[SIMD](simd.md)） |
| **強度低減** | `x * 2` を、`x + x` や シフトに。`x / 4` を、`x >> 2` に（符号なしなど条件による） |
| **レジスタ割り当て** | 変数をメモリではなく、CPU のレジスタに置く |
| <strong>コピーの省略（RVO）</strong> | 戻り値のコピーをなくす（[コピーとムーブ](copy-move.md)） |
| **分岐の最適化** | `if` の条件から、ありえない分岐を消す |

```cpp
// 書き換えなくてよい：コンパイラが同じ命令にする
int a = x * 2;       // と、x << 1 は、同じ
for (int i = 0; i < n; i++) {}    // と、++i は、同じ
```

## コンパイラがやってくれないこと

| 自分で直すもの | 理由 |
| --- | --- |
| **アルゴリズム**（O(n²) → O(n)） | コンパイラは計算量を変えられない |
| **メモリの並び**（AoS → SoA、ポインタの連鎖） | データ構造は変えられない |
| **メモリ確保の回数** | `new` の呼び出しを勝手には減らせない（一部は除去されることもある） |
| **無駄なコピー**（値渡し） | `const&` にするのは、自分 |
| **マルチスレッド化** | 自動では並列にならない |
| **仮想関数のコスト** | 型が決まっていれば、デバイルチャライズ（直接呼び出しに変換）されることがあるが期待しない |
| **ポインタのエイリアシングの疑い** | 同じメモリを指す可能性があると、最適化を控える。`__restrict` で教える |

## コンパイル時に計算する

**`constexpr`** を付けた関数や変数は、**コンパイル時に計算**できます。実行時には結果の値だけが残ります。

```cpp
// コンパイル時に計算される（実行時には、計算が残らない）
constexpr int Factorial(int n) {
  return n <= 1 ? 1 : n * Factorial(n - 1);
}
constexpr int kTable[] = {Factorial(1), Factorial(2), Factorial(3), Factorial(4)};   // 1, 2, 6, 24

// 実行時の定数の計算を、コンパイル時にやってしまう
constexpr float kDegToRad = 3.14159265f / 180.0f;
constexpr auto sin_table = []() {
  std::array<float, 360> t{};
  for (int i = 0; i < 360; ++i) t[i] = std::sin(i * kDegToRad);   // C++26 で、sin も constexpr に
  return t;
}();
```

| キーワード | 意味 |
| --- | --- |
| **`constexpr`** | コンパイル時に計算できる（実行時にも使える） |
| **`consteval`**（C++20） | **必ず**コンパイル時に計算する（実行時には呼べない） |
| **`constinit`**（C++20） | 静的変数をコンパイル時に初期化する（初期化順序の問題を避ける） |

- **ルックアップ テーブル**（サイン、イージング、ハッシュ値）を、コンパイル時に作る
- 文字列のハッシュを、コンパイル時に計算する（[std::hash](../stl/utilities/hash.md#fnv1a)）

## 最適化されたコードで、バグが出るとき

**Debug では動くのに、Release でだけおかしくなる**とき、原因はほぼ、次のどれかです。コンパイラのバグであることは、めったにありません。

| 原因 | 症状 | 見つけ方 |
| --- | --- | --- |
| **初期化されていない変数** | Debug はたまたま 0 で動き、Release はゴミが入る | 警告 `C4700`、全部の変数を初期化する |
| **未定義動作**（範囲外アクセス、符号付き整数のオーバーフロー、ダングリング） | 最適化でコンパイラが「起きない」と仮定して、消す | AddressSanitizer、UBSan（[未定義動作](../basics/ub.md)） |
| **スレッドのデータ競争** | タイミングで結果が変わる | ThreadSanitizer |
| **`volatile` の誤用** | スレッド間の同期に使っても、保証されない | `std::atomic` を使う |
| **浮動小数点の比較** | 最適化でレジスタの精度が変わる | `==` で比べず、誤差で比べる |

**確認の手順:** まず「最適化なしの Release」（`/Od`）で、再現するかを見ます。再現しなければ、最適化で起きる未定義動作の可能性が高いです。

## コンパイラの出力を見る

| 道具 | 使い方 |
| --- | --- |
| **Compiler Explorer**（godbolt.org） | ソースを貼ると生成された機械語が見られる。コンパイラやオプションを変えて、比べられる。**ベクトル化されたか、インライン化されたか**が分かる |
| **Visual Studio の逆アセンブリ** | デバッグ中に「デバッグ → ウィンドウ → 逆アセンブル」。Release で実際の命令を見る |
| **`/FA`**（アセンブリ リストの出力） | `.asm` ファイルを出力する |

## ゲームでの使いどころ

| 場面 | 設定・方法 |
| --- | --- |
| 開発中の普段のビルド | Debug が遅すぎるなら、「Development」構成（`/O2` + デバッグ情報 + assert 有効） |
| 製品版 | Release。`/O2`、`/GL` + `/LTCG`、不要な機能を無効に |
| 重いライブラリ（物理、数学） | ライブラリ自体を、Release でビルドしたものを使う（Debug のまま使うと、とても遅い） |
| ルックアップ テーブル | `constexpr` で、コンパイル時に作る |
| AVX2 を使いたい | `/arch:AVX2`。ただし、非対応の CPU への対応を決める |
| ビルドが遅い | `/MP`（並列コンパイル）、プリコンパイル済みヘッダ（[ビルドと CMake の構成](../design/practice/build-cmake.md)） |

## よくあるミス

??? failure "Debug のままで、速さを比べる"
    Debug は `/Od` と、標準ライブラリの検査で、何倍も遅いです。**Release で測ります**。

??? failure "小さな書き換えに、時間を使う"
    `++i`、`inline`、`x * 2` → `x << 1` などは、コンパイラが同じコードにします。アルゴリズムとメモリの使い方を直します。

??? failure "`/O3` や `/fp:fast` を理由なく入れる"
    結果が変わったり、かえって遅くなったりします。**測ってから**入れます。

??? failure "ライブラリを Debug でビルドして、Release のゲームにリンクする"
    ライブラリ側が最適化されず、ゲーム全体が遅くなります（ランタイム ライブラリの不一致のエラーにもなります）。ライブラリも Release で作ります。

??? failure "`volatile` で、スレッド間の変数を守る"
    `volatile` は、最適化を止めるだけでスレッド間の同期は保証されません。`std::atomic` を使います。
