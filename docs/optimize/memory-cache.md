# メモリとキャッシュ

現代の CPU は、**計算するより、メモリからデータを持ってくるほうが、ずっと遅い**です。CPU が 1 回の計算に使う時間が約 0.3 ナノ秒なのに対し、メインメモリからデータを読むのは約 80〜100 ナノ秒かかります。その差は、300 倍です。この差を埋めるのが キャッシュ（CPU のすぐ近くにある、小さくて高速なメモリ）です。キャッシュに乗っているデータを使えば速く、乗っていないと遅い。つまり、データをメモリ上にどう並べるかで、同じ処理が何倍も速くなったり、遅くなったりします。このページは、ゲームでよく効く、メモリの並べ方をまとめます（基礎は [キャッシュ効率](../basics/cache.md)）。

!!! tip "ポイント"
    - CPU は、メモリを<strong>キャッシュ ライン（64 バイト）</strong>の単位で読む。**近くのデータは、まとめて速く読める**。
    - 連続した配列（`std::vector`）を、前から順に読むのが、一番速い。
    - ポインタをたどるデータ（`list`、`map`、`vector<unique_ptr<T>>`）は、そのたびに遠いメモリを読んで、遅い。
    - 処理で使うデータだけを、近くに並べる（AoS → SoA、熱いデータと冷たいデータを分ける）。
    - 構造体は小さく。使わないメンバが大きいと、キャッシュを無駄にする。

## メモリの階層

| 階層 | 速さ | 大きさ |
| --- | --- | --- |
| レジスタ | 約 0 ns（最速） | 数百 B |
| L1 キャッシュ | 約 1 ns | 32〜64 KB |
| L2 キャッシュ | 約 4 ns | 数百 KB |
| L3 キャッシュ | 約 15 ns | 数 MB〜 |
| メインメモリ（RAM） | 約 80 ns | 数 GB |
| SSD | 約 100,000 ns（最遅） | 大きい |

上ほど速くて小さく、下ほど遅くて大きくなります。

| 場所 | 速さ（目安） | 大きさ（目安） |
| --- | --- | --- |
| **L1 キャッシュ** | 約 1 ns（数サイクル） | 32〜64 KB（コアごと） |
| L2 キャッシュ | 約 4 ns | 256 KB〜数 MB |
| L3 キャッシュ | 約 15 ns | 数 MB〜数十 MB（共有） |
| メインメモリ | 約 80 ns | 数 GB |

CPU がデータを要求したとき、L1 にあれば速く（ヒット）、なければ下の階層へ探しに行きます（ミス）。メインメモリまで行くと、L1 ヒットの約 100 倍かかります。この遅さを「キャッシュミス」と呼び、ゲームの遅さの大きな原因です。

## キャッシュ ライン

CPU は、メモリを 1 バイトずつではなく、<strong>64 バイトのかたまり（キャッシュ ライン）</strong>ごとに読み込みます。`int`（4 バイト）を 1 つ読むと、その周りの 64 バイト（`int` 16 個ぶん）が、一緒にキャッシュに入ります。

<div class="anim" data-label="連続した配列：1 回の読み込みで、まとめて取れる">
A B C D E F G H # 連続した 8 個（1 つの要素は 8 バイト）
*A *B *C *D *E *F *G *H # 1 回のメモリ読み込みで、キャッシュ ライン（64 バイト）ぶんが、全部手に入る
A B C D E F G H # 2 個目以降は、すでにキャッシュにあるので、速い（ヒット）
</div>

### 配列を順に読む vs ポインタをたどる

| 並べ方 | キャッシュの働き |
| --- | --- |
| `std::vector<Enemy>`（連続） | 1 体読むと、隣の敵も同じキャッシュ ラインに入る。次の読み込みは、ほぼヒット |
| `std::vector<std::unique_ptr<Enemy>>`（ポインタ） | 敵は、ヒープのあちこちにある。1 体ごとに、遠いメモリを読みに行く（ミス） |
| `std::list<Enemy>` | ノードがバラバラ。1 つずつポインタをたどる。最も遅い |

```cpp
// 遅い：敵がヒープに散らばる。1 体ごとにキャッシュミス
std::vector<std::unique_ptr<Enemy>> enemies;
for (auto& e : enemies) e->position += e->velocity * dt;

// 速い：敵のデータが、連続して並ぶ
std::vector<Enemy> enemies;
for (Enemy& e : enemies) e.position += e.velocity * dt;
```

「`vector<Enemy>` なら連続」ですが、`Enemy` が大きいと、1 体が数キャッシュ ラインを使います。次の「使うデータだけを並べる」が、さらに効きます。

## 使うデータだけを、近くに並べる

### AoS と SoA

```cpp
// AoS（構造体の配列）：1 体ぶんのデータが、まとまっている
struct Enemy {
  Vec3 position;     // 12 バイト
  Vec3 velocity;     // 12 バイト
  int hp;            // 4
  std::string name;  // 32  ← 位置の更新には使わない
  Mesh* mesh;        // 8   ← 同上
  // ... 合計 100 バイト以上
};
std::vector<Enemy> enemies;

// SoA（配列の構造体）：項目ごとに、別の配列
struct Enemies {
  std::vector<Vec3> position;
  std::vector<Vec3> velocity;
  std::vector<int> hp;
  std::vector<std::string> name;
};
```

「全員の位置を、速度で更新する」処理のとき、

<div class="anim" data-label="AoS と SoA：使うデータだけが、連続して並ぶ">
P V h n P V h n P V h n # AoS：位置 P と速度 V のほかに、hp h・名前 n も一緒に読み込まれる
*P *V h n *P *V h n *P *V h n # 位置と速度だけ使いたいのに、4 分の 2 しか役に立たない
P P P P V V V V # SoA：位置の配列と、速度の配列に分ける
*P *P *P *P *V *V *V *V # 読み込んだデータが、すべて使える。無駄がない
</div>

| 並べ方 | 向いている処理 |
| --- | --- |
| **AoS** | 1 体の全部の項目を、まとめて使う処理（描画、保存） |
| SoA | 一部の項目だけを、全員に対して処理する（位置の更新、当たり判定の前処理） |

SoA を徹底したものが、[ECS](../design/patterns/ecs.md) です。まず AoS で書いて、プロファイラーで遅いと分かったループだけを SoA にします。

### 熱いデータと冷たいデータを分ける

毎フレーム使う（熱い）データと、たまにしか使わない（冷たい）データを、別の構造体に分けます。

```cpp
// 熱い：毎フレーム全員が使う（小さくまとめる）
struct EnemyHot {
  Vec3 position;
  Vec3 velocity;
  int hp;
};

// 冷たい：たまにしか使わない（名前、説明文、ドロップ表など）
struct EnemyCold {
  std::string name;
  std::string description;
  std::vector<int> drops;
};

std::vector<EnemyHot> hot;     // 連続して並ぶ。小さい
std::vector<EnemyCold> cold;   // hot[i] と cold[i] が、同じ敵
```

## 構造体を小さくする

構造体の大きさが、**キャッシュ ラインに何個入るか**を決めます。小さいほど、一度に多く読めます。

### パディング（隙間）に注意

メンバの並びによって、コンパイラが隙間（パディング）を入れて、アライメントをそろえます。

```cpp
struct Bad {
  bool a;      // 1 バイト + 7 バイトの隙間
  double b;    // 8 バイト
  bool c;      // 1 バイト + 7 バイトの隙間
};             // 合計 24 バイト

struct Good {
  double b;    // 8 バイト
  bool a;      // 1
  bool c;      // 1 + 6 バイトの隙間（末尾）
};             // 合計 16 バイト
```

| 工夫 | 説明 |
| --- | --- |
| 大きい型から順に並べる | `double`、`int64`、`int`、`short`、`bool` の順にすると、隙間が減る |
| 小さい型にする | `int` で足りるなら `int8_t` / `int16_t`、`double` で足りるなら `float` |
| `bool` を並べるなら、ビット フィールド | 8 個のフラグを 1 バイトに |
| `sizeof` を確認する | `static_assert(sizeof(Enemy) == 64);` で、大きさを固定して、増えたら気づく |
| キャッシュ ラインにそろえる | `alignas(64)` で、64 バイトの境界に置く（複数スレッドでの false sharing 対策） |

## アクセスの順番

| コツ | 説明 |
| --- | --- |
| **前から順に読む** | CPU が、次を先読み（プリフェッチ）してくれる。ランダムに飛ぶと、先読みが効かない |
| 多次元配列は、内側のループを「連続する方向」に | `a[y][x]` なら、`x` を内側のループに（行ごとに連続している） |
| ポインタをたどる回数を減らす | `a->b->c->d` のような、長い連鎖を避ける。必要な値を、近くにコピーしておく |
| 処理を種類ごとにまとめる | 同じ処理を、同じ種類のものにまとめて行う（命令キャッシュにも優しい） |

```cpp
// 遅い：列方向（メモリが飛ぶ方向）が、内側のループ
for (int x = 0; x < width; ++x)
  for (int y = 0; y < height; ++y)
    sum += grid[y * width + x];

// 速い：行方向（メモリが連続する方向）が、内側のループ
for (int y = 0; y < height; ++y)
  for (int x = 0; x < width; ++x)
    sum += grid[y * width + x];
```

## false sharing（複数スレッドでの罠）

別々の変数でも、**同じキャッシュ ライン（64 バイト）に入っている**と、別々のコアが書き込むたびに、お互いのキャッシュを無効にしあって、遅くなります。

```cpp
// 悪い：2 つのカウンターが、同じキャッシュ ラインにある
struct Counters {
  std::atomic<int> thread_a;
  std::atomic<int> thread_b;
};

// 良い：別のキャッシュ ラインに置く
struct Counters {
  alignas(64) std::atomic<int> thread_a;
  alignas(64) std::atomic<int> thread_b;
};
```

詳しくは [マルチスレッド化](multithreading.md) を見てください。

## コンテナの選び方（キャッシュの目で）

| コンテナ | メモリの並び | キャッシュの相性 |
| --- | --- | --- |
| **`std::vector<T>`** | 連続 | ◎ 最高 |
| `std::array<T, N>` | 連続（スタック） | ◎ |
| `std::deque<T>` | 小さなブロックが連続 | ○ |
| `std::flat_map` / 整列済み `vector` | 連続 | ◎（検索は二分探索） |
| `std::unordered_map` | バケットとノードが分散 | △ |
| `std::map` / `std::set` | ノードが分散（木） | △〜× |
| `std::list` | ノードが分散 | × 最悪 |
| `vector<unique_ptr<T>>` | ポインタの配列 + 分散したオブジェクト | △ |

「迷ったら `vector`」の理由は、キャッシュです。計算量が O(n) でも、`list` の O(1) 挿入より、`vector` の O(n) 挿入のほうが、速いことがあります。

## ゲームでの使いどころ

| 場面 | 直し方 |
| --- | --- |
| 敵・弾・パーティクルのループが重い | `vector<T>` に、連続して並べる。ポインタの配列をやめる |
| 位置の更新だけ遅い | 位置・速度の SoA、熱いデータと冷たいデータを分ける |
| 構造体が 200 バイトある | メンバを見直し、使わないものを別に分け、型を小さくする |
| タイルマップの走査が遅い | 行方向に連続して読む。1 次元配列で持つ |
| `std::list` を使っている | `vector` + 「消す印」、`erase_if` |
| マルチスレッドで速くならない | false sharing を疑う。`alignas(64)` |

## よくあるミス

??? failure "SoA にすれば、いつでも速いと思う"
    1 体の全部の項目を使う処理では、AoS のほうが速いです。**ループが使うデータ**で、決めます。

??? failure "構造体の大きさを、気にしない"
    いつの間にかメンバが増えて、200 バイトになり、1 体で 3 キャッシュ ラインを使うようになります。`static_assert(sizeof(T) <= 64)` で、見張ります。

??? failure "`std::list` が速いと信じる"
    教科書では、`list` の挿入・削除は O(1) ですが、要素へのアクセスのたびにキャッシュミスが起きます。実際は、`vector` のほうが速いことがほとんどです。

??? failure "ベンチマークが、データが小さすぎてキャッシュに全部乗る"
    小さいデータで測ると、すべてが L1 に乗り、差が出ません。実際のゲームの量で測ります。

## これだけ覚える

!!! abstract "まとめ"
    - [x] メモリ読み込みは遅い（約 100 倍）。<strong>キャッシュ ライン（64 バイト）</strong>ごとに読まれる
    - [x] 連続した `vector` を、前から順に読むのが一番速い。ポインタの連鎖は遅い
    - [x] ループで使うデータだけを近くに並べる（AoS → SoA、熱い / 冷たいを分ける）
    - [x] 構造体を小さく。メンバは大きい型から並べ、`sizeof` を見張る
    - [x] 複数スレッドで別の変数を書くなら、キャッシュ ラインを分ける（`alignas(64)`）
