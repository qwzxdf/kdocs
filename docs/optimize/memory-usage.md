# メモリ使用量

ゲームが使えるメモリには、**上限があります**。PC でもプレイヤーの PC は 8 GB かもしれませんし、ゲーム機やスマホは、さらに厳しい制限があります。メモリを使いすぎると遅くなり（スワップ）、最悪はクラッシュします。さらにメモリが小さいと速いという面もあります。小さいデータは、[キャッシュ](memory-cache.md)に乗りやすく、ロードも速いからです。このページはメモリ使用量を知る・減らす・リーク（解放し忘れ）を見つける方法をまとめます。

!!! tip "ポイント"
    - まず<strong>何がどれだけ使っているか</strong>を測る。<strong>テクスチャとモデルがたいてい大部分</strong>。
    - 大きなものから減らす。テクスチャの圧縮（BC 形式）、解像度の見直し、ミップマップ。
    - 構造体を小さく（型を小さく、メンバを並べ替え）。大量にあるものほど効く。
    - 使っていないものは解放する（シーンを出たら、リソースを手放す）。
    - リークはツールで見つける。RAII（`unique_ptr`）で、そもそも起きにくくする。

## メモリの内訳を知る

一般的なゲームでは、メモリの大部分は、次のものです。

| 項目 | 目安 | 減らし方 |
| --- | --- | --- |
| **テクスチャ** | 一番大きい（全体の 50〜80%） | 圧縮、解像度の見直し、不要なものを解放 |
| メッシュ（頂点・インデックス） | 大きい | 頂点フォーマットの圧縮、LOD、共有 |
| 音声 | 大きい（圧縮なしの WAV） | 圧縮（OGG）、長い BGM は、ストリーミング |
| アニメーション | 中 | キーフレームの削減、圧縮 |
| ゲームのオブジェクト（敵、アイテム） | 小〜中 | 構造体の小型化、プール |
| コード・ライブラリ | 小 | 不要なライブラリの除去 |
| スタック・ヒープの管理情報 | 小 | |

何がメモリを使っているかは、勘ではなく、ツールで測ります。

## 測る

| 道具 | 何が分かるか |
| --- | --- |
| **タスク マネージャー** | プロセスのメモリ使用量（ざっくり）。ワーキング セット（実際に物理メモリにある量）と、コミット サイズ（確保した量） |
| Visual Studio の診断ツール（デバッグ中に表示） | メモリ使用量の推移。スナップショットを取って、前後の差を比較できる |
| Visual Studio の「メモリ使用量」プロファイラー（Alt + F2） | どの型がどれだけ確保されているか |
| 自作のカウンター | 確保の回数と大きさを数える（[メモリ確保](allocation.md)）。リソースの種類ごとに集計する |
| Tracy のメモリ追跡 | 確保・解放の場所と時間をタイムラインで見る |
| GPU のメモリ（VRAM） | PIX、RenderDoc、タスク マネージャーの「専用 GPU メモリ」 |

### 自作の集計

ゲームの中でリソースの種類ごとに使用量を集計して、デバッグ画面に出すと増え続けるものにすぐ気づけます。

```cpp
struct MemoryStats {
  std::size_t textures = 0;
  std::size_t meshes = 0;
  std::size_t audio = 0;
};

// リソースを読み込むときに加算、解放するときに減算
stats.textures += texture.SizeInBytes();

// ImGui などで、画面に出す
ImGui::Text("テクスチャ: %.1f MB", stats.textures / (1024.0 * 1024.0));
```

## テクスチャを減らす

一番効果が大きいところです。

### 圧縮（BC フォーマット）

**GPU が圧縮したまま読める**テクスチャ形式です。品質をほとんど落とさずに、メモリを 4〜8 分の 1 にできます。

| 形式 | 用途 | 圧縮率（RGBA8 に対して） |
| --- | --- | --- |
| BC1（DXT1） | 不透明な色テクスチャ | 1/8 |
| BC3（DXT5） | アルファ（透明）付きの色 | 1/4 |
| BC4 | 1 チャンネル（高さ、マスク） | 1/8 |
| BC5 | 2 チャンネル（法線マップ） | 1/4 |
| BC7 | 高品質な色（アルファ付き）。エンコードは遅い | 1/4 |
| ASTC（スマホ向け） | モバイルの標準。ブロック サイズを選べる | 設定による |

- ビルド時に変換する（`texconv`、Compressonator などのツール）。実行時に変換するとロードが遅い
- PNG / JPG は、ディスク上の圧縮であり、メモリ上では展開された巨大なデータになる。GPU に送る形（BC）に事前に変換しておく

### 大きさを見直す

| 方法 | 説明 |
| --- | --- |
| 画面での大きさに合わせる | 画面で 128 ピクセルのものに、2048 のテクスチャは要らない |
| ミップマップ | 縮小版を持つ（メモリは約 1.33 倍）。ただし、遠くを描くときに小さい版だけ読めばよく、速い |
| ミップを上から数段飛ばして読む | 低品質設定では、一番大きな階層を読み込まない |
| テクスチャ アトラス | 小さな画像を 1 枚にまとめる（隙間に注意） |
| 使っていないテクスチャを解放 | シーンを出たら、リソースを手放す（[リソース管理](../engine/resource.md)） |
| 同じ画像の重複をなくす | 共有する（`shared_ptr` やハンドルで、1 つだけ読み込む） |

## 構造体を小さくする

大量にあるオブジェクト（弾、パーティクル、タイル）は、**1 個のサイズ × 個数**で、メモリが決まります。

```cpp
// 40 バイト
struct Particle {
  Vec3 position;       // 12
  Vec3 velocity;       // 12
  float life;          // 4
  float size;          // 4
  Color color;         // 4 × 4 = 16 (float x4)
};

// 28 バイト：色を 4 バイト（8 ビット ×4）に位置を保ったまま
struct ParticleSmall {
  Vec3 position;       // 12
  Vec3 velocity;       // 12
  uint16_t life;       // 2（フレーム数や、固定小数点）
  uint16_t size;       // 2
  uint32_t color;      // 4（RGBA8）
};
```

| 方法 | 説明 |
| --- | --- |
| 小さい型にする | `int` → `int16_t`、`float` → 固定小数点・`half`、`bool` の配列 → ビット |
| メンバを大きい順に並べる | パディング（隙間）が減る（[メモリとキャッシュ](memory-cache.md#パディング隙間に注意)） |
| ポインタを 32 ビットの ID にする | 64 ビット環境で、8 バイト → 4 バイト（ハンドル） |
| 使わないメンバを消す・別に持つ | 熱いデータと冷たいデータを分ける |
| `bool` を並べない | 8 個のフラグは、1 バイトに（`std::bitset` やビット フィールド） |
| `std::string` を持たない | 1 つが 32 バイト。ID（整数）か、共有の文字列テーブルに |

### コンテナのメモリ

| コンテナ | メモリの無駄 |
| --- | --- |
| `std::vector` | 容量が 2 倍ずつ増えるので、最大で 2 倍近く確保される。`shrink_to_fit()` で縮める |
| `std::unordered_map` | ノード 1 つごとにポインタと管理情報。要素の数倍になることも |
| `std::map` / `std::set` | ノードごとに 3 つのポインタ + 色 |
| `std::list` | ノードごとに 2 つのポインタ（16 バイトの無駄） |
| `std::string` | 短ければ中に持つ（SSO）。長いとヒープ + 管理情報 |
| `std::shared_ptr` | 制御ブロック（参照カウント）が別に確保される（`make_shared` で、1 つにまとまる） |

大量に持つなら、`vector` や連続した配列がメモリ的にも有利です。

## 使っていないものを解放する

| 場面 | 方法 |
| --- | --- |
| **シーンを出たとき** | そのシーンだけが使うリソースを解放（参照カウントで自動に） |
| ステージの切り替え | 前のステージのアセットを全部解放してから、次を読む（ピークを下げる） |
| キャッシュが肥大化する | 上限を決めて、古いものから捨てる（LRU） |
| `vector` の過剰な容量 | `shrink_to_fit()`、またはスワップで縮める |
| 一時データ | フレーム用アリーナなどで、使い回す |

## メモリ リーク（解放し忘れ）を見つける

**リーク**は確保したメモリを解放しないまま、アクセスできなくなる（ポインタを失う）ことです。プレイ時間が長いと少しずつ増えて、メモリ不足になります。

### 防ぐ（一番大事）

| 方法 | 説明 |
| --- | --- |
| `new` / `delete` を書かず、`unique_ptr` と `vector` | 自動で解放される（[RAII](../design/patterns/raii.md)） |
| 所有者を 1 人に決める | 誰が消すかが明確（[所有権とライフタイム設計](../design/foundations/ownership-lifetime.md)） |
| `shared_ptr` の循環を避ける | お互いを `shared_ptr` で持つと、永久に残る。片方を `weak_ptr` に |

### 見つける

| 道具 | 使い方 |
| --- | --- |
| CRT のリーク検出（Debug） | `#define _CRTDBG_MAP_ALLOC` + `<crtdbg.h>` を include し、`_CrtDumpMemoryLeaks();` を終了時に呼ぶ。終了時に解放されていない確保が出力に出る |
| Visual Studio の診断ツール | スナップショットを 2 つ取って、増えているものを比較する |
| AddressSanitizer + LeakSanitizer（Clang / GCC） | 終了時にリークを報告。MSVC の ASan は、リーク検出が限定的 |
| 自作のカウンター | 確保・解放の回数を数えて、終了時に一致するか確認する（Debug） |
| Tracy / Heaptrack | 確保の場所と寿命を可視化する |

```cpp
// Debug ビルド：終了時に解放されていないメモリを出力ウィンドウに表示する
#define _CRTDBG_MAP_ALLOC
#include <crtdbg.h>

int main() {
  _CrtSetDbgFlag(_CRTDBG_ALLOC_MEM_DF | _CRTDBG_LEAK_CHECK_DF);   // 終了時に自動でチェック
  RunGame();
}
```

### リークと「増え続ける」は別

| 症状 | 原因 |
| --- | --- |
| リーク（ポインタを失った） | `delete` し忘れ。ツールで検出できる |
| 増え続ける（ポインタは持っているが、減らさない） | キャッシュが無限に増える、`vector` に追加するだけで消さない、ログを溜める。ツールではリークと報告されない（まだ参照されているため） |

後者はメモリ使用量のグラフ（時間の経過）で見つけます。プレイを続けて、ずっと右上がりなら、疑います。

## ゲームでの使いどころ

| 場面 | 方法 |
| --- | --- |
| メモリが足りない | プロファイラーで内訳を見て、一番大きいもの（たいていテクスチャ）から圧縮 |
| 弾・パーティクルが大量 | 構造体を小さく。プールで確保を一定に |
| 長時間プレイで重くなる | メモリ使用量の推移を見る。増え続けるキャッシュ・ログを疑う |
| モバイル・ゲーム機 | 上限が厳しい。テクスチャの圧縮（ASTC）、音の圧縮、ストリーミング |
| 開発中 | デバッグ画面に種類ごとの使用量を出しておく |

## よくあるミス

??? failure "PNG のファイルサイズ ＝ メモリの大きさだと思う"
    PNG はディスク上の圧縮で、メモリ上では展開された RGBA（1 ピクセル 4 バイト）になります。2048×2048 の画像は、ファイルが 1 MB でも、メモリ上は **16 MB**（ミップマップ込みで約 21 MB）です。BC 圧縮に変換して、メモリを減らします。

??? failure "`shrink_to_fit()` で、必ず縮むと思う"
    保証されていません（実装に任せられます）。確実に縮めるなら、新しい `vector` に、ムーブ（またはコピー）して、入れ替えます。

??? failure "リークを「終了時に OS が回収するから」と放置する"
    短時間のゲームでは問題になりませんが、プレイ中に増え続けるものは、長時間プレイで必ず問題になります。繰り返し作られるものを特に見直します。

??? failure "メモリを減らすために、速さが落ちる設計にする"
    圧縮を実行時に毎回展開する、などです。メモリと速さのトレードオフを測って判断します。

??? failure "開発 PC のメモリ量でしか確認しない"
    プレイヤーの PC は、もっと少ないかもしれません。最低スペックの環境で動作確認します。
