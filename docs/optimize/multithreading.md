# マルチスレッド化

今の PC やゲーム機は、**複数のコア**（独立して計算できる部品）を持っています。1 つのスレッドだけで動かすと、**ほかのコアは遊んでいる**ことになります。重い処理を、**複数のコアに分担**させることができれば、理論上、コアの数だけ速くなります。ただし、**マルチスレッド化は、最適化の中で一番難しく、バグも増えます**。データ競争、デッドロック、「たまにしか起きない」バグがあるからです。そのため、**1 スレッドで、アルゴリズムとメモリの並びを直してから**考えます。ここでは、**速さの観点**から、どう分担すれば効くかをまとめます（バグを避ける設計は [並行処理の設計](../design/practice/concurrency-design.md)、道具は [thread](../stl/concurrency/thread.md)・[mutex](../stl/concurrency/mutex.md) を見てください）。

!!! tip "ポイント"
    - <strong>最後の手段</strong>。まず 1 スレッドで、<strong>アルゴリズム → メモリの並び → 確保</strong>を直す。
    - 効く処理は、<strong>独立した大量の仕事</strong>（全敵の更新、パーティクル、画像処理）。互いに依存する処理は、効かない。
    - スレッドを手で作らず、<strong>ジョブ システム（スレッド プール）</strong>に仕事を投げる。
    - <strong>共有しない</strong>設計にする。データを分割し、スレッドごとに別の場所を触る。
    - 速くなるのは<strong>コア数まで</strong>。しかも<strong>直列に残る部分</strong>で、頭打ちになる（アムダールの法則）。

## 何倍速くなるのか

**アムダールの法則**: 全体のうち、並列化できない部分があると、そこで速さが頭打ちになります。

| 並列にできる割合 | 4 コアでの速さ | 8 コアでの速さ | 無限のコアでの上限 |
| --- | --- | --- | --- |
| 50% | 1.6 倍 | 1.8 倍 | 2 倍 |
| 90% | 3.1 倍 | 4.7 倍 | 10 倍 |
| 99% | 3.9 倍 | 7.5 倍 | 100 倍 |

「8 コアだから 8 倍」にはなりません。**並列にできない部分**（準備、結果のまとめ、ロックの待ち）を減らすことが重要です。

## どう分担するか

### 1. データ並列（同じ処理を、データを分けて）

**同じ処理を、データの別の部分に対して、同時に行います**。一番簡単で、効果も大きいです。

<div class="anim" data-label="データ並列：配列を分けて、同時に処理する">
1 2 3 4 5 6 7 8 # 8 個の敵。1 スレッドなら、順に 8 回
*1 *2 3 4 5 6 7 8 # スレッド A：前半を担当
*1 *2 *3 *4 5 6 7 8 # スレッド A が前半
1 2 3 4 *5 *6 *7 *8 # スレッド B が後半。同時に進む
1 2 3 4 5 6 7 8 # 全員終わったら、結果をまとめる（同期）
</div>

```cpp
#include <algorithm>
#include <execution>

// 標準の並列アルゴリズム：std::execution::par を付けるだけ
std::for_each(std::execution::par, enemies.begin(), enemies.end(),
              [dt](Enemy& e) { e.position += e.velocity * dt; });
```

| 方法 | 説明 |
| --- | --- |
| **`std::execution::par`**（C++17） | 標準アルゴリズムに付けるだけ。MSVC は対応。環境によっては遅い・未対応 |
| **OpenMP**（`#pragma omp parallel for`） | ループに 1 行書くだけ。MSVC は `/openmp` で有効 |
| **Intel TBB**（`tbb::parallel_for`） | 本格的。スレッド プール内蔵。vcpkg: `tbb` |
| **自作のジョブ システム** | ゲーム エンジンで、細かい制御が必要なとき |

**独立していること**が条件です。`e.position` を各敵が自分だけ更新するなら安全ですが、**共有の変数に書き込む**（合計を足していく）と、データ競争になります。

### 2. タスク並列（違う処理を、同時に）

**違う種類の処理を、別のスレッドで**同時に動かします。

| 分け方 | 説明 |
| --- | --- |
| **更新 / 描画の分離** | ゲームの更新と、描画コマンドの作成を、1 フレームずらして並行 |
| **物理 / AI / アニメーション** | 依存のない、別々のシステムを同時に |
| **ロード / ゲーム本体** | ロードを別スレッドで（[ロード時間](loading.md)） |
| **音 / ネットワーク** | 専用のスレッドで、常に動かす |

タスク並列は、**依存関係の設計**が難しく、並列にできる量も、タスクの数までです。データ並列のほうが、スケールします。

### 3. ジョブ システム

**仕事（ジョブ）を小さく分けて、スレッド プールに投げ、空いたスレッドが取って実行する**仕組みです。ゲームでは標準的な設計です。

<div class="anim" data-type="graph" data-label="ジョブを積み、ワーカーが実行し、メインが完了を待つ">
n m1 メインスレッド_ジョブを作る 0 1 hit
n q キュー 1 1 hit
l m1 q hit 積む
---
n m1 メインスレッド_ジョブを作る 0 1
n q キュー 1 1
n w ワーカー_1,2,3… 2 1 hit
l m1 q - 積む
l q w hit 空いたものが取る
---
n m1 メインスレッド_ジョブを作る 0 1
n q キュー 1 1
n w ワーカー_1,2,3… 2 1
n m2 メインスレッド_完了を待つ（同期） 3 1 hit
l m1 q - 積む
l q w - 空いたものが取る
l w m2 hit 全部終わる
</div>

| 設計のポイント | 説明 |
| --- | --- |
| **ジョブの大きさ** | 小さすぎるとキューの管理が重く、大きすぎると、負荷が偏る。**数百マイクロ秒〜数ミリ秒**が目安 |
| **依存関係**（A の後に B） | ジョブに、依存するジョブを指定する（グラフ） |
| **ワーカーの数** | **コア数 − 1**（メイン スレッドの分を残す）が基本。`std::thread::hardware_concurrency()` |
| **フレームごとに同期** | 毎フレーム、ジョブを投げて、終わりを待つ（フレームの区切りで、データが安定する） |

## 速さを妨げるもの

| 原因 | 説明 | 対策 |
| --- | --- | --- |
| **ロックの待ち** | 1 つのロックに、全スレッドが並ぶ | 共有を減らす。ロックの範囲を短く。ロックを使わない設計（データを分ける） |
| **false sharing** | 別々の変数が、同じキャッシュ ラインにあって、お互いを邪魔する | `alignas(64)` で、別のキャッシュ ラインに（[メモリとキャッシュ](memory-cache.md)） |
| **負荷の偏り** | 一部のスレッドだけ仕事が多く、他は待つ | ジョブを細かく分けて、動的に割り当てる |
| **同期のコスト** | スレッドの起動・待ち合わせ自体に、時間がかかる | 小さな仕事は、並列にしない。ジョブをまとめる |
| **メモリ帯域が限界** | 計算ではなく、メモリの読み込みが遅い | コアを増やしても効かない。データを小さく |
| **確保のロック** | `new` は、内部でロックを取ることがある | スレッドごとのアリーナ・プール（[メモリ確保](allocation.md)） |

### 共有しない設計

| 方法 | 説明 |
| --- | --- |
| **データを分割する** | 敵の配列を、スレッドごとの範囲に分ける。お互いの範囲は触らない |
| **結果を別の場所に書く** | 入力は読むだけ、出力は、スレッド専用の配列へ。最後にまとめる |
| **スレッド ローカル**（`thread_local`） | スレッドごとに別の変数（乱数、バッファ、カウンター）。最後に合算 |
| **ダブル バッファ** | 読む用と書く用を分けて、フレームの区切りで入れ替える |

```cpp
// 悪い：全スレッドが、1 つの合計に足す（ロックか atomic が必要で、遅い）
std::atomic<int> total = 0;
parallel_for(items, [&](const Item& i) { total += i.score; });

// 良い：スレッドごとに部分和を作り、最後に合算する（共有なし）
std::vector<int> partial(thread_count, 0);
parallel_for_indexed(items, [&](int thread_id, const Item& i) { partial[thread_id] += i.score; });
int total = std::accumulate(partial.begin(), partial.end(), 0);
```

（`partial[thread_id]` の隣り合う要素が、false sharing にならないよう、`alignas(64)` の構造体にするとさらに良いです。）

## 測って確認する

マルチスレッド化は、**速くなったか、必ず測ります**。

| 見る点 | 方法 |
| --- | --- |
| **フレーム時間が縮んだか** | 前後で、同じ場面を測る |
| **各コアが、ちゃんと使われているか** | Visual Studio の「並列スタック」「CPU 使用率」、Tracy のスレッド表示 |
| <strong>待ち時間（ロック競合）</strong> | プロファイラーで、ロックを待っている時間を見る |
| **スレッドを増やすと、速くなるか** | 1、2、4、8 スレッドで測って、グラフにする |

バグの検出には、**ThreadSanitizer**（Clang / GCC）や、Visual Studio の診断ツールを使います。

## ゲームでの使いどころ

| 場面 | 方法 |
| --- | --- |
| 数千の敵・パーティクルの更新 | データ並列（`par`、OpenMP、TBB、自作ジョブ） |
| 物理・当たり判定 | 物理エンジン（Jolt など）は、内部でジョブ システムを使う |
| アニメーションの計算（スキニング） | キャラクターごとに、ジョブに分ける |
| ロード | 別スレッド（`std::async`、`std::jthread`） |
| 描画コマンドの作成 | 更新のスレッドとは別に、コマンドを並列に作る |
| 画像・音の処理 | 区切って、並列に |

## よくあるミス

??? failure "小さな処理を、並列にして遅くなる"
    スレッドの起動・同期のコストが、仕事の時間を上回ると、1 スレッドより遅くなります。**十分に重い処理**だけを、並列にします。

??? failure "共有変数に、全スレッドが書く"
    ロックや atomic の競合で、ほぼ 1 スレッドぶんの速さに戻ります。データを分けて、最後にまとめます。

??? failure "スレッド数を、コア数以上に増やす"
    コア数を超えるスレッドは、切り替えのコストが増えるだけです。ワーカーは、コア数に合わせます。

??? failure "メイン スレッドが、ワーカーを待ち続ける"
    ジョブの完了待ちの間、メイン スレッドが遊びます。待っている間に、**自分も仕事を取る**（ジョブを手伝う）設計にします。

??? failure "並列にしたら、結果が毎回違う"
    浮動小数点の足し算の順序が変わる、データ競争がある、などです。再現性が必要なら、順序を固定する設計にします。
