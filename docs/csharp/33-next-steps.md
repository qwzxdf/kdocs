# 第 33 章 まとめとこれから

最後の章です。作ったものの全体を振り返り途中で下した<strong>設計の判断</strong>を整理します。そして、このエディタを<strong>さらに育てる</strong>ための道筋とよくある疑問をまとめます。

## 作ったもの

```text
MiniEngine.sln
├─ Engine      C++ DLL   DX12 描画、シーン、ピッキング、カメラ、ゲームの読み込み・ホット リロード
├─ EngineApi   C++ DLL   Engine を C の関数にした入口（ハンドル、エラー コード、例外を境界で止める）
├─ Game        C++ DLL   ゲームのコード（IGameModule を実装）。差し替えられる
├─ Player      C++ EXE   Engine と Game を動かす実行側
├─ EngineBridge C++/CLI  Engine を包む橋（比較用）
└─ Editor      C# EXE    WPF + Prism のエディタ
     ├─ Views / ViewModels / Models / Services
     └─ Modules: SceneTree, Property, Asset, Log, Viewport
```

エディタの機能の一覧です。

| 機能 | 章 | 使った主な技術 |
| --- | --- | --- |
| ソリューションの分割 | 1 | `Directory.Build.props`、プロジェクトの依存 |
| エンジンの骨組み | 2〜4 | DLL、Pimpl、DirectX 12、Win32 のメッセージ ループ |
| C#・WPF・Prism | 5〜10 | 型、プロパティ、XAML、データ バインディング、MVVM、DI、リージョン、モジュール |
| C# ⇄ C++ | 11〜15 | C API、P/Invoke、`SafeHandle`、コールバック、C++/CLI |

| シーン編集 | 20〜23 | ドキュメントとエンジンの分離、ツリー、プロパティ、ピッキング、ギズモ |
| Undo/Redo、保存 | 24〜25 | コマンド パターン、JSON、非同期 |

## 設計の判断を振り返る

この教材では途中で何度か<strong>選択肢を比べて決めました</strong>。その判断と理由を 1 つの表にします。自分のプロジェクトで同じ問題に当たったときこの表の考え方が役に立ちます。

| 判断 | 選んだもの | 理由 | 別の選択肢とその場合 |
| --- | --- | --- | --- |
| エディタの言語 | C# + WPF | 画面作りの生産性が高い | ImGui（C++）：画面が単純で、エンジンと一体化したいとき |
| C# ⇄ C++ の方式 | P/Invoke + C API | 壊れにくい。追加プロジェクトが要らない | C++/CLI：C++ のクラスをそのまま見せたいとき |
| 境界を越える型 | blittable な型と UTF-8 | 変換が要らない。言語・コンパイラーに依存しない | COM：言語非依存のオブジェクトが必要なとき |
| ビューポート | `HwndHost` | DX12 をそのまま使える。速い | `D3DImage`：WPF の部品を上に重ねたいとき |
| エンジンを触るスレッド | <strong>描画スレッド 1 本</strong> | ロックを書かずに済む | エンジンを内部で並列化：大規模な更新が必要なとき |
| データの持ち主 | <strong>エディタのドキュメント</strong>（エンジンは写し） | Undo、保存、Play の復元が簡単 | エンジンが持つ：エディタとゲームのデータが同一のとき |
| ID の採番 | C# が決める | Undo で同じ ID に復元できる | エンジンが採番：永続的な ID が不要なとき |
| 編集の窓口 | `ISceneEditor` | Undo を後から差し込める | 直接変更：Undo が不要な小さなツール |
| Undo の方式 | コマンド パターン | 小さく、操作の名前が分かる | スナップショット：小さなシーン、実装を最小にしたいとき |
| ゲームの境界 | 純粋仮想クラス + 版の照合 | ゲームを C++ のクラスで書ける | C の関数表：コンパイラーを越えたいとき |
| ホット リロード | シャドウ コピー + 状態の引き継ぎ | ロックを避ける。状態を保てる | 別プロセス：ゲームのクラッシュを隔離したいとき |
| Play 中の編集 | 禁止 | 混乱を防ぐ | 許可して Stop で捨てる：試行錯誤を重視するとき |
| エラー | 想定内は捕捉、致命的はダンプ | 原因の調査ができる | 別プロセスのクラッシュ ハンドラー：製品品質のとき |

## この教材の「割り切り」

簡単さのために<strong>本格的なエディタとは違う作り</strong>にした所があります。次のステップへの手がかりです。

| 割り切り | 実際の製品では |
| --- | --- |
| シーンの物は<strong>ワイヤーフレームの箱だけ</strong> | メッシュ、マテリアル、テクスチャ、ライトをアセットとして読み込んで描く |
| 回転は<strong>オイラー角</strong> | クォータニオンで持ち表示だけオイラー角にする（ジンバルロックを避ける） |
| ギズモは<strong>移動だけ</strong> | 回転、拡大のギズモ。ローカル／ワールド座標の切り替え。スナップ（グリッドに吸着） |
| 深度テストなしの線 | 深度バッファーを持ち前後関係を正しく描く。選択物のアウトライン |
| ツリーは<strong>全展開で読む</strong> | 遅延読み込み仮想化 |
| 画面の配置は<strong>固定</strong> | <strong>ドッキング</strong>（AvalonDock など）：パネルを自由に配置・保存 |
| コンポーネントがない | 物にコンポーネント（メッシュ、ライト、スクリプト）を持たせる。<strong>ECS</strong> との相性（[ECS](../design/patterns/ecs.md)） |
| ゲームは<strong>単一の `IGameModule`</strong> | コンポーネントの型をゲーム DLL がエンジンに<strong>登録</strong>する仕組み（リフレクション）。ホット リロードで登録し直す |
| 入力は<strong>エディタのカメラ</strong>だけ | Play 中は、ゲームに入力を渡す。ゲームのカメラに切り替える |
| Play 中の<strong>値の表示がない</strong> | インスペクターで、Play 中の値をエンジンから読み取って表示する |
| 単一のビューポート | 複数のビューポート（上・正面・右・透視）。ビューポートごとのカメラ |
| テクスチャのサムネイルのみ | モデルやマテリアルのプレビューをエンジンでオフスクリーン描画して作る |

## これから伸ばす道筋

優先度が高く効果が大きい順に並べます。

### 1. 見た目を良くする（エンジン側）

1. <strong>深度バッファー</strong>と<strong>メッシュの描画</strong>（ソリッド表示）。
2. <strong>glTF の読み込み</strong>（[tinygltf](../libs/index.md) などのライブラリ）。アセットのドロップで実際のモデルが出る。
3. <strong>マテリアル</strong>と<strong>ライト</strong>。[シェーダー](../graphics/index.md) の原理を使う。
4. <strong>選択のアウトライン</strong>、グリッドの改善。

### 2. 編集を便利にする（エディタ側）

1. <strong>回転・拡大のギズモ</strong>、スナップ。
2. <strong>コピー、貼り付け複製</strong>（`Ctrl+C`/`V`/`D`）。スナップショットの仕組みを使える。
3. <strong>ドッキングするパネル</strong>（`AvalonDock`）と配置の保存。
4. <strong>複数選択の編集</strong>（プロパティ パネルで全員に反映）。
5. <strong>コンポーネント</strong>の追加・削除とプロパティの自動生成（属性やリフレクションから画面を作る）。

### 3. ゲームの開発を支える

1. <strong>コンポーネントの登録</strong>：ゲーム DLL がエンジンに型を登録し、エディタがそれを見て「コンポーネントの追加」メニューを作る。
2. <strong>Play 中の入力</strong>とゲームのカメラ。
3. <strong>プロファイラー</strong>：フレームごとの時間をエンジンが計測し、エディタが表示する。[最適化](../optimize/index.md) の知識を使う。
4. <strong>ビルドの統合</strong>：エラーの行をログから Visual Studio で開く。

### 4. 品質と運用

1. <strong>自動テスト</strong>：ビューモデルのテストを増やす。エンジンの `Scene` や `Picking` にも C++ のテスト。
2. <strong>CI</strong>：ビルド、テスト、配布物の自動生成。
3. <strong>クラッシュ レポートの収集</strong>。
4. <strong>自動保存</strong>（バックアップ）：クラッシュで作業を失わないように。

## よくある疑問

??? question "WPF は古い技術ではないですか？"
    WPF は Windows のデスクトップ アプリのための成熟した技術で、.NET 8 でも更新されています。後継として WinUI 3 がありますが、<strong>3D のビューポートを埋め込む</strong>という用途では、WPF の `HwndHost` が最も実績があります。エディタを新しく作るとき WPF は今でも妥当な選択です。この教材の<strong>設計（MVVM、DI、リージョン、コマンド、ドキュメントの分離）は UI フレームワークが変わっても通用します</strong>。

??? question "Avalonia や WinUI 3 では作れませんか？"
    作れます。MVVM と Prism 風の設計は同じです。ただし、ビューポートの埋め込み方が違います。WinUI 3 には `SwapChainPanel` がありエアスペース問題がありません。Avalonia はクロスプラットフォームですが、DirectX 12 のスワップ チェーンを埋め込む部分は、プラットフォームごとの対応が要ります。

??? question "エンジンを C# で書いてはいけませんか？"
    書けます（Unity が C# をゲームのスクリプトに使っています）。ただし、この教材は<strong>C++ のエンジン</strong>を前提にしています。エンジンの中核を C# にするなら GC の停止（フレーム落ち）、メモリ配置の制御、SIMD の扱いなどを検討します。

??? question "P/Invoke の宣言を手で書くのが大変です"
    ツールで生成できます。C のヘッダーから C# の宣言を自動生成する <strong>ClangSharp</strong> のようなツールや、C# から C++ を呼ぶコードを生成する <strong>CsWin32</strong>（Windows API 用）があります。または、API を <strong>IDL</strong>（インターフェース記述言語）に書いて、両側のコードを生成する方法もあります。

??? question "C++ と C# を行き来するデバッグが難しいです"
    第 15 章の<strong>混在デバッグ</strong>（ネイティブ コードのデバッグを有効にする）が基本です。それでも難しい場合、<strong>境界でログを出す</strong>（引数と戻り値を記録する）とどちら側の問題かを切り分けられます。

??? question "ゲームが落ちると、エディタごと落ちます"
    ゲームをエディタと<strong>同じプロセス</strong>で動かしている以上、避けられません。保険として<strong>自動保存</strong>と<strong>クラッシュ ダンプ</strong>を整えます。完全に隔離したいならゲームを別のプロセスで動かし、IPC で通信する構造にします（複雑さと引き換えです）。

## 作ってみて分かったこと

この教材の構造には<strong>繰り返し出てきた考え方</strong>があります。

| 考え方 | 現れた場所 |
| --- | --- |
| <strong>境界では単純な物だけを渡す</strong> | C API、ゲームのインターフェース |
| <strong>持ち主を 1 つに決める</strong> | データ（ドキュメント）、スレッド（描画スレッド）、メモリ（確保した側が解放） |
| <strong>窓口を 1 つにする</strong> | `IEngineService`、`ISceneEditor`、`IRenderLoop` |
| <strong>外から来る物は疑う</strong> | 引数の検査、ファイルの検証、ゲームの版の照合 |
| <strong>失敗しても今の状態を壊さない</strong> | 読み込みの 2 段階、ホット リロードの「新しい物を先に」 |
| <strong>後から足せる形にしておく</strong> | `ISceneEditor`（Undo）、モジュール、DI |
| <strong>見て分かる形にする</strong> | ログ、Play 中の枠の色、ダーティ フラグ |

これらはエディタに限らず<strong>ツールやミドルウェアを作る</strong>ときに広く使える考え方です。

## 最後に

ここまでたどり着いたあなたは<strong>C++ のエンジン、C# のエディタ、その間の橋</strong>を一から作りました。個々の部品（DirectX、WPF、Prism、P/Invoke）はそれぞれが大きな世界です。しかし、<strong>つなぎ方の勘所</strong>をつかんだことで、それぞれを深める準備ができました。

次は<strong>好きな機能を 1 つ選んで、足してみてください</strong>。ギズモの回転でもメッシュの読み込みでもコピー＆ペーストでも構いません。自分で機能を足す経験がこの教材の内容を本当に自分のものにします。
