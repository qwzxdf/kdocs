# 第 35 章 3D ビューポートを埋め込む方法の比較

この章から第 4 部です。エディタの真ん中にエンジンが描く 3D の絵を出します。ただし、この章ではまだコードをほとんど書きません。WPF の画面の中に DirectX 12 の絵を出す方法を比べて、この教材ではどれを使うのかを決めます。

## 2 つの描画の世界を 1 つの窓に入れる

WPF の画面は、WPF 自身が描いています。ボタンも文字も、半透明のパネルも、WPF が描いた絵です。一方、エンジンは DirectX 12 で描きます。この 2 つを 1 つの画面に同居させなければいけません。

```text
┌──────── Editor のウィンドウ ────────┐
│  WPF が描く世界                    │
│  ┌────────────┐                  │
│  │ DirectX 12 │ ← エンジンが描く世界 │
│  │ の絵        │                  │
│  └────────────┘                  │
└──────────────────────────────┘
```

同居のさせ方は、「絵をどうやって渡すか」で、3 つの考え方に分かれます。

1. 場所を分ける。画面の一部を別のウィンドウ（HWND）として切り出して、そこにはエンジンが直接描く。
2. 絵を渡す。エンジンが描いた絵を WPF のテクスチャとして渡して、WPF が他の部品と一緒に合成する。
3. 絵を運ぶ。エンジンの絵を CPU のメモリ経由で、WPF のビットマップにコピーする。

この教材のエンジンは DirectX 12 です。DirectX 12 は、WPF との組み合わせで追加の制約が出るので、DX12 の場合を中心に見ていきます。

## 方式 A：HwndHost（子ウィンドウ）

`HwndHost` は、Win32 の子ウィンドウを WPF の画面の中に場所を確保して置くための部品です。

```text
Editor.exe の最上位ウィンドウ（HWND）
 └─ WPF の描画面
     └─ [HwndHost の領域]
          └─ 子ウィンドウ（HWND）  ← Engine がここへ、スワップ チェーンで直接描く
```

エンジンは、この子ウィンドウの `HWND` に `CreateSwapChainForHwnd` でスワップ チェーンを作ります。エンジンの絵は WPF を通らず、Windows の合成（DWM）が直接ウィンドウに表示します。

利点は、仕組みが単純なことです。Player と同じ作り（HWND にスワップ チェーン）なので、第 3 章の `Engine` がそのまま使えます。余計なコピーや変換がなく、速くて遅延も小さいです。WPF との共有リソースが要らないので、DX12 のキューとフェンスの仕組みも、そのまま使えます。子ウィンドウがマウスやキーボードのメッセージを直接受け取れるのも便利です。多くのツールがこの方式を使っているので、困ったときの情報も多いです。

### 欠点：エアスペース問題

困るのは、WPF の部品を `HwndHost` の上に重ねられないことです。子ウィンドウは WPF の描画面の外にある別のウィンドウなので、WPF のコンテンツは、常に子ウィンドウの下に隠れます。

```text
  ┌─────────────────────────┐
  │ ビューポート               │
  │   ┌─────────┐ ← WPF の   │
  │   │ ツール    │   オーバーレイを│
  │   │ バー      │   置いても、  │
  │   └─────────┘   隠れる    │
  └─────────────────────────┘
```

「エアスペース」という名前は、1 つのピクセルを WPF と Win32 のどちらか一方しか所有できないことから来ています。具体的には、次のようなことができません。

- ビューポートの上にボタンや文字を重ねる。重ねたいものは、ビューポートの外（上のツール バーや下のステータス）に置きます。
- 半透明のパネルや角丸にする。
- ビューポートの領域で、WPF のアニメーションやトランジションを効かせる。

一方で、ポップアップ、メニュー、ツール チップは独立したウィンドウなので、ビューポートの上に問題なく出ます。ほかには、DPI（画面の拡大率）の扱い（第 36 章）や、キーボード入力の橋渡し（`IKeyboardInputSink`）にも気をつける必要があります。

## 方式 B：D3DImage

`D3DImage` は、Direct3D 9 のサーフェスを WPF の画像として表示できる部品です。他の WPF の部品と同じ描画面に合成されるので、エアスペース問題がありません。ビューポートの上に何でも自由に重ねられます。

ところが DX12 では、`D3DImage` が D3D9 しか受け取れないので、橋渡しの連鎖が必要になります。

```text
DX12 でレンダー ターゲットに描く（共有可能なリソース）
   ↓ 共有ハンドル
D3D11On12 または D3D11（共有テクスチャを開く）
   ↓ 共有ハンドル（レガシー）
D3D9Ex（サーフェスとして開く）
   ↓
D3DImage.SetBackBuffer(...)
```

実装の概略は、こうです。DX12 側でレンダー ターゲットを `D3D12_HEAP_FLAG_SHARED` で作って共有ハンドルを得ます。D3D11 側で `OpenSharedResource1` を使って同じ実体を開き、D3D9Ex が開けるレガシー共有ハンドルが必要になる場合は、`D3D11On12` でラップしたテクスチャにコピーします。D3D9Ex 側で共有ハンドルからサーフェスを作り、WPF 側で `D3DImage.Lock()`、`SetBackBuffer(...)`、`AddDirtyRect(...)`、`Unlock()` の順に呼びます。

この方式の欠点は、橋が長いことです。D3D12 から 11、11 から 9 の共有では、形式の制約（`B8G8R8A8_UNORM` など）と同期（フェンス）が複雑になります。WPF の合成のタイミングは 60 Hz 固定なので、入力から表示までの遅延も増えます。D3D9 は保守されているだけの古い技術なので、将来のサポートも不安です。ディスプレイの切り替えやスリープで D3D9 のデバイスが失われると、作り直しも必要です。

この教材では、これを実装しません。仕組みを知っておくために、概要だけを紹介しました。

## 方式 C：WriteableBitmap

エンジンが描いた絵を GPU から CPU のメモリにコピー（リードバック）して、WPF の `WriteableBitmap` のピクセルに書き込みます。

```text
DX12 でオフスクリーンに描く
   ↓ CopyResource（GPU → CPU から読めるバッファー）
フェンスで GPU の完了を待つ
   ↓ Map
CPU のメモリ
   ↓ memcpy
WriteableBitmap.WritePixels(...)
   ↓
WPF が表示
```

利点は実装がいちばん簡単なことです。共有リソースも HWND も要らず、コピーするだけです。エアスペース問題もありません。

ただし遅いです。1280×720（約 3.7MB）を毎フレームコピーすると、60 fps で約 220MB/s、4K なら約 1.9GB/s になります。GPU の完了を待つのでパイプラインが止まり、遅延も大きくなります。メインのビューポートには向きませんが、アセットのサムネイルのように、小さくて更新の少ない絵を作るには便利です。

## 方式 D：別ウィンドウを重ねる

エンジンを独立した最上位ウィンドウに描かせて、エディタの特定の位置に位置と大きさを合わせて重ねる方法もあります。エンジンの描画が WPF に影響されませんが、エディタを動かすたびに追従させる処理、Z オーダー、フォーカス、最小化、タスク バーの扱いをすべて自前で書くことになります。エアスペース問題も残ります。`HwndHost` はこれを正式な方法でやってくれる部品なので、特別な理由がなければ方式 A を選びます。

## その他

- DirectComposition を直接使って、WPF の描画面と DX12 のスワップ チェーンを同じ合成ツリーに入れる方法があります。エアスペースを避けられますが、実装が高度で、WPF 側の対応も限られるので、扱いません。
- WinUI 3 には `SwapChainPanel` という部品があり、DX12 のスワップ チェーンをそのまま XAML に埋め込めます。エアスペースもありません。ただし WPF ではありません。
- エンジンを別プロセスにして共有メモリで絵を受け取る方法や、映像として配信する方法もありますが、複雑だったり、遅延が大きかったりします。

## 比べる

| | A: HwndHost | B: D3DImage | C: WriteableBitmap | D: 別ウィンドウ |
| --- | --- | --- | --- | --- |
| 実装の難しさ | 低から中 | 高（D3D12→11→9） | 低 | 中 |
| 描画の速さ | 速い | 共有の同期がある | 遅い（コピー） | 速い |
| 入力から表示までの遅延 | 小さい | 中（60 Hz に縛られる） | 大きい | 小さい |
| エアスペース問題 | あり | なし | なし | あり |
| WPF の部品を重ねる | できない | できる | できる | できない |
| DX12 との相性 | そのまま使える | 橋が必要 | リードバックで可 | 良い |
| 高解像度・高 fps | 向く | まあまあ | 向かない | 向く |
| よく使われる場面 | 多くの商用ツール | 一部の WPF + D3D アプリ | サムネイル、簡易プレビュー | ツールのサブウィンドウ |

## この教材の選択

メインの 3D ビューポートは、方式 A の `HwndHost` にします。理由は 3 つです。

1. DX12 の作りを変えずに使えます。第 3〜4 章で作った `Engine` と Player の関係がそのまま `HwndHost` に引き継がれます。
2. 性能と遅延が良いです。3D エディタの操作感（カメラの回転、物のドラッグ）に直結します。
3. 実績が多く、問題が起きたときの情報が見つけやすいです。

アセットのサムネイルのような小さな静止画は、方式 C の考え方を応用します（第 45 章）。

エアスペース問題は、UI の置き方で避けられます。エディタという用途では、大きな制約にはなりません。避けるための指針は、次のとおりです。

- ビューポートは、四角い領域だけにします。角丸、変形、半透明のパネルを重ねません。
- ツール バーは、ビューポートの上や横の、外側の行に置きます。
- FPS やギズモのような情報は、エンジン側で描きます（第 42 章）。
- `ContextMenu`、`ToolTip`、`Popup` は、独立したウィンドウなので、使って構いません。
- アセットのドラッグ アンド ドロップは、WPF の `Drop` イベントではなく、子ウィンドウ側で受けます（第 45 章）。
