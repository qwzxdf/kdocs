## 作ったもの

```text
MiniEngine.sln
├─ Engine      C++ DLL   DX12 描画、シーン、ピッキング、カメラ、ゲームの読み込み・ホット リロード
├─ EngineApi   C++ DLL   Engine を C の関数にした入口（ハンドル、エラー コード、例外を境界で止める）
├─ Game        C++ DLL   ゲームのコード（IGameModule を実装）。差し替えられる
├─ Player      C++ EXE   Engine と Game を動かす実行側
├─ EngineBridge C++/CLI  Engine を包む橋（比較用）
└─ Editor      C# EXE    WPF + Prism のエディタ
     ├─ Views / ViewModels / Models / Services
     └─ Modules: SceneTree, Property, Asset, Log, Viewport
```

## 設計の判断を振り返る

この教材では、途中で何度か選択肢を比べて決めました。その判断と理由を、1 つの表にします。自分のプロジェクトで同じ問題に当たったとき、この表の考え方が役に立ちます。

| 判断 | 選んだもの | 理由 | 別の選択肢とその場合 |
| --- | --- | --- | --- |
| エディタの言語 | C# + WPF | 画面作りの生産性が高い | ImGui（C++）：画面が単純で、エンジンと一体化したいとき |
| C# ⇄ C++ の方式 | P/Invoke + C API | 壊れにくい。追加プロジェクトが要らない | C++/CLI：C++ のクラスをそのまま見せたいとき |
| 境界を越える型 | blittable な型と UTF-8 | 変換が要らない。言語・コンパイラーに依存しない | COM：言語非依存のオブジェクトが必要なとき |
| ビューポート | `HwndHost` | DX12 をそのまま使える。速い | `D3DImage`：WPF の部品を上に重ねたいとき |
| エンジンを触るスレッド | 描画スレッド 1 本 | ロックを書かずに済む | エンジンを内部で並列化：大規模な更新が必要なとき |
| データの持ち主 | エディタのドキュメント（エンジンは写し） | Undo、保存、Play の復元が簡単 | エンジンが持つ：エディタとゲームのデータが同一のとき |
| ID の採番 | C# が決める | Undo で同じ ID に復元できる | エンジンが採番：永続的な ID が不要なとき |
| 編集の窓口 | `ISceneEditor` | Undo を後から差し込める | 直接変更：Undo が不要な小さなツール |
| Undo の方式 | コマンド パターン | 小さく、操作の名前が分かる | スナップショット：小さなシーン、実装を最小にしたいとき |
| ゲームの境界 | 純粋仮想クラス + 版の照合 | ゲームを C++ のクラスで書ける | C の関数表：コンパイラーを越えたいとき |
| ホット リロード | シャドウ コピー + 状態の引き継ぎ | ロックを避ける。状態を保てる | 別プロセス：ゲームのクラッシュを隔離したいとき |
| Play 中の編集 | 禁止 | 混乱を防ぐ | 許可して Stop で捨てる：試行錯誤を重視するとき |
| エラー | 想定内は捕捉、致命的はダンプ | 原因の調査ができる | 別プロセスのクラッシュ ハンドラー：製品品質のとき |

## この教材の「割り切り」

簡単さのために、本格的なエディタとは違う作りにした所があります。次のステップへの手がかりです。

| 割り切り | 実際の製品では |
| --- | --- |
| シーンの物はワイヤーフレームの箱だけ | メッシュ、マテリアル、テクスチャ、ライトをアセットとして読み込んで描く |
| 回転はオイラー角 | クォータニオンで持ち、表示だけオイラー角にする（ジンバルロックを避ける） |
| ギズモは移動だけ | 回転、拡大のギズモ。ローカル／ワールド座標の切り替え。スナップ（グリッドに吸着） |
| 深度テストなしの線 | 深度バッファーを持ち、前後関係を正しく描く。選択物のアウトライン |
| ツリーは全展開で読む | 遅延読み込みと仮想化 |
| 画面の配置は固定 | ドッキング（AvalonDock など）：パネルを自由に配置・保存 |
| コンポーネントがない | 物にコンポーネント（メッシュ、ライト、スクリプト）を持たせる。ECS との相性（[ECS](../design/patterns/ecs.md)） |
| ゲームは単一の `IGameModule` | コンポーネントの型をゲーム DLL がエンジンに登録する仕組み（リフレクション）。ホット リロードで登録し直す |
| 入力はエディタのカメラだけ | Play 中は、ゲームに入力を渡す。ゲームのカメラに切り替える |
| Play 中の値の表示がない | インスペクターで、Play 中の値をエンジンから読み取って表示する |
| 単一のビューポート | 複数のビューポート（上・正面・右・透視）。ビューポートごとのカメラ |
| テクスチャのサムネイルのみ | モデルやマテリアルのプレビューを、エンジンでオフスクリーン描画して作る |

## これから伸ばす道筋

優先度が高く、効果が大きい順に並べます。

### 1. 見た目を良くする（エンジン側）

1. 深度バッファーとメッシュの描画（ソリッド表示）。
2. glTF の読み込み（[tinygltf](../libs/index.md) などのライブラリ）。アセットのドロップで、実際のモデルが出る。
3. マテリアルとライト。[シェーダー](../graphics/index.md)の原理を使う。
4. 選択のアウトライン、グリッドの改善。

### 2. 編集を便利にする（エディタ側）

1. 回転・拡大のギズモ、スナップ。
2. コピー、貼り付け、複製（`Ctrl+C`/`V`/`D`）。スナップショットの仕組みを使える。
3. ドッキングするパネル（`AvalonDock`）と、配置の保存。
4. 複数選択の編集（プロパティ パネルで全員に反映）。
5. コンポーネントの追加・削除と、プロパティの自動生成（属性やリフレクションから画面を作る）。

### 3. ゲームの開発を支える

1. コンポーネントの登録：ゲーム DLL がエンジンに型を登録し、エディタがそれを見て「コンポーネントの追加」メニューを作る。
2. Play 中の入力と、ゲームのカメラ。
3. プロファイラー：フレームごとの時間をエンジンが計測し、エディタが表示する。[最適化](../optimize/index.md)の知識を使う。
4. ビルドの統合：エラーの行をログから Visual Studio で開く。

### 4. 品質と運用

1. 自動テスト：ビューモデルのテストを増やす。エンジンの `Scene` や `Picking` にも C++ のテストを書く。
2. CI：ビルド、テスト、配布物の自動生成。
3. クラッシュ レポートの収集。
4. 自動保存（バックアップ）：クラッシュで作業を失わないように。

## よくある疑問

??? question "WPF は古い技術ではないですか？"
    WPF は Windows のデスクトップ アプリのための成熟した技術で、.NET 8 でも更新されています。後継として WinUI 3 がありますが、3D のビューポートを埋め込む用途では、WPF の `HwndHost` が最も実績があります。エディタを新しく作るとき、WPF は今でも妥当な選択です。この教材の設計（MVVM、DI、リージョン、コマンド、ドキュメントの分離）は、UI フレームワークが変わっても通用します。

??? question "Avalonia や WinUI 3 では作れませんか？"
    作れます。MVVM と Prism 風の設計は同じです。ただし、ビューポートの埋め込み方が違います。WinUI 3 には `SwapChainPanel` があり、エアスペース問題がありません。Avalonia はクロスプラットフォームですが、DirectX 12 のスワップ チェーンを埋め込む部分は、プラットフォームごとの対応が要ります。

??? question "エンジンを C# で書いてはいけませんか？"
    書けます（Unity が C# をゲームのスクリプトに使っています）。ただし、この教材は C++ のエンジンを前提にしています。エンジンの中核を C# にするなら、GC の停止（フレーム落ち）、メモリ配置の制御、SIMD の扱いなどを検討します。

??? question "P/Invoke の宣言を手で書くのが大変です"
    ツールで生成できます。C のヘッダーから C# の宣言を自動生成する ClangSharp のようなツールや、Windows API 用の CsWin32 があります。API を IDL（インターフェース記述言語）に書いて、両側のコードを生成する方法もあります。

??? question "C++ と C# を行き来するデバッグが難しいです"
    第 29 章の混在デバッグ（ネイティブ コードのデバッグを有効にする）が基本です。それでも難しい場合は、境界でログを出す（引数と戻り値を記録する）と、どちら側の問題かを切り分けられます。

??? question "ゲームが落ちると、エディタごと落ちます"
    ゲームをエディタと同じプロセスで動かしている以上、避けられません。保険として、自動保存とクラッシュ ダンプを整えます。完全に隔離したいなら、ゲームを別のプロセスで動かして、IPC で通信する構造にします（複雑さと引き換えです）。

## 作ってみて分かったこと

この教材の構造には、繰り返し出てきた考え方があります。

| 考え方 | 現れた場所 |
| --- | --- |
| 境界では単純な物だけを渡す | C API、ゲームのインターフェース |
| 持ち主を 1 つに決める | データ（ドキュメント）、スレッド（描画スレッド）、メモリ（確保した側が解放） |
| 窓口を 1 つにする | `IEngineService`、`ISceneEditor`、`IRenderLoop` |
| 外から来る物は疑う | 引数の検査、ファイルの検証、ゲームの版の照合 |
| 失敗しても今の状態を壊さない | 読み込みの 2 段階、ホット リロードの「新しい物を先に」 |
| 後から足せる形にしておく | `ISceneEditor`（Undo）、モジュール、DI |
| 見て分かる形にする | ログ、Play 中の枠の色、ダーティ フラグ |

これらは、エディタに限らず、ツールやミドルウェアを作るときに広く使える考え方です。

## 最後に

ここまでたどり着いたあなたは、C++ のエンジン、C# のエディタ、その間の橋を、一から作りました。個々の部品（DirectX、WPF、Prism、P/Invoke）は、それぞれが大きな世界です。けれども、つなぎ方の勘所をつかんだことで、それぞれを深める準備ができました。

次は、好きな機能を 1 つ選んで、足してみてください。ギズモの回転でも、メッシュの読み込みでも、コピー＆ペーストでも構いません。自分で機能を足す経験が、この教材の内容を、本当に自分のものにします。
