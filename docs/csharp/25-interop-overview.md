# 第 25 章 C# から C++ を呼ぶ：連携方式の比較

この章から第 3 部です。ここでは<strong>コードを書かず</strong>、C# と C++ をつなぐ方法を整理します。第 26 章以降で作る連携はこの章の理解の上に立っています。「なぜ C のインターフェースにするのか」「なぜ文字列は UTF-8 なのか」といった、後の章の決めごとの理由が全部ここにあります。

## この章の考え方

C# と C++ は <strong>まったく別の実行環境</strong>で動きます。

| | C#（マネージド） | C++（ネイティブ） |
| --- | --- | --- |
| 実行 | .NET の CLR が、中間言語（IL）を機械語に変換（JIT）して動かす | コンパイラーが作った機械語を CPU が直接動かす |
| メモリ | GC が管理。オブジェクトは GC が<strong>動かす</strong>ことがある | 自分で管理。アドレスは変わらない |
| 文字列 | UTF-16、不変、GC の管理下 | `char*`（UTF-8 / ANSI）、`wchar_t*`（UTF-16）、`std::string` などバラバラ |
| 例外 | CLR の例外 | C++ の例外（SEH）。<strong>互いに理解できない</strong> |
| 型 | .NET の型システム | C++ の型（クラス、テンプレート、仮想関数の配置はコンパイラー依存） |

この 2 つの世界の間に<strong>橋</strong>をかけるのが「連携（相互運用、interop）」です。橋のかけ方には複数の流儀があります。この章ではそれぞれの仕組みと長所・短所を整理します。

## 橋のかけ方の候補

### ① P/Invoke（Platform Invoke）

C# から<strong>DLL の C 関数</strong>を直接呼ぶ仕組みです。

```csharp
[LibraryImport("EngineApi.dll")]
private static partial int me_get_api_version();
```

| 項目 | 内容 |
| --- | --- |
| 仕組み | C# の宣言に DLL 名と関数名を書く。呼び出しの瞬間に CLR が引数を変換（マーシャリング）して、DLL の関数を呼ぶ |
| 長所 | C# だけで完結する（C++ 側は、C の関数を `extern "C"` で出すだけ）。特別なプロジェクトが要らない。ビルドが速い。.NET 標準の仕組み |
| 短所 | 呼べるのは<strong>C の関数だけ</strong>（クラスやテンプレートは不可）。宣言を C# 側にも手で書く（ずれると、実行時に壊れる）。関数ごとに宣言が要る |
| 向いている場面 | 関数の数が数十〜数百で、API が安定している |

### ② C++/CLI

C++ に <strong>CLR 向けの拡張</strong>を足した言語で、<strong>マネージドとネイティブの両方を 1 つのファイルに書ける</strong>橋渡し専用の言語です。

```cpp
public ref class EngineBridge {
 public:
  void Tick(float dt) { engine_->Tick(dt); }
 private:
  mini::Engine* engine_;
};
```

| 項目 | 内容 |
| --- | --- |
| 仕組み | `ref class`（マネージド クラス）の中から、ネイティブの C++ のクラスをそのまま呼べる。C# からは普通の .NET クラスとして見える |
| 長所 | C++ のクラスをそのまま包める（C の API に落とさなくてよい）。型が C# から見て自然（.NET のクラス）。型のずれをコンパイラーが検出する |
| 短所 | C++/CLI の文法を学ぶ必要がある。<strong>Windows 専用</strong>。ビルドが遅くプロジェクトの設定が癖だらけ（`/clr`、`/MD` 必須、一部の C++ 機能と非互換）。.NET Core 対応は `/clr:netcore` で、使える環境に制限がある |
| 向いている場面 | 橋渡しの対象が、クラスの多い C++ の API で、C の API に落とすのが大変なとき |

### ③ COM

Windows の古くからの<strong>言語非依存のオブジェクト</strong>の仕組みです。DirectX も COM です。

| 項目 | 内容 |
| --- | --- |
| 仕組み | インターフェース（仮想関数テーブルの形）を決まった方式で公開する。C# からは COM 相互運用で呼べる |
| 長所 | 言語に依存しない。バージョン管理の仕組みがある |
| 短所 | 実装が大変（`IUnknown`、参照カウント、GUID、登録）。C# 側のマーシャリングも複雑 |
| 向いている場面 | 既存の COM コンポーネントを使うとき |

### ④ プロセス間通信（IPC）

エンジンを<strong>別のプロセス</strong>にして、パイプやソケットでやり取りする方式です。

| 項目 | 内容 |
| --- | --- |
| 長所 | エンジンが落ちても、エディタは落ちない。言語もビット数も自由 |
| 短所 | データのコピーが必要で遅い。<strong>3D ビューポートの表示が難しい</strong>（別プロセスのウィンドウを埋め込む）。同期が複雑 |
| 向いている場面 | エディタとゲームを分離して、デバッグしたいとき |

### ⑤ C# の側にネイティブを載せる（ホスティング）

逆向きに C++ の EXE が、.NET を起動して C# を呼ぶ方式です（`nethost`）。エディタを C# にする教材の構成とは逆なので、ここでは扱いません。

## 4 つを比べる

| 観点 | P/Invoke + C API | C++/CLI | COM | IPC |
| --- | --- | --- | --- | --- |
| C++ のクラスを渡せるか | ×（ハンドルで間接的に） | ○（そのまま包む） | ○（インターフェース） | ×（メッセージ） |
| 追加のプロジェクト | 不要（C の API を出すだけ） | 必要（C++/CLI プロジェクト） | 必要（COM の実装） | 必要（通信の層） |
| 呼び出しの速さ | 速い（数十ナノ秒） | 速い（同じ程度） | やや遅い | 遅い（マイクロ秒〜） |
| C++ の例外 | 境界で止める必要がある | `try/catch` で変換できる | `HRESULT` に変換 | メッセージで返す |
| ビルドの手間 | 小さい | 大きい | 大きい | 中 |
| 移植性 | 他の OS にも広げられる | Windows 専用 | Windows 専用 | 広い |
| 型の安全 | C# 側の宣言と手で合わせる | コンパイラーが検査する | IDL / 型ライブラリ | プロトコル次第 |
| 習得の負担 | 小さい | 中〜大 | 大 | 中 |

## この教材の方針

| 項目 | 方針 |
| --- | --- |
| <strong>主な方式</strong> | <strong>P/Invoke + C API</strong>（第 26、27 章） |
| 比較のための実装 | C++/CLI 版も作る（第 28 章）。同じ `IEngineService` を実装し差し替えられるようにする |
| COM と IPC | 概念の説明にとどめる |

P/Invoke を主にする理由は次のとおりです。

1. <strong>C の API は最も壊れにくい境界</strong>です。クラスのレイアウト、仮想関数テーブル、`std::` の実装、例外といった「コンパイラー依存」の問題が、一切入り込みません。
2. 追加のプロジェクトが要らないので、<strong>ビルドが速く設定が単純</strong>です。
3. エンジンの API を C の関数として整理すること自体が、<strong>設計の良い練習</strong>になります（何を公開し、何を隠すか）。
4. 将来、別の言語（Python のスクリプトなど）や別の OS から使うときにも、同じ C API が使えます。

一方、C++/CLI は C++ のクラス構造をそのまま見せたいときに有効です。第 28 章で実際に作って手間と書き味を比べます。

## 境界を越えるときの決まりごと

どの方式でも<strong>境界を越えるもの</strong>は、慎重に選びます。ここで決めることは後の章の設計の前提になります。

### 型

境界を<strong>そのままのバイト列で</strong>越えられる型を <strong>blittable（ブリッタブル）型</strong>と呼びます。C# と C++ でメモリ上の並びが同じなので、変換が要りません。

| C++ | C# | blittable | 備考 |
| --- | --- | --- | --- |
| `std::int8_t` / `uint8_t` | `sbyte` / `byte` | ○ | |
| `std::int16_t` / `uint16_t` | `short` / `ushort` | ○ | |
| `std::int32_t` / `uint32_t`（`int`） | `int` / `uint` | ○ | |
| `std::int64_t` / `uint64_t` | `long` / `ulong` | ○ | C++ の Windows の `long` は 32 ビットなので、使わない |
| `float` / `double` | `float` / `double` | ○ | |
| `void*`、ポインター | `IntPtr` / `nint`、`T*`（unsafe） | ○ | |
| `bool` | `bool` | <strong>×</strong> | C++ は 1 バイト、C# の既定のマーシャリングは 4 バイト（Win32 `BOOL`）。<strong>使わず `uint8_t` / `int32_t` で渡す</strong> |
| `wchar_t` | `char` | ○ | Windows では 16 ビット（UTF-16） |
| `char*` | `string`（変換あり） | <strong>×</strong> | 変換が必要。UTF-8 の約束にする |
| 構造体（`struct`） | `struct`（`StructLayout`） | 中身が blittable なら ○ | 並びとパディングを合わせる（第 27 章） |
| `enum` | `enum`（基底型を指定） | ○ | `enum : int32_t` に統一する |
| クラス、`std::string`、`std::vector` | — | <strong>×</strong> | 渡せない |

!!! warning "bool は渡さない"
    `bool` の大きさは言語ごと方式ごとに違います。この教材では境界を越える真偽値を <strong>`std::uint8_t`（0 か 1）か `std::int32_t`</strong> にします。

### 文字列

| 方式 | 内容 | この教材での扱い |
| --- | --- | --- |
| UTF-16（`wchar_t*`） | Windows API と同じ。C# の `string` と同じ形式 | 使わない |
| ANSI（`char*`、システムのコード ページ） | 環境で文字化けする | 使わない（[文字コード](../encoding/index.md)） |
| <strong>UTF-8（`const char*`）</strong> | 世界標準。C++ 側でも扱いやすい | <strong>採用</strong>。境界では `const char*`、C# 側で `StringMarshalling.Utf8` を指定する |

### メモリの所有者

「誰がメモリを確保し誰が解放するか」を<strong>常に確実に決めておく</strong>必要があります。

| 受け渡し | 規則 |
| --- | --- |
| C# → C++ の入力（文字列、構造体） | 呼び出しの間だけ有効。C++ は<strong>保持しない</strong>（必要ならコピー） |
| C++ → C# の出力（文字列） | 呼び出し側（C#）が用意したバッファーに、C++ が書き込む。または、C++ が持つ文字列を<strong>次の呼び出しまで</strong>有効なポインターで返す |
| オブジェクト | C++ が作って、<strong>不透明なハンドル</strong>（ポインター）で渡す。解放も C++ の `destroy` 関数で行う |
| 配列 | 呼び出し側が確保したバッファーに C++ が書く。必要な数は先に別の関数で聞く |

C# の GC が管理するメモリのアドレスを C++ に渡して<strong>保持させない</strong>ことが、特に大事です。GC はメモリを移動することがあるからです（<strong>ピン留め</strong>していれば、移動しません）。

### 例外

C++ の例外は DLL の境界を越えると、<strong>未定義動作</strong>です。C# の例外も C++ には通じません。

| 規則 | 理由 |
| --- | --- |
| C++ の関数は<strong>境界の中で、すべての例外を捕まえる</strong> | 越えると、クラッシュする |
| 失敗は<strong>戻り値（エラー コード）</strong>で返す | 単純で、どの言語でも扱える |
| 詳細なメッセージは `GetLastError` 的な関数で取る | メッセージは、エラー コードより長いので別の窓口で |
| C# 側でエラー コードを<strong>例外に変換</strong>する | C# の流儀で、使えるようにする |
| コールバック（C++ → C#）の中でも<strong>例外を投げない</strong> | C++ の呼び出しスタックの中に、C# の例外が通ってしまう |

### 呼び出し規約

関数を呼ぶときの引数の置き場所や後片付けの約束です。<strong>x64 では呼び出し規約は 1 つだけ</strong>なので、`__cdecl` / `__stdcall` の違いは実質的に意味がありません。ただし、<strong>宣言には書く</strong>のが習慣です。

| C++ | C# |
| --- | --- |
| `extern "C" __declspec(dllexport) int __cdecl me_xxx(…)` | `[UnmanagedCallConv(CallConvs = new[] { typeof(CallConvCdecl) })]` |

### 関数名

C++ の関数名は型の情報を含む名前に<strong>変換</strong>されます（名前修飾、マングリング）。`extern "C"` を付けると変換されず `me_engine_create` という名前のまま DLL から公開されます。C# の `[LibraryImport]` が探す名前はこの素の名前です。

## 連携の構造

この教材のエディタとエンジンのつながりを図にします。

```text
┌─────────────────── Editor.exe （C#） ───────────────────┐
│  ViewModel ──▶ IEngineService（インターフェース）            │
│                    ├─ PInvokeEngineService  ← 第 27 章 │
│                    └─ ClrEngineService      ← 第 28 章 │
└──────────────┬────────────────────────┬────────────────┘
               │ P/Invoke               │ 参照
               ▼                        ▼
      EngineApi.dll（C ABI）     EngineBridge.dll（C++/CLI）
               │                        │
               └───────────┬────────────┘
                           ▼
                      Engine.dll（C++）
```

`IEngineService` を境界にするとビューモデルは P/Invoke 版か C++/CLI 版かを知りません。差し替えて比較できます。

## 比べるときの観点

第 28 章で 2 つを作ったあと次の観点で比べます。

| 観点 | 見る点 |
| --- | --- |
| 書く量 | C++ 側、C# 側それぞれ何行増えるか |
| ずれの検出 | 宣言を間違えたときいつ（ビルド時／実行時）分かるか |
| 例外 | どこでどう変換するか |
| ビルド時間 | 変更のたびにどれだけかかるか |
| デバッグ | ブレークポイントが、C# と C++ を行き来できるか |
| 将来性 | 他の OS、他の言語へ広げられるか |

## この章のまとめ

- 連携の方式は P/Invoke、C++/CLI、COM、IPC。この教材は P/Invoke + C API を主に C++/CLI を比較のために作る。
- 境界を越えるのは<strong>blittable な型</strong>（整数、浮動小数、ポインター）と UTF-8 の `const char*`。
- メモリの所有者、例外、`bool` の扱いを<strong>境界ごとに決めておく</strong>。
