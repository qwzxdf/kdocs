# 第 0 章 はじめる前に：道具と言葉の準備

この章では、コードを書く前に、<strong>必要な道具を入れ、この教材で何度も出てくる言葉の意味をそろえます</strong>。「本当に一から」の人が、第 1 章の最初の一歩でつまずかないための章です。すでに Visual Studio で C++ のプロジェクトを作ったことがあり、DLL とは何かを知っている人は、「道具の準備」だけ確認して、第 1 章へ進んで構いません。

## この教材で作るもの

作るのは、<strong>ゲーム エンジンと、そのエディタ</strong>です。

- <strong>ゲーム エンジン</strong>は、画面に絵を出し、物を動かし、入力を受け取る、ゲームの土台になるプログラムです。この教材では、とても小さなエンジン（<strong>MiniEngine</strong>）を、C++ で作ります。
- <strong>エディタ</strong>は、そのエンジンで使う世界（シーン）を、マウスで作る道具です。Unity や Unreal Engine の、画面の真ん中に 3D が見えていて、左に物の一覧、右に数値の入力欄がある、あの画面です。この教材では、エディタを <strong>C# と WPF</strong> で作ります。

つまり、<strong>2 つの言語で、1 つのアプリを作る</strong>ことになります。C++ で書いた部分と、C# で書いた部分が、お互いを呼び合います。この「呼び合う仕組み」が、この教材の中心です。

## なぜ 2 つの言語を使うのか

画面作りには C#、速さが要る中核には C++ が向いているからです。理由は第 1 章でくわしく説明します。ここでは、<strong>「2 つの言語を使うことは、現場でよくある普通のやり方」</strong>だと知っておいてください。実際、多くのゲーム会社のツール（エディタ）は、C# や別の言語で作られ、ゲーム本体は C++ で作られています。

## 道具の準備

| 道具 | 内容 |
| --- | --- |
| Windows | Windows 10 または 11（64 ビット）。DirectX 12 を使うため、Windows 専用になる |
| GPU | DirectX 12 に対応した GPU（ここ数年のノート PC なら、たいてい対応している）。迷ったら、`Win + R` → `dxdiag` → 「ディスプレイ」タブの「機能レベル」に `12_0` などが見えればよい |
| Visual Studio 2022 | Community（無料）で十分。2022 より新しい版でも、ほぼ同じ手順で進められる |
| Git（任意） | 章ごとに記録を残しておくと、うまくいかなくなったときに戻せる |

### Visual Studio のインストール

Visual Studio Installer で、次の 2 つの<strong>ワークロード</strong>（機能のまとまり）にチェックを入れます。

| ワークロード | なぜ必要か |
| --- | --- |
| <strong>C++ によるデスクトップ開発</strong> | C++ のコンパイラ、Windows SDK（DirectX のヘッダーとライブラリ）が入る |
| <strong>.NET デスクトップ開発</strong> | C# のコンパイラ、.NET、WPF の設計画面（XAML デザイナー）が入る |

さらに、「個別のコンポーネント」タブで、次を確認します。

| コンポーネント | なぜ必要か |
| --- | --- |
| Windows 11 SDK（または Windows 10 SDK） | DirectX 12 のヘッダー。ワークロードに含まれるが、入っているか確認する |
| .NET 8.0 ランタイム | Editor を動かす。ワークロードに含まれる |
| C++/CLI サポート（最新の v143 ビルド ツール） | 第 28 章で、C++/CLI の橋渡しを作るときに使う。今のうちに入れておく |

加えて、Windows の「設定 → システム → オプション機能」から、<strong>「グラフィックス ツール」</strong>を入れておきます。DirectX 12 の<strong>デバッグ レイヤー</strong>（間違った使い方を教えてくれる機能）に必要です。入れていないと、デバッグ ビルドでエンジンが起動しないことがあります（第 4 章の「よくあるミス」）。

## 言葉の準備

この教材では、次の言葉が何度も出てきます。覚える必要はありません。<strong>分からなくなったら、この表に戻ってきてください。</strong>

### Visual Studio の言葉

| 言葉 | 意味 |
| --- | --- |
| ソリューション（`.sln`） | プロジェクトを、まとめて開くための入れ物。この教材では `MiniEngine.sln` |
| プロジェクト | 1 つの成果物（`.exe` や `.dll`）を作るための、ソース ファイルと設定のまとまり。C++ は `.vcxproj`、C# は `.csproj` |
| ビルド | ソース コードから、成果物（`.exe`、`.dll`）を作る作業全体。コンパイルとリンクを含む |
| 構成（Debug / Release） | Debug は、デバッグしやすいが遅い設定。Release は、速いがデバッグしにくい設定 |
| プラットフォーム（x64） | 動かす CPU の種類。この教材は、<strong>x64（64 ビット）だけ</strong>を使う |
| NuGet | C# のライブラリを、インターネットから入れる仕組み（C++ の vcpkg に近い） |
| ソリューション エクスプローラー | 画面の右側にある、ファイルとプロジェクトの一覧 |
| 出力ウィンドウ | ビルドの結果や、プログラムが出したログが出る場所 |

### 実行ファイルの言葉

| 言葉 | 意味 |
| --- | --- |
| EXE | 実行できるプログラム。ダブルクリックで動く。1 つのプロセスの入口（`main` など）を持つ |
| DLL | 他のプログラムから、<strong>実行時に読み込まれる</strong>部品。EXE から呼ばれる関数やクラスを持つ。単体では動かない |
| インポート ライブラリ（`.lib`） | DLL を<strong>使う側</strong>が、ビルドのときにリンクする目録。「この名前の関数は、この DLL にある」と書いてある |
| 公開ヘッダー | DLL の利用者に見せる、`.h` ファイル。宣言だけが書いてある |
| エクスポート | DLL が、外から使える関数やクラスとして公開すること |
| 静的リンクと動的リンク | 静的は、部品を EXE の中に埋め込む。動的は、部品を別ファイル（DLL）のままにして、実行時に読み込む |
| プロセス | 実行中のプログラム 1 つ分。それぞれが、独立したメモリ空間を持つ |

### C# 連携の言葉

| 言葉 | 意味 |
| --- | --- |
| ネイティブ（アンマネージド）コード | C++ のように、CPU がそのまま実行する機械語のコード。メモリは自分で管理する |
| マネージド コード | C# のように、.NET の実行環境（CLR）の上で動くコード。メモリは、ガベージ コレクターが管理する |
| CLR | .NET の実行環境（Common Language Runtime）。C# のコードを動かす仕組み |
| ガベージ コレクター（GC） | 使われなくなったオブジェクトを、自動で見つけて解放する仕組み。C++ の `delete` が、要らない |
| P/Invoke | C# から、DLL の C 関数を呼ぶ仕組み（Platform Invoke） |
| マーシャリング | C# と C++ の間で、データの形式を変換して受け渡すこと |
| ABI | 関数の呼び方の約束（引数をどこに置くか、戻り値をどう返すか）。DLL の境界では、これがそろっている必要がある |

### 画面作りの言葉

| 言葉 | 意味 |
| --- | --- |
| WPF | Windows のデスクトップ アプリの、画面を作る仕組み（Windows Presentation Foundation） |
| XAML | 画面の構造を書く言語。XML の仲間。ボタンや文字の配置を、タグで書く |
| ビューとビューモデル | 画面（ビュー）と、画面が見せるデータと操作（ビューモデル）を、分ける設計（MVVM） |
| データ バインディング | 画面の部品と、データを、「つなぐ」仕組み。データが変わると、画面が自動で変わる |
| Prism | WPF のアプリを、部品に分けて育てやすくするための、フレームワーク |
| DI（依存性注入） | 必要な部品を、自分で作らず、外から渡してもらう設計 |

## この教材の読み方

### 各章の流れ

どの章も、<strong>ゴール → 追加するもの → 手順 → 新しく出てきたもの → 動作確認 → よくあるミス → 次の章へ</strong>の順です。

- <strong>ゴール</strong>で、その章の終わりに何ができているかを確かめます。
- <strong>手順</strong>は、上から順に実行します。コードは、写して構いません。ただし、<strong>写しながら、直後の解説を読んでください</strong>。解説を読まずに写すだけだと、後で自分の手で直せなくなります。
- <strong>「新しく出てきたもの」の表</strong>は、その場で初めて出た言葉や型の説明です。初めて見たものは、必ずここに載っています。
- <strong>動作確認</strong>で、期待する結果になっていなければ、先に進まず、「よくあるミス」を読みます。

### つまずいたとき

| 状況 | まず見る所 |
| --- | --- |
| ビルドが通らない | 出力ウィンドウの、<strong>最初の</strong>エラー。2 つ目以降は、最初のエラーの連鎖であることが多い。エラー コード（`C2065`、`LNK2019`、`CS0103` など）で検索する |
| 動くが、結果が違う | その章の「動作確認」の表と見比べる。1 つ前の章の最後の状態に、戻れるか確認する |
| 起動しない、すぐ落ちる | 出力ウィンドウのログと、Visual Studio の例外ダイアログ。例外の<strong>メッセージ</strong>をそのまま読む |
| 全然分からない | 章ごとに、Git で記録を残しておく。直前の章に戻って、手順をやり直す |

!!! tip "章ごとに Git で記録する"
    ソリューションのフォルダーで `git init` をして、章が終わるたびに `git add -A` と `git commit -m "第 N 章"` をしておくと、いつでも前の章に戻れます。`bin\` と `obj\` と `.vs\` は記録しない（`.gitignore` に書く）のが、おすすめです。

### コードの写し方

- コードのコメントは、<strong>日本語で解説目的に</strong>書いてあります。自分で書くときに、同じ書き方をする必要はありません。
- ファイル名は、コード ブロックの前に書いてあります。<strong>どのファイルに書くか</strong>を、必ず確認します。
- コードは、実際にビルドして確認してはいません。動かないときは、タイプミス、インクルードや `using` の抜け、プロジェクト設定の見落としを、まず疑います。

## 全体の流れ

```text
第 1〜4 章   エンジン側（C++）を、先に作る。Player で動かして確かめる
第 5〜24 章  C# と WPF と Prism を、学びながら、エディタの骨組みを作る
第 25〜29 章 C# から C++ を呼ぶ仕組みを作る（P/Invoke と C++/CLI を比べる）
第 30〜33 章 エディタの真ん中に、エンジンの 3D 画面を埋め込む
第 34〜40 章 シーン ツリー、プロパティ、Undo/Redo、保存、アセット ブラウザ
第 41〜47 章 ゲーム DLL のホット リロード、Play モード、仕上げ
```

先に C++ 側を作る理由は、<strong>「エンジンだけで動く」状態を、先に作っておく</strong>ためです。エディタを作り始めてから動かないとき、エンジンが悪いのか、連携が悪いのか、分からなくなってしまうからです。
