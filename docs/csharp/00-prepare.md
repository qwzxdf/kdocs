# 第 0 章 はじめる前に：道具と言葉の準備

この章では、コードを書く前に必要な道具を入れて、この教材で何度も出てくる言葉の意味をそろえます。「本当に一から」始める人が第 1 章の最初の一歩でつまずかないための章です。Visual Studio で C++ のプロジェクトを作ったことがあり、DLL が何かも知っている人は、「道具の準備」だけ確認して、第 1 章へ進んで構いません。

## この教材で作るもの

作るのは、ゲーム エンジンと、そのエディタです。

- ゲーム エンジンは、画面に絵を出し、物を動かし、入力を受け取る、ゲームの土台になるプログラムです。この教材では、とても小さなエンジン（MiniEngine）を C++ で作ります。
- エディタは、そのエンジンで使う世界（シーン）をマウスで作る道具です。Unity や Unreal Engine の、真ん中に 3D が見えていて、左に物の一覧、右に数値の入力欄が並んでいる、あの画面です。この教材では、エディタを C# と WPF で作ります。

つまり、2 つの言語で 1 つのアプリを作ることになります。C++ で書いた部分と C# で書いた部分がお互いを呼び合います。この「呼び合う仕組み」がこの教材の中心です。

## なぜ 2 つの言語を使うのか

画面作りには C#、速さが要る中核には C++ が向いているからです。理由は第 1 章で詳しく説明します。ここでは、2 つの言語を使うのは現場でよくある普通のやり方だ、と知っておいてください。実際、多くのゲーム会社では、ツール（エディタ）は C# などで作り、ゲーム本体は C++ で作っています。

## 道具の準備

| 道具 | 内容 |
| --- | --- |
| Windows | Windows 10 または 11（64 ビット）。DirectX 12 を使うため、Windows 専用になる |
| GPU | DirectX 12 に対応した GPU（ここ数年のノート PC なら、たいてい対応している）。迷ったら、`Win + R` → `dxdiag` → 「ディスプレイ」タブの「機能レベル」に `12_0` などが見えればよい |
| Visual Studio 2026 | Community（無料）で十分 |
| Git（任意） | 章ごとに記録を残しておくと、うまくいかなくなったときに戻せる |

### Visual Studio のインストール

Visual Studio Installer で、次の 2 つのワークロード（機能のまとまり）にチェックを入れます。

| ワークロード | なぜ必要か |
| --- | --- |
| C++ によるデスクトップ開発 | C++ のコンパイラ、Windows SDK（DirectX のヘッダーとライブラリ）が入る |
| .NET デスクトップ開発 | C# のコンパイラ、.NET、WPF の設計画面（XAML デザイナー）が入る |

さらに、「個別のコンポーネント」タブで、次を確認します。

| コンポーネント | なぜ必要か |
| --- | --- |
| Windows 11 SDK（または Windows 10 SDK） | DirectX 12 のヘッダー。ワークロードに含まれるが、入っているか確認する |
| .NET 8.0 ランタイム | Editor を動かす。ワークロードに含まれる |
| C++/CLI サポート（最新の v145 ビルド ツール） | 第 33 章で、C++/CLI の橋渡しを作るときに使う。今のうちに入れておく |

さらに、Windows の「設定 → システム → オプション機能」から、「グラフィックス ツール」を入れておきます。DirectX 12 のデバッグ レイヤー（間違った使い方を教えてくれる機能）に必要です。入れていないと、デバッグ ビルドでエンジンが起動しないことがあります（第 4 章の「よくあるミス」）。

## 言葉の準備

この教材では、次の言葉が何度も出てきます。覚える必要はありません。分からなくなったら、この表に戻ってきてください。

### Visual Studio の言葉

| 言葉 | 意味 |
| --- | --- |
| ソリューション（`.sln`） | プロジェクトをまとめて開くための入れ物。この教材では `MiniEngine.sln` |
| プロジェクト | 1 つの成果物（`.exe` や `.dll`）を作るための、ソース ファイルと設定のまとまり。C++ は `.vcxproj`、C# は `.csproj` |
| ビルド | ソース コードから、成果物（`.exe`、`.dll`）を作る作業全体。コンパイルとリンクを含む |
| 構成（Debug / Release） | Debug は、デバッグしやすいが遅い設定。Release は、速いがデバッグしにくい設定 |
| プラットフォーム（x64） | 動かす CPU の種類。この教材は、x64（64 ビット）だけを使う |
| NuGet | C# のライブラリをインターネットから入れる仕組み（C++ の vcpkg に近い） |
| ソリューション エクスプローラー | 画面の右側にある、ファイルとプロジェクトの一覧 |
| 出力ウィンドウ | ビルドの結果や、プログラムが出したログが出る場所 |

### 実行ファイルの言葉

| 言葉 | 意味 |
| --- | --- |
| EXE | 実行できるプログラム。ダブルクリックで動く。1 つのプロセスの入口（`main` など）を持つ |
| DLL | 他のプログラムから、実行時に読み込まれる部品。EXE から呼ばれる関数やクラスを持つ。単体では動かない |
| インポート ライブラリ（`.lib`） | DLL を使う側がビルドのときにリンクする目録。「この名前の関数は、この DLL にある」と書いてある |
| 公開ヘッダー | DLL の利用者に見せる、`.h` ファイル。宣言だけが書いてある |
| エクスポート | DLL が、外から使える関数やクラスとして公開すること |
| 静的リンクと動的リンク | 静的は、部品を EXE の中に埋め込む。動的は、部品を別ファイル（DLL）のままにして、実行時に読み込む |
| プロセス | 実行中のプログラム 1 つ分。それぞれが、独立したメモリ空間を持つ |

### C# 連携の言葉

| 言葉 | 意味 |
| --- | --- |
| ネイティブ（アンマネージド）コード | C++ のように、CPU がそのまま実行する機械語のコード。メモリは自分で管理する |
| マネージド コード | C# のように、.NET の実行環境（CLR）の上で動くコード。メモリは、ガベージ コレクターが管理する |
| CLR | .NET の実行環境（Common Language Runtime）。C# のコードを動かす仕組み |
| ガベージ コレクター（GC） | 使われなくなったオブジェクトを自動で見つけて解放する仕組み。C++ の `delete` が、要らない |
| P/Invoke | C# から、DLL の C 関数を呼ぶ仕組み（Platform Invoke） |
| マーシャリング | C# と C++ の間で、データの形式を変換して受け渡すこと |
| ABI | 関数の呼び方の約束（引数をどこに置くか、戻り値をどう返すか）。DLL の境界では、これがそろっている必要がある |

### 画面作りの言葉

| 言葉 | 意味 |
| --- | --- |
| WPF | Windows のデスクトップ アプリの、画面を作る仕組み（Windows Presentation Foundation） |
| XAML | 画面の構造を書く言語。XML の仲間。ボタンや文字の配置をタグで書く |
| ビューとビューモデル | 画面（ビュー）と、画面が見せるデータと操作（ビューモデル）を分ける設計（MVVM） |
| データ バインディング | 画面の部品と、データを「つなぐ」仕組み。データが変わると、画面が自動で変わる |
| Prism | WPF のアプリを部品に分けて育てやすくするための、フレームワーク |
| DI（依存性注入） | 必要な部品を自分で作らず、外から渡してもらう設計 |

## この教材の読み方

### 各章の流れ

どの章も、ゴール → 追加するもの → 手順 → 新しく出てきたもの → 動作確認 → よくあるミス → 次の章への順です。

- ゴールには、その章の終わりに何ができているかが書いてあります。
- 手順は、上から順に実行します。コードは写して構いません。ただし、写しながら直後の解説を読んでください。解説を読まずに写すだけでは、後で自分の手で直せなくなります。
- 「新しく出てきたもの」の表は、その場で初めて出た言葉や型の説明です。初めて見たものは、必ずここに載っています。
- 動作確認で期待どおりの結果にならなかったら、先に進まずに、「よくあるミス」を読んでください。

### つまずいたとき

| 状況 | まず見る所 |
| --- | --- |
| ビルドが通らない | 出力ウィンドウの、最初のエラー。2 つ目以降は、最初のエラーの連鎖であることが多い。エラー コード（`C2065`、`LNK2019`、`CS0103` など）で検索する |
| 動くが、結果が違う | その章の「動作確認」の表と見比べる。1 つ前の章の最後の状態に戻れるか確認する |
| 起動しない、すぐ落ちる | 出力ウィンドウのログと、Visual Studio の例外ダイアログ。例外のメッセージをそのまま読む |
| 全然分からない | 章ごとに、Git で記録を残しておく。直前の章に戻って、手順をやり直す |

!!! tip "章ごとに Git で記録する"
    ソリューションのフォルダーで `git init` をして、章が終わるたびに `git add -A` と `git commit -m "第 N 章"` をしておくと、いつでも前の章に戻れます。`bin\` と `obj\` と `.vs\` は記録しない（`.gitignore` に書く）のが、おすすめです。

### コードの写し方

- コードのコメントは、日本語で解説目的に書いてあります。自分で書くときに、同じ書き方をする必要はありません。
- ファイル名は、コード ブロックの前に書いてあります。どのファイルに書くかを必ず確認します。
- コードは、実際にビルドして確認してはいません。動かないときは、タイプミス、インクルードや `using` の抜け、プロジェクト設定の見落としをまず疑います。

## 全体の流れ

```text
第 1〜4 章   エンジン側（C++）を先に作る。Player で動かして確かめる
第 5〜29 章  C# と WPF と Prism を学びながら、エディタの骨組みを作る
第 30〜34 章 C# から C++ を呼ぶ仕組みを作る（P/Invoke と C++/CLI を比べる）
第 35〜38 章 エディタの真ん中に、エンジンの 3D 画面を埋め込む
第 39〜45 章 シーン ツリー、プロパティ、Undo/Redo、保存、アセット ブラウザ
第 46〜52 章 ゲーム DLL のホット リロード、Play モード、仕上げ
```

先に C++ 側を作るのは、「エンジンだけで動く」状態を先に作っておくためです。エディタを作り始めてから動かなくなったとき、エンジンが悪いのか連携が悪いのか、分からなくなってしまうからです。
