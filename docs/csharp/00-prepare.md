# 第 0 章 はじめる前に：道具と言葉の準備

この教材は C++ のエンジンと C# のエディタという 2 つの言語を行き来します。いきなり第 1 章を始めると、「ソリューション」「DLL」「マーシャリング」といった言葉が説明なしに出てきて、手順は追えても何をしているのかが分からなくなりがちです。そこで、コードを書く前に道具を入れて、何度も出てくる言葉の意味をそろえておきます。Visual Studio で C++ のプロジェクトを作ったことがあり、DLL が何かも知っている人は「道具の準備」だけ確認して、第 1 章へ進んで構いません。

## この教材で作るもの

作るのはゲーム エンジンとそのエディタです。

- ゲーム エンジンは画面に絵を出し、物を動かし入力を受け取るゲームの土台になるプログラムです。この教材ではとても小さなエンジン（MiniEngine）を C++ で作ります。
- エディタはそのエンジンで使う世界（シーン）をマウスで作る道具です。Unity や Unreal Engine の真ん中に 3D が見えていて、左に物の一覧、右に数値の入力欄が並んでいる、あの画面です。この教材ではエディタを C# と WPF で作ります。

つまり、2 つの言語で 1 つのアプリを作ることになります。C++ で書いた部分と C# で書いた部分がお互いを呼び合います。この「呼び合う仕組み」がこの教材の中心です。

## なぜ 2 つの言語を使うのか

画面作りには C#、速さが要る中核には C++ が向いているからです。理由は第 1 章で詳しく説明します。ここでは、2 つの言語を使うのは現場でよくある普通のやり方だと知っておいてください。実際、多くのゲーム会社ではツール（エディタ）は C# などで作りゲーム本体は C++ で作っています。

## 道具の準備

OS は Windows 10 または 11（64 ビット）です。DirectX 12 を使うので、Windows 専用の教材になります。

GPU は DirectX 12 に対応しているものが要ります。ここ数年のノート PC ならたいてい対応しています。迷ったら `Win + R` で `dxdiag` を開いて、「ディスプレイ」タブの「機能レベル」に `12_0` などが見えれば大丈夫です。

開発には Visual Studio 2026 を使います。Community（無料）で十分です。

Git は必須ではありませんが、章ごとに記録を残しておくとうまくいかなくなったときに前の章へ戻れるので、入れておくことをすすめます。

### Visual Studio のインストール

Visual Studio Installer で、次の 2 つのワークロード（機能のまとまり）にチェックを入れます。

「C++ によるデスクトップ開発」には、C++ のコンパイラと Windows SDK（DirectX のヘッダーとライブラリ）が入っています。エンジン側を作るのに要ります。

「.NET デスクトップ開発」には C# のコンパイラと .NET、それに WPF の設計画面（XAML デザイナー）が入っています。エディタ側を作るのに要ります。

さらに、「個別のコンポーネント」タブで、次を確認します。

Windows 11 SDK（または Windows 10 SDK）は、DirectX 12 のヘッダーです。ワークロードに含まれていますが、入っているかを確かめてください。.NET 8.0 ランタイムも Editor を動かすのに要るもので、ワークロードに含まれています。

「C++/CLI サポート（最新の v145 ビルド ツール）」は、ワークロードには含まれません。第 34 章で C++/CLI の橋渡しを作るときに使うので、今のうちに入れておくとあとで Installer を開き直さずに済みます。

さらに、Windows の「設定 → システム → オプション機能」から、「グラフィックス ツール」を入れておきます。DirectX 12 のデバッグ レイヤー（間違った使い方を教えてくれる機能）に必要です。入れていないとデバッグ ビルドでエンジンが起動しないことがあります（第 4 章の「よくあるミス」）。

## 言葉の準備

この教材では次の言葉が何度も出てきます。覚える必要はありません。分からなくなったらこの表に戻ってきてください。

### Visual Studio の言葉

- ソリューション（`.sln`）: プロジェクトをまとめて開くための入れ物。この教材では `MiniEngine.sln`
- プロジェクト: 1 つの成果物（`.exe` や `.dll`）を作るためのソース ファイルと設定のまとまり。C++ は `.vcxproj`、C# は `.csproj`
- ビルド: ソース コードから、成果物（`.exe`、`.dll`）を作る作業全体。コンパイルとリンクを含む
- 構成（Debug / Release）: Debug は、デバッグしやすいが遅い設定。Release は速いがデバッグしにくい設定
- プラットフォーム（x64）: 動かす CPU の種類。この教材は x64（64 ビット）だけを使う
- NuGet: C# のライブラリをインターネットから入れる仕組み（C++ の vcpkg に近い）
- ソリューション エクスプローラー: 画面の右側にある、ファイルとプロジェクトの一覧
- 出力ウィンドウ: ビルドの結果やプログラムが出したログが出る場所

### 実行ファイルの言葉

- EXE: 実行できるプログラム。ダブルクリックで動く。1 つのプロセスの入口（`main` など）を持つ
- DLL: 他のプログラムから、実行時に読み込まれる部品。EXE から呼ばれる関数やクラスを持つ。単体では動かない
- インポート ライブラリ（`.lib`）: DLL を使う側がビルドのときにリンクする目録。「この名前の関数はこの DLL にある」と書いてある
- 公開ヘッダー: DLL の利用者に見せる `.h` ファイル。宣言だけが書いてある
- エクスポート: DLL が、外から使える関数やクラスとして公開すること
- 静的リンクと動的リンク: 静的は、部品を EXE の中に埋め込む。動的は部品を別ファイル（DLL）のままにして、実行時に読み込む
- プロセス: 実行中のプログラム 1 つ分。それぞれが独立したメモリ空間を持つ

### C# 連携の言葉

- ネイティブ（アンマネージド）コード: C++ のように CPU がそのまま実行する機械語のコード。メモリは自分で管理する
- マネージド コード: C# のように.NET の実行環境（CLR）の上で動くコード。メモリはガベージ コレクターが管理する
- CLR: .NET の実行環境（Common Language Runtime）。C# のコードを動かす仕組み
- ガベージ コレクター（GC）: 使われなくなったオブジェクトを自動で見つけて解放する仕組み。C++ の `delete` が要らない
- P/Invoke: C# から、DLL の C 関数を呼ぶ仕組み（Platform Invoke）
- マーシャリング: C# と C++ の間で、データの形式を変換して受け渡すこと
- ABI: 関数の呼び方の約束（引数をどこに置くか戻り値をどう返すか）。DLL の境界ではこれがそろっている必要がある

### 画面作りの言葉

- WPF: Windows のデスクトップ アプリの画面を作る仕組み（Windows Presentation Foundation）
- XAML: 画面の構造を書く言語。XML の仲間。ボタンや文字の配置をタグで書く
- ビューとビューモデル: 画面（ビュー）と画面が見せるデータと操作（ビューモデル）を分ける設計（MVVM）
- データ バインディング: 画面の部品とデータを「つなぐ」仕組み。データが変わると画面が自動で変わる
- Prism: WPF のアプリを部品に分けて育てやすくするためのフレームワーク
- DI（依存性注入）: 必要な部品を自分で作らず外から渡してもらう設計

## この教材の読み方

### 各章の流れ

どの章もゴール → 追加するもの → 手順 → 新しく出てきたもの → 動作確認 → よくあるミス → 次の章への順です。

- ゴールにはその章の終わりに何ができているかが書いてあります。
- 手順は上から順に実行します。コードは写して構いません。ただし、写しながら直後の解説を読んでください。解説を読まずに写すだけでは後で自分の手で直せなくなります。
- 「新しく出てきたもの」の表はその場で初めて出た言葉や型の説明です。初めて見たものは必ずここに載っています。
- 動作確認で期待どおりの結果にならなかったら、先に進まずに「よくあるミス」を読んでください。

### つまずいたとき

ビルドが通らないときは出力ウィンドウの最初のエラーだけを見ます。2 つ目以降のエラーは最初のエラーの連鎖であることが多いからです。エラー コード（`C2065`、`LNK2019`、`CS0103` など）で検索すると原因が見つかります。

動くけれど結果が違うときはその章の「動作確認」と見比べて、1 つ前の章の最後の状態に戻れるかを確かめます。

起動しないすぐ落ちるときは出力ウィンドウのログと Visual Studio の例外ダイアログを見ます。例外のメッセージはそのまま読んでください。そこに原因が書いてあります。

どうしても分からなくなったら、Git で記録しておいた直前の章に戻って、手順をやり直します。

!!! tip "章ごとに Git で記録する"
    ソリューションのフォルダーで `git init` をして、章が終わるたびに `git add -A` と `git commit -m "第 N 章"` をしておくといつでも前の章に戻れます。`bin\` と `obj\` と `.vs\` は記録しない（`.gitignore` に書く）のが、おすすめです。

### コードの写し方

- コードのコメントは日本語で解説目的に書いてあります。自分で書くときに同じ書き方をする必要はありません。
- ファイル名はコード ブロックの前に書いてあります。どのファイルに書くかを必ず確認します。
- コードは実際にビルドして確認してはいません。動かないときはタイプミス、インクルードや `using` の抜けプロジェクト設定の見落としをまず疑います。

## 全体の流れ

```text
第 1〜4 章   エンジン側（C++）を先に作る。Player で動かして確かめる
第 5〜30 章  C# と WPF と Prism を学びながら、エディタの骨組みを作る
第 31〜35 章 C# から C++ を呼ぶ仕組みを作る（P/Invoke と C++/CLI を比べる）
第 36〜39 章 エディタの真ん中に、エンジンの 3D 画面を埋め込む
第 40〜46 章 シーン ツリー、プロパティ、Undo/Redo、保存、アセット ブラウザ
第 47〜53 章 ゲーム DLL のホット リロード、Play モード、仕上げ
```

先に C++ 側を作るのは「エンジンだけで動く」状態を先に作っておくためです。エディタを作り始めてから動かなくなったときエンジンが悪いのか連携が悪いのか、分からなくなってしまうからです。
