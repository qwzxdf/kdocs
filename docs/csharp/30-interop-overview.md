# 第 30 章 C# から C++ を呼ぶ：連携方式の比較

この章から第 3 部です。エディタ（C#）とエンジン（C++）をつなぎます。ただ、いきなりコードを書き始める前につなぎ方にはどんな選択肢があって、なぜこの教材は今の方式を選んだのかを整理しておきたいと思います。この章にコードはほとんど出てきません。ですが、「なぜ C の関数にするのか」「なぜ文字列は UTF-8 なのか」「なぜ `bool` を渡さないのか」といった、後の章の決めごとの理由は、全部ここに書いてあります。

## C# と C++ は、そもそも別の世界で動いている

つなぐ前に何がつなぎにくいのかを知っておくと、あとの話が分かりやすくなります。

| | C# | C++ |
| --- | --- | --- |
| 動き方 | .NET の実行環境（CLR）が中間言語を機械語に変換しながら動かす | コンパイラーが作った機械語を CPU が直接動かす |
| メモリ | GC が管理する。オブジェクトを GC が勝手に動かすことがある | 自分で管理する。アドレスは動かない |
| 文字列 | UTF-16。変更できない。GC の管理下 | `char*`、`wchar_t*`、`std::string` など、場面によってバラバラ |
| 例外 | CLR の例外 | C++ の例外（や SEH）。お互いに相手の例外を理解できない |
| 型 | .NET の型 | クラスのレイアウトや仮想関数テーブルは、コンパイラー次第 |

この 2 つの世界の間に橋をかけるのが、連携（相互運用、interop）です。特に困るのは、「GC がオブジェクトを動かす」ことと、「お互いの例外が通じない」ことです。この 2 つは、これから何度も出てきます。

## つなぎ方の候補

### P/Invoke

C# から、DLL が公開している C の関数を直接呼びます。

```csharp
[LibraryImport("EngineApi.dll")]
private static partial int me_get_api_version();
```

C# の側に「この名前の関数がこの DLL にあります」という宣言を書くだけです。呼び出しの瞬間に CLR が引数を C の形に変換して（マーシャリング）、関数を呼んでくれます。C++ の側は、`extern "C"` を付けて関数を公開するだけでよく、特別なプロジェクトも要りません。

困るのは、呼べるものが C の関数に限られることです。クラスやテンプレートは渡せません。そして、C のヘッダーと C# の宣言を手で見比べながら 2 回書くことになります。C# のコンパイラーは C のヘッダーを読めないので、宣言が食い違っていても、ビルドは通ってしまいます。壊れるのは実行時です。

### C++/CLI

C++ に、.NET 向けの拡張を足した言語です。マネージド（C#）側とネイティブ（C++）側の両方を 1 つのファイルの中に書けます。

```cpp
public ref class EngineBridge {
 public:
  void Tick(float dt) { engine_->Tick(dt); }   // 中でネイティブのクラスをそのまま呼ぶ
 private:
  mini::Engine* engine_;
};
```

C# からは、これは普通の .NET のクラスに見えます。C++ のクラスを C の関数に分解する必要がなく、型のずれもコンパイラーが見つけてくれるので、一見すると理想的です。

ただし代償もあります。C++/CLI という別の言語を学ぶ必要があり、Windows 専用で、ビルドが遅く、プロジェクトの設定にもクセがあります（`/clr`、ランタイムは `/MD` 必須、新しい C++ の機能との相性など）。

### COM

Windows の古くからある、言語に依存しないオブジェクトの仕組みです。DirectX も COM でできています。長所は言語を問わないことですが、実装が大変です（`IUnknown`、参照カウント、GUID、登録）。すでにある COM のコンポーネントを使うときの選択肢で、新しく作る連携にはあまり向きません。

### プロセス間通信（IPC）

エンジンを別のプロセスにして、パイプやソケットでやり取りします。エンジンが落ちてもエディタは落ちず、言語もビット数も自由です。反面、データのコピーが必要で遅く、何より 3D ビューポートの表示が難しくなります（別プロセスの絵を WPF の中に出さないといけません）。エディタとゲームを分離してデバッグしたい、といった目的に向きます。

## 並べて比べる

| | P/Invoke + C API | C++/CLI | COM | IPC |
| --- | --- | --- | --- | --- |
| C++ のクラスを渡せるか | 渡せない（ハンドルで間接的に） | そのまま包める | インターフェースで渡せる | メッセージで送る |
| 追加のプロジェクト | 要らない | 要る | 要る | 要る |
| 呼び出しの速さ | 速い（数十ナノ秒） | 速い | やや遅い | 遅い |
| C++ の例外 | 境界で止める | `try/catch` で変換できる | `HRESULT` にする | メッセージで返す |
| ビルドの手間 | 小さい | 大きい | 大きい | 中くらい |
| 他の OS | 使い回せる | 使えない | 使えない | 使える |
| 宣言のずれ | 実行時に壊れる | ビルドで見つかる | IDL で管理 | プロトコル次第 |

## この教材の選択

主役は P/Invoke + C API にします。次の 4 つの理由があります。

1. C の API は、いちばん壊れにくい境界です。クラスのレイアウト、仮想関数テーブル、`std::` の実装、例外といった、コンパイラー依存の問題が入り込みません。
2. 追加のプロジェクトが要らないので、ビルドが速く、設定も単純です。
3. エンジンの API を C の関数として整理すること自体が設計の練習になります。何を公開して、何を隠すのかを嫌でも考えることになるからです。
4. 将来、別の言語（Python のスクリプトなど）や別の OS から使うときも、同じ C API が使えます。

ただし比較のために、C++/CLI 版も第 33 章で実際に作ります。どちらの方式でも同じ `IEngineService` というインターフェースを実装しておくので、ビューモデルは、どちらが使われているかを知りません。

```text
┌─────────────────── Editor.exe （C#） ───────────────────┐
│  ViewModel ──▶ IEngineService（インターフェース）            │
│                    ├─ PInvokeEngineService  ← 第 32 章  │
│                    └─ ClrEngineService      ← 第 33 章  │
└──────────────┬────────────────────────┬────────────────┘
               │ P/Invoke               │ 参照
               ▼                        ▼
      EngineApi.dll（C ABI）     EngineBridge.dll（C++/CLI）
               │                        │
               └───────────┬────────────┘
                           ▼
                      Engine.dll（C++）
```

## 境界を越えるときの決まりごと

どの方式を選んでも、境界を越えるものは慎重に選ばなければいけません。この教材の決まりごとを先にまとめておきます。

### 型は、そのままのバイト列で越えられるものだけ

C# と C++ で、メモリ上の並びが同じ型を blittable（ブリッタブル）な型と呼びます。変換が要らないので、速くて安全です。

| C++ | C# | そのまま渡せるか |
| --- | --- | --- |
| `int8_t` / `uint8_t` | `sbyte` / `byte` | 渡せる |
| `int16_t` / `uint16_t` | `short` / `ushort` | 渡せる |
| `int32_t` / `uint32_t` | `int` / `uint` | 渡せる |
| `int64_t` / `uint64_t` | `long` / `ulong` | 渡せる（C++ の Windows の `long` は 32 ビットなので使わない） |
| `float` / `double` | `float` / `double` | 渡せる |
| ポインター | `nint`、`T*` | 渡せる |
| 構造体 | `struct` | 中身がすべて渡せる型なら渡せる。並びを合わせる（第 32 章） |
| `enum` | `enum` | 渡せる。土台の型を `int32_t` にそろえる |
| `bool` | `bool` | 渡せない |
| `char*`（文字列） | `string` | 変換が要る。UTF-8 と決めておく |
| クラス、`std::string`、`std::vector` | なし | 渡せない |

`bool` が渡せないのは、少し意外かもしれません。C++ の `bool` は 1 バイトですが、C# が既定で期待する `bool` は 4 バイト（Windows の `BOOL`）なので、大きさが食い違います。この教材では、境界を越える真偽値は、`uint8_t`（0 か 1）か `int32_t` にします。

### 文字列は UTF-8

文字列の形式は、UTF-16（`wchar_t*`）、ANSI（システムのコード ページ）、UTF-8 の 3 つが考えられます。ANSI は環境によって文字化けします。UTF-16 は Windows API にはなじみますが、C++ 側で扱いにくい場面が多いです。そこで、境界では UTF-8 の `const char*` に統一します。C# 側は、宣言に `StringMarshalling.Utf8` と書くだけで変換してくれます（[文字コード](../encoding/index.md)）。

### メモリは、確保した側が解放する

これも、最初に決めておかないと必ず事故になります。

- C# から C++ に渡す文字列や構造体は、呼び出しの間だけ有効です。C++ はそれを保存せず、必要ならコピーします。
- C++ から C# に文字列を返すときは、C# が用意したバッファーに C++ が書き込みます。
- オブジェクトは、C++ が作って、不透明なハンドル（ポインター）で渡します。解放も、C++ の `destroy` 関数で行います。

もう 1 つ気をつけたいのは、C# の GC が管理しているメモリのアドレスを C++ に渡して保持させないことです。GC はメモリを動かすことがあるので、保持されたアドレスがいつの間にか無効になります（ピン留めすれば動かなくなりますが、短い呼び出しの間だけにします）。

### 例外は境界で止める

C++ の例外が DLL の境界を越えると、未定義動作になります。C# の例外も、C++ には通じません。そこで、次の約束にします。

- C++ の公開関数は、中ですべての例外を捕まえる。
- 失敗は、戻り値のエラー コードで返す。詳しいメッセージは、別の関数（`me_get_last_error`）で取れるようにする。
- C# 側で、エラー コードを例外に変換する。
- C++ から C# を呼ぶコールバックの中でも、例外を外に出さない。

### 関数の名前と呼び出し規約

C++ の関数名は、型の情報を含んだ名前に変換されます（名前修飾）。`extern "C"` を付けると変換されず、`me_engine_create` のような素の名前で公開されます。C# の `[LibraryImport]` が探すのは、この素の名前です。

呼び出し規約は、x64 では 1 種類しかないので、`__cdecl` と `__stdcall` の違いは、実質ありません。それでも、宣言には書くのが習慣です。
