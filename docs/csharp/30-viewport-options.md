# 第 30 章 3D ビューポートを埋め込む方法の比較

この章から第 4 部です。エディタの真ん中に、<strong>エンジンが描く 3D の絵</strong>を出します。ここでは<strong>コードをほとんど書かず</strong>、WPF の画面の中に DirectX 12 の絵を出す方法を比べ、この教材で使う方式を決めます。

## この章の考え方

WPF の画面は、WPF 自身が描いています。WPF は DirectX 9 の技術を使って、ウィンドウ全体を 1 枚の絵として合成しています。ボタンも、文字も、透明度のあるパネルも、WPF が描いた絵です。

一方、エンジンは、DirectX 12 で描きます。この 2 つの<strong>描画の世界</strong>を、1 つの画面に同居させる必要があります。

```text
┌──────── Editor のウィンドウ ────────┐
│  WPF が描く世界                    │
│  ┌────────────┐                  │
│  │ DirectX 12 │ ← エンジンが描く世界 │
│  │ の絵        │                  │
│  └────────────┘                  │
└──────────────────────────────┘
```

同居のさせ方は、「<strong>絵をどうやって渡すか</strong>」で分かれます。

| 考え方 | 内容 |
| --- | --- |
| ① 場所を分ける | 画面の一部を、<strong>別のウィンドウ（HWND）</strong>として切り出し、そこにはエンジンが直接描く |
| ② 絵を渡す | エンジンが描いた絵を、<strong>WPF のテクスチャ</strong>として渡し、WPF が他の部品と一緒に合成する |
| ③ 絵を運ぶ | エンジンの絵を、<strong>CPU のメモリ経由</strong>で WPF のビットマップにコピーする |

この章では、この 3 つを順に見て、比べます。

## 前提：DX12 を使う

この教材のエンジンは、DirectX 12 です。スワップ チェーン、フェンスなどの扱いは、第 3 章で作りました。WPF と組み合わせる方式は、DX12 だと<strong>追加の制約</strong>が出ます。それぞれの方式の説明で、DX12 の場合を中心に述べます。

## 方式 A：HwndHost（子ウィンドウ）

### 仕組み

WPF の部品の `HwndHost` は、<strong>Win32 の子ウィンドウ</strong>を、WPF の画面の中に<strong>場所を確保して</strong>置く部品です。

```text
Editor.exe の最上位ウィンドウ（HWND）
 └─ WPF の描画面
     └─ [HwndHost の領域]
          └─ 子ウィンドウ（HWND）  ← Engine がここへ、スワップ チェーンで直接描く
```

エンジンは、この子ウィンドウの `HWND` に対して、`CreateSwapChainForHwnd` でスワップ チェーンを作ります。エンジンの絵は、<strong>WPF を通らず</strong>、Windows の合成（DWM）が、直接ウィンドウに表示します。

### 長所

| 長所 | 説明 |
| --- | --- |
| 仕組みが単純 | Player と同じ作り（HWND にスワップ チェーン）。第 3 章の `Engine` が、そのまま使える |
| 速い | 余計なコピー、変換が無い。VSync、フリップ モデルの利点が、そのまま得られる |
| DX12 向き | WPF との共有リソースが要らない。DX12 のキュー、フェンスの仕組みが、そのまま使える |
| 入力を受けやすい | 子ウィンドウが、マウスやキーボードのメッセージ（`WM_MOUSEMOVE` など）を直接受け取れる |
| 実績がある | 多くのツールが、この方式を使っている |

### 短所：エアスペース（Airspace）問題

<strong>WPF の部品を、HwndHost の上に重ねられません</strong>。子ウィンドウは、WPF の描画面の「外」にある別のウィンドウなので、<strong>WPF のコンテンツは、常に子ウィンドウの下に隠れます</strong>。

```text
  ┌─────────────────────────┐
  │ ビューポート               │
  │   ┌─────────┐ ← WPF の   │
  │   │ ツール    │   オーバーレイを│
  │   │ バー      │   置いても、  │
  │   └─────────┘   隠れる    │
  └─────────────────────────┘
```

| 影響 | 対処 |
| --- | --- |
| ビューポートの上に、ボタンや文字を重ねられない | 重ねたいものは、ビューポートの<strong>外</strong>（上のツール バー、下のステータス）に置く |
| 半透明のパネルや角丸にできない | 諦める。または、エンジンが直接描く（ImGui など）。第 33 章でギズモを扱う |
| ポップアップ、メニュー、ツール チップ | これらは<strong>独立したウィンドウ</strong>なので、ビューポートの上に出る（問題ない） |
| ドラッグ中のアニメーション、トランジション | ビューポートの領域では、WPF のアニメーションが効かない |
| 画面のキャプチャ | 一部のキャプチャ ツールで、子ウィンドウが写らないことがある |

「エアスペース」という名前は、<strong>1 つのピクセルを、WPF と Win32 のどちらか一方しか所有できない</strong>（空間を共有できない）ことに由来します。

### 短所：その他

- DPI（画面の拡大率）の扱いに注意が必要（第 31 章）。
- WPF のレイアウトが変わったとき、子ウィンドウの位置と大きさを、<strong>自分で更新</strong>しないといけない（`HwndHost` が、大部分を自動で行う）。
- フォーカスやキーボード入力の橋渡しが必要（`IKeyboardInputSink`）。

## 方式 B：D3DImage（WPF のテクスチャとして渡す）

### 仕組み

`D3DImage` は、WPF が持つ<strong>画像の種類</strong>の 1 つで、<strong>Direct3D 9 のサーフェス</strong>を、WPF の画像として表示できます。WPF の他の部品と<strong>同じ描画面</strong>に合成されるので、<strong>エアスペース問題がありません</strong>。上に何でも重ねられます。

DX12 の場合、D3DImage は D3D9 しか受け取れないので、<strong>橋渡しの連鎖</strong>が必要になります。

```text
DX12 でレンダー ターゲットに描く（共有可能なリソース）
   ↓ 共有ハンドル
D3D11On12 または D3D11（共有テクスチャを開く）
   ↓ 共有ハンドル（レガシー）
D3D9Ex（サーフェスとして開く）
   ↓
D3DImage.SetBackBuffer(…)
```

### 長所

| 長所 | 説明 |
| --- | --- |
| エアスペース問題が無い | WPF のコントロールを、ビューポートの上に自由に重ねられる |
| WPF のレイアウトとの親和性 | 画像のように扱える。拡大縮小、クリップ、変形、不透明度 |
| 画面キャプチャが問題ない | 通常の WPF 部品として写る |

### 短所

| 短所 | 説明 |
| --- | --- |
| <strong>DX12 では、橋が長い</strong> | D3D12 → D3D11 → D3D9 の共有。形式の制約（`B8G8R8A8_UNORM` など）と、同期（フェンス）が複雑 |
| 余計な遅延 | WPF の合成のタイミング（60 Hz 固定）に縛られ、入力から表示までの遅延が増える |
| 同期が難しい | DX12 の GPU 完了と、D3D9 側の読み出しの順序を、自分で保証する必要がある |
| 古い技術に依存 | D3D9 は、メンテナンスのみ。将来のサポートが不安 |
| デバイスの喪失 | ディスプレイ切り替え、スリープなどで D3D9 のデバイスが失われると、作り直す必要がある |
| 性能 | 共有テクスチャのコピーが入ることがある |

### 実装の概略

- DX12 側：レンダー ターゲットを `D3D12_HEAP_FLAG_SHARED` で作り、`CreateSharedHandle` で共有ハンドルを得る。
- D3D11 側：`ID3D11Device1::OpenSharedResource1` で、同じ実体を D3D11 のテクスチャとして開く。さらに、D3D9Ex で開くための<strong>レガシー共有ハンドル</strong>が必要になる場合、`D3D11On12` でラップして共有フラグ付きのテクスチャにコピーする。
- D3D9Ex 側：`IDirect3DDevice9Ex::CreateTexture` に共有ハンドルを渡して、サーフェスを得る。
- WPF 側：`D3DImage.Lock()` → `SetBackBuffer(D3DResourceType.IDirect3DSurface9, surface)` → `AddDirtyRect(…)` → `Unlock()`。

この教材では、<strong>これを実装しません</strong>。仕組みの理解のために、概要だけを知っておきます。

## 方式 C：WriteableBitmap（CPU 経由）

### 仕組み

エンジンが描いた絵を、<strong>GPU から CPU のメモリにコピー</strong>（リードバックと呼ぶ）し、WPF の `WriteableBitmap` のピクセルに書き込みます。

```text
DX12 でオフスクリーンに描く
   ↓ CopyResource（GPU → CPU から読めるバッファー）
フェンスで GPU の完了を待つ
   ↓ Map
CPU のメモリ
   ↓ memcpy
WriteableBitmap.WritePixels(…)
   ↓
WPF が表示
```

### 長所

| 長所 | 説明 |
| --- | --- |
| 実装が最も単純 | 共有リソースも、HWND も要らない。コピーするだけ |
| エアスペース問題が無い | 普通の画像として WPF に載る |
| 技術的な依存が少ない | D3D9 も要らない |

### 短所

| 短所 | 説明 |
| --- | --- |
| <strong>遅い</strong> | 1280×720（約 3.7MB）を毎フレームコピー。60 fps で約 220MB/s。解像度が上がると急に厳しい（4K で約 1.9GB/s） |
| 遅延が大きい | GPU の完了を待つので、パイプラインが止まる |
| CPU の負荷が高い | コピーと変換（色の並び）が、毎フレーム |
| HDR 非対応 | 8 ビットの画像として扱う |

### 向いている場面

- 静止画のサムネイル（マテリアルのプレビュー、アセットのアイコン）を作るとき。
- 低い更新頻度のプレビュー。
- テスト、スクリーンショットの保存。

エディタのメインのビューポートには向きません。

## 方式 D：別ウィンドウを重ねる

### 仕組み

エンジンは<strong>独立した最上位ウィンドウ</strong>（または `SetParent` で親を変えたウィンドウ）に描き、エディタの特定の位置に、<strong>位置とサイズを合わせて</strong>重ねます。

### 長所と短所

| | |
| --- | --- |
| 長所 | 独立しているので、エンジンの描画が WPF に影響されない。マルチ モニターで、別のモニターに出すのも簡単 |
| 短所 | エディタのウィンドウを動かすたびに、位置を追従させる必要がある。重なりの順序（Z オーダー）、フォーカス、最小化、タスク バーの扱いなどが、すべて自前。エアスペース問題も残る |

`HwndHost` は、これを<strong>正式な方法で</strong>行うものなので、特別な理由がなければ、方式 A を選びます。

## 方式 E：その他

| 方式 | 内容 | この教材 |
| --- | --- | --- |
| <strong>DirectComposition</strong> | DWM の合成機能を直接使い、WPF の描画面と DX12 のスワップ チェーンを、同じ合成ツリーに入れる。エアスペースを避けられる | 実装が高度で、WPF 側の対応が限定的。扱わない |
| <strong>WinUI 3 の `SwapChainPanel`</strong> | WinUI 3（WPF の後継）の部品。DX12 のスワップ チェーンを、そのまま XAML に埋め込める。エアスペースが無い | WPF ではない。参考として知っておく |
| <strong>別プロセスのエンジン</strong> | エンジンを別 EXE にし、共有メモリや共有テクスチャで絵を受け取る | 複雑。扱わない |
| <strong>WebView2 + ストリーミング</strong> | エンジンの絵を、映像として配信 | 遅延が大きく、扱わない |

## 比較表

| 観点 | A: HwndHost | B: D3DImage | C: WriteableBitmap | D: 別ウィンドウ |
| --- | --- | --- | --- | --- |
| 実装の難しさ | <strong>低〜中</strong> | <strong>高</strong>（D3D12 → 11 → 9 の連鎖） | 低 | 中 |
| 描画の速さ | <strong>◎</strong> | ○（共有の同期あり） | ×（コピー） | ◎ |
| 入力から表示までの遅延 | <strong>小</strong> | 中（WPF の 60 Hz に縛られる） | 大 | 小 |
| エアスペース問題 | <strong>あり</strong> | <strong>なし</strong> | なし | あり |
| WPF の部品を重ねる | ×（外に置く） | ○ | ○ | × |
| DX12 との相性 | <strong>◎</strong>（そのまま） | △（橋が必要） | ○（リードバック） | ◎ |
| 将来性 | ○ | △（D3D9 依存） | ○ | △ |
| 高解像度・高 fps | ◎ | ○ | × | ◎ |
| 使われ方 | 多くの商用ツール | 一部の WPF + D3D アプリ | サムネイル、簡易プレビュー | ツールのサブウィンドウ |

## この教材の選択

| 用途 | 方式 |
| --- | --- |
| <strong>メインの 3D ビューポート</strong> | <strong>A: HwndHost</strong>（第 31 章） |
| アセットのサムネイルなど、小さな静止画 | C: 方式を応用（第 40 章。必要なら） |
| エアスペースで困った場合 | ビューポートの外に UI を置く。ギズモなどはエンジンが直接描く（第 37 章）。透過が必要な表示は、ビューポートの上に<strong>独立した透明ウィンドウ</strong>を重ねる |

<strong>A を選ぶ理由</strong>は 3 つです。

1. <strong>DX12 の作りを、変えずに使える</strong>。第 3〜4 章で作った `Engine` と Player の関係が、そのまま、HwndHost に引き継がれる。
2. <strong>性能と遅延が良い</strong>。3D エディタの操作感（カメラの回転、オブジェクトのドラッグ）に直結する。
3. <strong>多くのツールで実績がある</strong>。問題が起きても、情報が多い。

エアスペース問題は、<strong>UI の置き方で避けられる</strong>ものであり、エディタという用途では大きな制約になりません。

## エアスペースを避ける設計の指針

| 指針 | 内容 |
| --- | --- |
| ビューポートは、四角い領域だけ | 角丸や、変形、半透明のパネルを重ねない |
| ツール バーは、ビューポートの上や横 | ビューポートの<strong>外側の行</strong>に置く |
| 情報の表示は、エンジンが描く | FPS やギズモは、エンジン側で描く（デバッグ描画） |
| ポップアップは、使える | `ContextMenu`、`ToolTip`、`Popup` は独立したウィンドウなので、ビューポートの上に出る |
| ドラッグ アンド ドロップは、`HwndHost` で受ける | アセットをビューポートへドロップする処理は、子ウィンドウで受ける（第 40 章） |
