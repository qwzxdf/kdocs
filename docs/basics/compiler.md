# コンパイラとビルドの仕組み

C++ のソースコードは、**そのままでは動きません**。コンパイラが機械が実行できる命令に変換し、リンカーがそれらをつなげて、実行ファイル（`.exe`）を作ります。この一連の流れ（ビルド）を知っていると、エラーメッセージが読め、ビルドが遅い理由が分かり、最適化やデバッグの設定が理解できます。このページは、コンパイラが何をするのか、ビルドの段階、MSVC・Clang・GCC の違い、よく使う設定をゼロから説明します。

!!! tip "ポイント"
    - <strong>ビルド ＝ プリプロセス → コンパイル → リンク</strong>の 3 段階。<strong>各 `.cpp` が、別々に、コンパイルされる</strong>。
    - 翻訳単位（translation unit）＝ 1 つの `.cpp` と、それが `#include` したもの全部。コンパイルの単位。
    - コンパイル エラーは文法や型の間違い（`C2xxx`）、リンク エラーは定義が見つからない・重複（`LNK2xxx`）。
    - Visual Studio のコンパイラは MSVC（`cl.exe`）。Clang や GCC もある（同じ C++ でも、細かな違いがある）。
    - 最適化の設定で、同じコードが数倍〜数十倍、速さが変わる（Debug と Release）。
    - 警告は、バグの手がかり。`/W4` で、警告を多めに出す。

## コンパイラとは

**コンパイラ**は、人が書いたソースコードを CPU が実行できる機械語に翻訳するプログラムです。

```text
ソースコード（.cpp / .h）
      ↓ コンパイラ
機械語（オブジェクトファイル .obj）
      ↓ リンカー
実行ファイル（.exe）
```

| 道具 | 役割 |
| --- | --- |
| プリプロセッサ | `#include` や `#define` を文字列として処理する（コンパイルの前） |
| コンパイラ | C++ の文法に従って、機械語（`.obj`）に翻訳する |
| アセンブラ | （内部で）アセンブリ言語を機械語にする |
| リンカー | 複数の `.obj` とライブラリを 1 つにつなぐ |

Visual Studio の「ビルド」ボタンは、これらをまとめて実行します。

### 1. プリプロセス

**ソースコードを文字列として、加工**します（コンパイルの前）。

| 処理 | 内容 |
| --- | --- |
| `#include "x.h"` | `x.h` の中身をその場所にそのまま貼り付ける |
| `#define` | マクロの置き換え（`#define N 10` → `N` が `10` に） |
| `#if` / `#ifdef` | 条件によって、コードを残す・消す |
| コメントの削除 | コメントは、ここで消える |

プリプロセスの結果（`.i` ファイル）は、何千行にもなることがあります。ヘッダの中身が全部貼り付くためです（[ビルド時間の最適化](../optimize/build-time.md)）。

### 2. コンパイル

プリプロセスされたコードを文法に従って、解析して、機械語に翻訳します。

| 段階 | 内容 |
| --- | --- |
| 字句解析・構文解析 | コードをトークンに分け、文法の木にする（ここで文法エラーを見つける） |
| 意味解析 | 型の整合性、名前の解決（変数がどこで宣言されたか）、オーバーロードの選択、テンプレートの展開 |
| 最適化 | コードを速く・小さく書き換える（[コンパイラの最適化](../optimize/compiler.md)） |
| コード生成 | CPU の命令（機械語）を出力 |

出力は、`.obj`（オブジェクトファイル）です。実行はまだできません（他のファイルの関数への呼び出しが、未解決のため）。

### 3. リンク

複数の `.obj` と、ライブラリを 1 つの実行ファイルにつなぎます。

| 処理 | 内容 |
| --- | --- |
| シンボルの解決 | 「この関数を呼んでいる」→「どの `.obj` に、定義があるか」を見つける |
| ライブラリの取り込み | `.lib`（静的ライブラリ）の必要な部分を取り込む。`.dll` は、実行時に読む |
| アドレスの決定 | 各関数・変数の、メモリ上の位置を決める |
| 実行ファイルの生成 | `.exe`・`.dll` を作る |

## 翻訳単位

**コンパイラは、`.cpp` を 1 つずつ、独立して処理**します。1 つの `.cpp` と、それが `#include` した全部を翻訳単位（translation unit）と呼びます。

```text
main.cpp が #include "player.h" → player.h の宣言を、main.cpp の中で見られる
main.cpp は、enemy.cpp の中身を、見ない（宣言だけを頼りに、呼び出しを書く）
```

| 点 | 説明 |
| --- | --- |
| 宣言と定義 | 宣言＝「こういう関数がある」（`void Attack();`）、定義＝「中身」（`void Attack() { ... }`） |
| ヘッダ（`.h`） | 宣言を書いて、複数の `.cpp` で共有する |
| ソース（`.cpp`） | 定義を書く（1 回だけ） |
| リンク時に結びつく | `main.cpp` が呼んだ `Attack` が、`enemy.cpp` の定義にリンカーによってつながる |

### ODR（One Definition Rule：定義は 1 つだけ）

関数や変数の定義は、プログラム全体で、1 つだけです。

| 状況 | 結果 |
| --- | --- |
| 同じ関数を 2 つの `.cpp` で定義 | リンク エラー（`LNK2005`：すでに定義されています） |
| ヘッダに関数の定義を書いて、複数の `.cpp` が include | 同上。`inline` を付ける（複数の定義を許す） |
| 宣言だけで、定義がない | リンク エラー（`LNK2019`：未解決の外部シンボル） |

（[ヘッダとソースの分け方](../design/foundations/header-source.md)、[よくあるエラー](../vs/errors.md)）

## コンパイル エラーとリンク エラー

| 種類 | 出るタイミング | 例 | 原因 |
| --- | --- | --- | --- |
| **コンパイル エラー**（`C2xxx`） | コンパイル中 | `C2065`：宣言されていない識別子 | 文法・型・名前の間違い |
| 警告（`C4xxx`） | コンパイル中 | `C4244`：型変換でデータが失われる | バグの可能性 |
| リンク エラー（`LNK2xxx`） | リンク中 | `LNK2019`：未解決の外部シンボル | 定義がない・ライブラリを指定していない |

### エラーメッセージの読み方

```text
main.cpp(12,5): error C2039: 'Foo': 'Enemy' のメンバーではありません
```

| 部分 | 意味 |
| --- | --- |
| `main.cpp(12,5)` | ファイル・行・列 |
| `error C2039` | エラー番号。検索すると、解説が見つかる |
| メッセージ | 何が問題か |

エラーが大量に出たら、先頭の 1 つを直します（最初のエラーが後ろのエラーを連鎖して起こすことが多い）。テンプレートのエラーは、長いことがあります。最初と最後の数行を読みます。

## コンパイラの種類

| コンパイラ | 提供元 | 主な用途 |
| --- | --- | --- |
| **MSVC**（`cl.exe`） | Microsoft | Visual Studio の標準。Windows のゲーム開発の、中心 |
| Clang（`clang++`） | LLVM プロジェクト | Mac / Linux の標準。警告やエラーが分かりやすい。Visual Studio からも使える（`clang-cl`） |
| GCC（`g++`） | GNU | Linux の標準。多くのプラットフォームに対応 |

同じ C++ のコードでも、コンパイラによって、細かな違いがあります（対応している機能の範囲、警告の出方、最適化の癖）。複数のコンパイラでビルドすると、移植性のバグに早く気づけます。

### Visual Studio での選択

| ツールセット | 説明 |
| --- | --- |
| MSVC（v145 など） | 既定。`cl.exe` |
| LLVM（clang-cl） | Clang を MSVC 互換のコマンドで使う。プロジェクトのプロパティ → 全般 → プラットフォーム ツールセットで、切り替える |
| CMake + Ninja | コンパイラを自由に選べる（[CMake](../vs/cmake.md)、[Ninja](../vs/ninja.md)） |

### コンパイラを手軽に試す（Compiler Explorer）

Compiler Explorer（godbolt.org）は、ブラウザで、コードを書くと、コンパイル結果（アセンブリ）が見えるサイトです。複数のコンパイラ・バージョンを並べて比べられます。このサイトのサンプルコードにも、「Compiler Explorer で開く」ボタンがあります。

## 主なコンパイラの設定（MSVC）

Visual Studio の**プロジェクトのプロパティ**で設定する項目は、コンパイラのオプションとして、渡されます。

| オプション | 意味 | 設定の場所 |
| --- | --- | --- |
| `/std:c++latest`（または `/std:c++23preview`） | C++ の標準のバージョン | C/C++ → 言語 |
| `/O2` / `/Od` | 最適化（速さ優先 / なし） | C/C++ → 最適化 |
| `/W4` | 警告のレベル（4 が詳しい） | C/C++ → 全般 |
| `/WX` | 警告をエラーとして扱う | 同上 |
| `/permissive-` | 標準に厳密（MSVC の独自拡張を無効に） | 言語 |
| `/utf-8` | ソースと実行時の文字コードを UTF-8 | コマンドライン |
| `/MP` | 複数のコアで、並列コンパイル | 全般 |
| `/Zi` | デバッグ情報を作る | 全般 |
| `/MD` / `/MDd` | ランタイム ライブラリ（DLL 版）を使う | コード生成 |
| `/GL` と `/LTCG` | リンク時の最適化 | 最適化・リンカー |
| `/fsanitize=address` | アドレス サニタイザー | 全般（[AddressSanitizer](../vs/asan.md)） |
| `/D マクロ名` | マクロの定義 | プリプロセッサ（[マクロ](../vs/preprocessor.md)） |

（詳しくは、[C++23 を使えるようにする設定](../vs/settings.md)）

### Debug と Release の違い

| | Debug | Release |
| --- | --- | --- |
| 最適化 | なし（`/Od`） | あり（`/O2`） |
| デバッグ情報 | あり（詳しい） | 必要なら、別に |
| 標準ライブラリの検査 | あり（範囲外などを検出）。遅い | なし |
| 速さ | 数倍〜数十倍、遅い | 本番の速さ |
| コードの対応 | 1 行ずつ、ソースと対応（デバッグしやすい） | 並び替え・削除されて、対応しにくい |
| 用途 | 開発・デバッグ | 配布・速度測定 |

速さを測る・配布するのは、Releaseです。

## コンパイラが行う最適化

**コンパイラは、コードを同じ動作のまま、速くなるように書き換えます**。

| 最適化 | 内容 |
| --- | --- |
| 定数畳み込み | **`2 * 3 + 4` を `10` に**（実行時の計算をビルド時に済ませる）（[コンパイル時の計算](../optimize/compile-time.md)） |
| インライン展開 | 関数の呼び出しを中身で置き換える（呼び出しコストの削減、さらなる最適化の足がかり） |
| 不要コードの削除 | 使われない変数・到達しないコードを消す |
| ループ展開 | ループを数回ぶん展開して、分岐を減らす |
| ベクトル化（SIMD） | 配列のループを複数要素を同時に処理する命令に（[SIMD](../optimize/simd.md)） |
| レジスタ割り当て | よく使う値を CPU の高速なレジスタに置く |
| 共通部分式の削除 | 同じ計算を 1 回にまとめる |

「コンパイラに任せられること」と「自分で直さないと、速くならないこと」を区別します（[コンパイラの最適化](../optimize/compiler.md)）。

!!! note "未定義動作（UB）"
    C++ には、「何が起きても、規格が保証しない」操作（未定義動作）があります（配列の範囲外・符号付き整数のオーバーフロー・ヌルポインタの参照など）。コンパイラは、「未定義動作は、起きない」と仮定して、最適化します。UB があると、Debug では動くのに、Release で壊れることが起きます（[未定義動作](ub.md)）。

## 警告を活用する

**警告は、「文法的には正しいが、バグの可能性がある」コード**を教えてくれます。

| よく出る警告 | 意味 |
| --- | --- |
| `C4244` | 型変換で、データが失われる（`double` → `int` など） |
| `C4267` | `size_t` から `int` への変換 |
| `C4100` | 未使用の引数 |
| `C4189` | 未使用のローカル変数 |
| `C4700` | 初期化されていない変数の使用 |
| `C4996` | 非推奨の関数（`strcpy` など） |

| 設定 | 説明 |
| --- | --- |
| `/W4` | 詳しい警告 |
| `/WX` | 警告をエラーに（警告ゼロを保つ） |
| `#pragma warning(disable: 4100)` | 特定の警告を一部だけ無効（理由を書く） |
| `[[maybe_unused]]` | 未使用でも、意図的であることを示す |

警告を放置しないことが、バグを減らします。外部ライブラリのヘッダの警告は、`/external:W0`（外部ヘッダとして扱う）で、消せます（[外部ライブラリの入れ方](../vs/libraries.md)）。

## ビルドを速くする

**ビルドが遅い原因の多くは、ヘッダの読み直し**です（[ビルド時間の最適化](../optimize/build-time.md)）。

| 方法 | 説明 |
| --- | --- |
| 並列コンパイル（`/MP`、Ninja） | コアを全部使う |
| include を減らす | 前方宣言を使う |
| プリコンパイル済みヘッダー | 変わらないヘッダを 1 回だけ解析 |
| テンプレートをヘッダに書きすぎない | コンパイルが重くなる |

## よくあるミス

??? failure "リンク エラー（`LNK2019`）をコンパイル エラーと間違える"
    コンパイルは通っているが、定義がない・ライブラリを指定していない。エラー番号が `LNK` なら、リンクの問題です。

??? failure "ヘッダに関数の定義を書いて、`LNK2005`（多重定義）になる"
    `inline` を付けるか、`.cpp` に移します。

??? failure "Debug で測った速さで、最適化を判断する"
    Release で測ります。

??? failure "警告を無視して、バグを見逃す"
    `/W4` にして、警告をゼロにします。

??? failure "Debug で動くのに、Release で壊れる"
    未定義動作、未初期化変数が疑われます（[未定義動作](ub.md)）。

??? failure "別のコンパイラで、コンパイルが通らない"
    MSVC の独自拡張（`/permissive-` で検出）を使っていないか確認します。
