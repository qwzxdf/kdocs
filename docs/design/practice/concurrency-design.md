# 並行処理の設計

**並行処理**は、複数の処理を**同時に**進める技術です。ゲームでは、「描画」「ゲームの更新」「ファイルのロード」「音の再生」「ネットワーク」を、別々のスレッドで動かすことがあります。うまく使うと、**ロード中も画面が止まらない**、**複数のコアを使って重い処理を速く終わらせる**といった効果があります。ただし、**スレッドは、バグの温床**です。「たまにしか起きない」「デバッグすると消える」バグ（データ競争、デッドロック）が起きやすく、**設計で、そもそも起きにくくしておく**ことが一番大事です。この考え方を、このページでまとめます（仕組みは [並行処理（基礎）](../../basics/concurrency.md) と [thread](../../stl/concurrency/thread.md)・[mutex](../../stl/concurrency/mutex.md) を見てください）。

!!! tip "ポイント"
    - <strong>できるだけスレッドを使わない。</strong> まず 1 スレッドで速くする。必要になってから、分ける。
    - 使うなら、<strong>「共有しない」</strong>設計にする。**共有するデータが少ないほど、バグも少ない**。
    - 共有するなら、**所有者を 1 つのスレッドに決める**。他は**メッセージ（コピー）で伝える**。
    - やむを得ず共有するデータは、**`mutex` で守る**か、**`atomic`** にする。ロックの範囲は**小さく、短く**。
    - **スレッドを手で作り回さず、「ジョブ（仕事）」を、スレッド プールに任せる**。
    - 「**スレッドの境界**」を、設計図に書く（どのデータを、どのスレッドが触るか）。

## 並行処理で起きる問題

| 問題 | 説明 |
| --- | --- |
| **データ競争**（data race） | 2 つのスレッドが、同じデータを**同時に**読み書き（片方は書き込み）する。**未定義動作** |
| **デッドロック** | スレッド A がロック 1 を持ってロック 2 を待ち、B がロック 2 を持ってロック 1 を待つ。永久に止まる |
| **競合状態**（race condition） | 実行の順番しだいで、結果が変わる。たまにしか再現しない |
| **ロックの待ちで遅くなる** | 1 つのロックに、全スレッドが並んで、結局 1 本しか動いていない |
| **false sharing** | 別々の変数でも、同じキャッシュ ラインにあると、スレッドが邪魔しあって遅くなる |

n a スレッドA 0 0
n b スレッドB 2 0
n l1 ロック1 0 1

n l2 ロック2 2 1 hit
l a l1 hit 持つ

</div>

## 設計の基本方針

### 1. 共有しない（一番安全）

**スレッドごとに、自分専用のデータ**を持たせます。データを共有しなければ、データ競争は起きません。

| 方法 | 説明 |
| --- | --- |
| **処理を分割して、データも分割する** | 敵の配列を、前半と後半に分けて、別々のスレッドで更新する（お互いのデータを触らない） |
| **スレッド ローカル**（`thread_local`） | スレッドごとに別の変数を持つ（乱数生成器、一時バッファ） |
| **コピーして渡す** | データをコピーして渡し、渡したら元のスレッドは触らない |
| **結果だけを返す** | 仕事の結果を、`std::future` や、メッセージ キューで受け取る |

### 2. 所有者を決める（メッセージで伝える）

データの持ち主を**1 つのスレッドだけ**にして、他のスレッドは、<strong>メッセージ（依頼）</strong>を送って、頼みます。

<div class="anim" data-type="graph" data-label="メッセージ キュー：所有者に頼む">
n render 描画スレッド 0 0
n queue キュー 2 1
n game ゲームスレッド_持ち主 4 1 hit
# ゲームのデータを持つのは、ゲーム スレッドだけ
---
n render 描画スレッド 0 0 hit
n queue キュー 2 1
n game ゲームスレッド_持ち主 4 1
l render queue hit 頼む
# 他のスレッドは、データを直接触らず、キューに依頼を入れる
---
n render 描画スレッド 0 0
n queue キュー 2 1 hit
n game ゲームスレッド_持ち主 4 1 hit
l queue game hit 取り出す
# 持ち主だけが、キューから取り出して処理する（ロックはキューの中だけ）
</div>

```cpp
// スレッド セーフなメッセージ キュー（簡易版）
template <class T>
class MessageQueue {
 public:
  void Push(T message) {
    {
      std::lock_guard lock(mutex_);
      queue_.push(std::move(message));
    }
    cv_.notify_one();
  }

  std::optional<T> TryPop() {
    std::lock_guard lock(mutex_);
    if (queue_.empty()) {
      return std::nullopt;
    }
    T message = std::move(queue_.front());
    queue_.pop();
    return message;
  }

 private:
  std::mutex mutex_;
  std::condition_variable cv_;
  std::queue<T> queue_;
};
```

| 利点 | 説明 |
| --- | --- |
| **ロックが、キューの中だけ**で済む | 他のコードは、ロックを意識しない |
| **所有者が明確** | データを変更するのは、持ち主のスレッドだけ |
| **デッドロックしにくい** | ロックが 1 つだけ |

### 3. 共有するなら、守る

どうしても共有するなら、次のどれかで守ります。

| 方法 | 使う場面 |
| --- | --- |
| **`std::mutex` + `std::lock_guard`**（[mutex](../../stl/concurrency/mutex.md)） | 複数の値をまとめて守る。基本はこれ |
| **`std::atomic<T>`**（[atomic](../../stl/concurrency/atomic.md)） | 1 つの数値・フラグ（カウンター、終了フラグ）。ロック不要 |
| **`std::shared_mutex`** | 読むのが多く、書くのが少ない（設定など） |
| **不変（読むだけ）にする** | 作り終えたら、**書き換えない**データは、複数のスレッドで読んでよい |
| **ダブル バッファ** | 書く用と読む用の 2 つを持ち、フレームの区切りで入れ替える |

### ロックのルール

| ルール | 理由 |
| --- | --- |
| <strong>ロックは `lock_guard` / `scoped_lock`（RAII）</strong> | 解除し忘れ・例外で外れないのを防ぐ（[RAII](../patterns/raii.md)） |
| **ロックの範囲は短く** | 長いと、他のスレッドが待たされる |
| **ロックを持ったまま、重い処理・I/O・他のロックをしない** | 遅くなる・デッドロックの元 |
| **複数のロックは、いつも同じ順番で取る**（または `std::scoped_lock(a, b)`） | デッドロックを防ぐ |
| **ロックの中から、外のコード（コールバック）を呼ばない** | 外のコードが、さらにロックを取ると、デッドロックする |
| **データと、それを守るロックを、同じクラスにまとめる** | どのロックで守るのか、はっきりする |

## ジョブ システム（仕事をプールに任せる）

スレッドを**自分で作って管理する**と大変です。ゲームでは、**スレッド プール**（決まった数のスレッドが、待機している）に、**ジョブ（小さな仕事）を投げる**設計がよく使われます。

```text
[ジョブ キュー]  ←── 仕事を積む（誰でも）
   ↓
ワーカー スレッド 1, 2, 3 …  ←── 空いたスレッドが、キューから取って実行
```

```cpp
// 例：重い読み込みを、別のスレッドに任せる（std::async）
std::future<Texture> loading = std::async(std::launch::async, [] {
  return LoadTexture("boss.png");       // 別のスレッドで実行
});

// ... ゲームの更新は、止まらず続く ...

if (loading.wait_for(std::chrono::seconds(0)) == std::future_status::ready) {
  Texture texture = loading.get();       // 終わっていれば、受け取る
}
```

| 方法 | 説明 |
| --- | --- |
| **`std::async` / `std::future`** | 1 回きりの仕事の、結果を受け取る（[future](../../stl/concurrency/future.md)） |
| **`std::jthread`** | 長く動くスレッド（ロード用、ネットワーク用） |
| **自作のスレッド プール + ジョブ キュー** | 毎フレーム、細かい仕事を大量に投げる（物理、AI、アニメーション） |
| **ライブラリ**（Intel TBB、OpenMP、`std::execution::par`） | 配列の処理を、並列で分ける（`parallel for`） |

## ゲームでよくあるスレッド構成

| 構成 | 説明 | 難しさ |
| --- | --- | --- |
| **1 スレッド** | すべて、メイン スレッドで | 簡単。まずこれ |
| **メイン + ロード スレッド** | ロード中も、画面（ローディング表示）が止まらない | 易しい（`std::async`） |
| <strong>メイン + ワーカー（ジョブ）</strong> | 物理・AI・アニメーションを、ジョブで並列化 | 中 |
| **ゲーム スレッド + 描画スレッド** | 更新と描画を、1 フレームずらして並行 | 難しい（データの受け渡しの設計が必要） |

### ロードを別スレッドにする（よくある使い方）

| 設計のポイント | 説明 |
| --- | --- |
| ロード スレッドは、**データを作るだけ** | ゲームの状態（シーン、ECS）は、**触らない** |
| 作ったものは、**完成してから、メイン スレッドに渡す** | `future` や、完成キューで |
| **GPU のリソース作成**は、API によって、スレッドの制限がある | DirectX 11 は、デバイス自体はスレッド セーフだが、デバイス コンテキストは単一スレッド。注意 |
| 進み具合は、`std::atomic<float>` で伝える | ロード画面の進捗バー |

## ゲームでの使いどころ

| 場面 | 設計 |
| --- | --- |
| ロード | 別スレッドでデータを作り、メインに渡す |
| 物理・AI | エンティティを分割して、ジョブで並列に。結果をまとめる |
| サウンド | ミキサーは別スレッド。メインからは、キューで「再生して」と頼む |
| ネットワーク | 受信スレッドが、メッセージ キューに積み、メインが読む |
| ログ | ログ スレッドに、メッセージを渡して、ファイルに書く（[ログとデバッグ支援](logging-debug.md)） |
| 描画 | ゲームの状態から、描画用のコマンドを**コピーして**、描画側に渡す |

## よくあるミス

??? failure "「たまにしか起きない」バグを、放っておく"
    データ競争は、動いたり動かなかったりします。**ThreadSanitizer**（Clang / GCC）や、Visual Studio の診断ツールで、競合を探します。

??? failure "`std::thread` を、`join` / `detach` せずに破棄する"
    `std::thread` のデストラクタは、**join も detach もされていないと `std::terminate`**（プログラムの強制終了）です。`std::jthread`（デストラクタで `join`）を使います。

??? failure "ロックの範囲が広い"
    関数全体をロックすると、他のスレッドが長く待たされます。**共有データに触る、ほんの一部**だけをロックします。

??? failure "スレッドの中で、ラムダが消えたローカル変数を参照する"
    `[&]` で、すぐに消える変数を借りたラムダを、別スレッドで実行すると、ダングリングです。コピーキャプチャ（`[=]`、`[x = std::move(x)]`）にします（[所有権とライフタイム設計](../foundations/ownership-lifetime.md)）。

??? failure "ロックを取る順番がバラバラ"
    スレッドごとに違う順番でロックを取ると、デッドロックします。**常に同じ順番**にするか、`std::scoped_lock(a, b)` を使います。

??? failure "最適化のために、最初からマルチスレッドにする"
    マルチスレッドは、複雑さが大きく増えます。**1 スレッドで、アルゴリズムとデータの並びを直してから**考えます（[パフォーマンス設計](performance-design.md)）。

## これだけ覚える

!!! abstract "まとめ"
    - [x] まず 1 スレッド。スレッドは、必要になってから
