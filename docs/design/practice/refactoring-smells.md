# リファクタリングとコードの臭い

**リファクタリング**は、プログラムの動きを変えずに、中の作りを読みやすく・直しやすく整えることです。機能を足すのではなく、散らかった部屋を片付けるようなものです。ゲームは作りながら仕様が変わるので、コードは必ず散らかっていきます。放っておくと、「触るのが怖い」「どこを直せばいいか分からない」コードになります。そこで「このコードは直したほうがいい」というサイン（コードの臭い：Code Smell）を見つける目と安全に直す手順を知っておくと、ゲームを長く作り続けられます。

!!! tip "ポイント"
    - リファクタリングは、**動きを変えない**。**機能追加とは別の作業**として、別のコミットにする。
    - 小さな手順を、1 つずつ。1 手順ごとに動くことを確認する。
    - 直す前に動きを確かめる方法（テスト、または決まった手順での確認）を用意する。
    - 「臭い」は、悪いコードの証拠ではなく、見直すサイン。全部を直す必要はない。
    - 触るついでに直す（ボーイスカウトの規則：来たときより、きれいにして帰る）。

## 安全なリファクタリングの手順

```text
① 動きを確認する方法を用意する（テスト、または「このステージを遊んで、こうなる」）
② 小さな 1 手を加える（名前を変える、関数に切り出す、…）
③ ビルドして、動きを確認する
④ OK ならコミットする（ダメなら元に戻す）
⑤ ②へ戻る
```

| 心得 | 理由 |
| --- | --- |
| **小さく刻む** | 失敗したときに原因が 1 手に絞れる |
| 機能追加と混ぜない | 動きが変わったとき、リファクタリングのせいか、機能のせいか分からなくなる |
| こまめにコミット | いつでも前の状態に戻れる |
| テストが無ければ、先に簡単なテストを書く | 壊したことに気づける（[テスト容易性の設計](../foundations/testability.md)） |
| IDE の機能を使う | Visual Studio の「名前の変更（Ctrl + R, R）」「メソッドの抽出」は、安全（[便利な機能](../../vs/tips.md)） |

## コードの臭いの一覧

「コードの臭い」（code smell）は、Martin Fowler の『リファクタリング』で広まった言葉で、バグそのものではなく、**将来バグや読みにくさを生みやすい書き方の兆候**のことです。臭いがあるからといって、すぐに直す必要はありません。「ここは触るときに困りそうだ」というサインとして覚えておき、そのコードに手を入れる機会（機能追加やバグ修正）が来たときに、ついでに直すのが現実的です。

以下では、ゲームのコードで特によく出会う 12 の臭いを、見分け方・困ること・直し方の順に説明します。

### 1. 長すぎる関数

| 見分け方 | 画面に収まらない。コメントで「ここから〜」と区切っている |
| --- | --- |
| 困ること | 全体が把握できない。変更が怖い。一部だけ再利用できない |
| 直し方 | 関数の抽出：まとまりごとに名前を付けた関数に切り出す |

```cpp
// 前：1 つの関数が、全部をやっている
void Update(float dt) {
  // --- 入力 ---
  // （30 行）
  // --- 移動 ---
  // （40 行）
  // --- 当たり判定 ---
  // （50 行）
}

// 後：やることが、名前で読める
void Update(float dt) {
  HandleInput();
  Move(dt);
  CheckCollisions();
}
```

### 2. マジックナンバー

| 見分け方 | コードの中に意味の分からない数字が直接ある（`if (hp < 30)`、`speed * 0.7f`） |
| --- | --- |
| 困ること | 数字の意味が分からない。同じ数字が何か所にもあり、直し漏れる |
| 直し方 | 名前付きの定数にする（`constexpr`）。調整する値はデータファイルへ |

```cpp
// 前
if (player.hp < 30) { ShowWarning(); }
velocity *= 0.7f;

// 後
constexpr int kLowHpThreshold = 30;
constexpr float kWaterSpeedRate = 0.7f;
if (player.hp < kLowHpThreshold) { ShowWarning(); }
velocity *= kWaterSpeedRate;
```

### 3. 重複したコード（コピペ）

| 見分け方 | ほぼ同じコードが何か所にもある |
| --- | --- |
| 困ること | 直すときに全部を直さないといけない。1 か所直し忘れて、バグになる |
| 直し方 | 共通の関数に切り出す。違う部分は引数にする |

### 4. 巨大なクラス（神クラス）

| 見分け方 | メンバ変数が 20 個以上、関数が 50 個以上。`GameManager` のような名前 |
| --- | --- |
| 困ること | 何でも屋で変更の影響範囲が広い。テストできない |
| 直し方 | 責任ごとにクラスを分ける（単一責任）。コンポーネントに分ける（[設計の基本原則](../foundations/principles.md)） |

### 5. 引数が多すぎる関数

| 見分け方 | 引数が 5 個以上。`Spawn(x, y, z, hp, speed, type, team, ...)` |
| --- | --- |
| 困ること | 順番を間違える。意味が分からない。増えるたびに全部を直す |
| 直し方 | 引数を構造体にまとめる（`SpawnParams`）。名前付きで渡せる |

```cpp
struct SpawnParams {
  Vec3 position;
  int hp = 10;
  float speed = 1.0f;
  Team team = Team::kEnemy;
};
Spawn({.position = {1, 0, 2}, .hp = 30});   // C++20 の指示付き初期化：名前で分かる
```

### 6. 深い入れ子（`if` のピラミッド）

| 見分け方 | `if` や `for` が 4 段以上ネストしている |
| --- | --- |
| 困ること | 読み進めるのに頭の中で条件を積む必要がある |
| 直し方 | 早期リターン（ガード節）、条件を関数に切り出す |

```cpp
// 前
void Attack(Enemy* e) {
  if (e) {
    if (e->IsAlive()) {
      if (InRange(e)) {
        e->TakeDamage(10);
      }
    }
  }
}

// 後：条件に合わないものを、先に返す
void Attack(Enemy* e) {
  if (!e || !e->IsAlive() || !InRange(e)) {
    return;
  }
  e->TakeDamage(10);
}
```

### 7. 分かりにくい名前

| 見分け方 | `data`、`tmp`、`flag`、`DoStuff`、`a`、`b`。略語だらけ |
| --- | --- |
| 困ること | 読む人が毎回、中身を読んで意味を推測する |
| 直し方 | 意図を表す名前に変える（[命名](../foundations/naming.md)）。一番安全で効果が大きい |

### 8. コメントで説明しないと分からない

| 見分け方 | 「// ここで敵の体力を減らす」のようにコードの説明をコメントが補っている |
| --- | --- |
| 困ること | コメントがコードと食い違っていく |
| 直し方 | コードをコメントがいらない形にする（名前を付けた関数・変数）。コメントは「なぜ」だけ書く |

### 9. 他のクラスのデータばかり触る（機能の羨望）

| 見分け方 | `a.GetX() * a.GetY() + a.GetZ()` のように他のクラスの値を取り出して計算ばかりしている |
| --- | --- |
| 困ること | データと処理が離れている。変更が散らばる |
| 直し方 | 処理をデータを持つクラスに移す（`a.Volume()`） |

### 10. `switch` / `if` の連鎖

| 見分け方 | 敵の種類で `switch` して、同じ分岐があちこちにある |
| --- | --- |
| 困ること | 種類を足すたびに全部の `switch` を直す |
| 直し方 | 仮想関数・[ストラテジー](../patterns/strategy.md)・[ステートマシン](../patterns/state-machine.md)・データ駆動にする |

### 11. グローバル変数・シングルトンだらけ

| 見分け方 | `g_` で始まる変数、`Xxx::Instance()` が、あちこちに出る |
| --- | --- |
| 困ること | どこで書き換わるか分からない。テストできない |
| 直し方 | 引数やコンストラクタで渡す（[依存性の注入](../patterns/dependency-injection.md)） |

### 12. 使っていないコード（デッドコード）

| 見分け方 | 呼ばれない関数、コメントアウトされた古いコード、使わない変数 |
| --- | --- |
| 困ること | 読む人を混乱させる。「消していいのか」分からず、残り続ける |
| 直し方 | 消す。Git に履歴があるので、戻せる |

## よく使うリファクタリング（技）

| 技 | 内容 |
| --- | --- |
| **名前の変更** | 意図が伝わる名前に（IDE の機能で全部まとめて） |
| 関数の抽出 | まとまった処理を名前を付けた関数に |
| 変数の抽出 | 複雑な式を名前を付けた変数に（`bool is_critical = roll < rate;`） |
| インライン化 | 意味のない小さな関数・変数を使っている場所に戻す |
| 引数オブジェクト | 引数をまとめて構造体に |
| 関数の移動 | 処理をデータのあるクラスへ |
| クラスの抽出 | 1 つのクラスの一部を、新しいクラスに |
| 条件の分解 | `if` の条件・本体を関数に |
| ガード節 | 例外的なケースを先頭で `return` |
| マジックナンバーを定数に | 名前付きの `constexpr` に |
| ポリモーフィズムで置き換える | `switch` を仮想関数に |

## ゲームのリファクタリングの進め方

| 場面 | 進め方 |
| --- | --- |
| **プロトタイプが動いた直後** | 一度、全体を見て、名前・重複・長い関数を整理する（仕様が固まる前に作り込みすぎない） |
| 機能を足す前 | 足しにくいなら、先に足しやすい形に直してから足す |
| バグを直す前 | 原因の関数が読めないなら、先に整理して、バグを見つけやすくする |
| 仕様が固まった後 | 設計を見直し、レイヤーやパターンを取り入れる |
| 締め切り前 | 触らない。動いているものを壊さない |

## ゲームでの使いどころ

| よくある臭い | 直し方 |
| --- | --- |
| `Update()` が 500 行 | 入力・移動・AI・当たり判定の関数に分ける。さらにコンポーネントに |
| 敵の種類ごとの `switch` が、あちこちに | データ（JSON）と、行動を差し替える部品に |
| 数字（ダメージ、速度）がコードに埋まっている | 設定ファイル（データ）へ |
| `Player` が描画・音・入力・保存まで知っている | 役割ごとのクラス・コンポーネントに |
| `g_game` というグローバルを、どこからでも使う | 必要なものを引数で渡す |

## よくあるミス

??? failure "動きを変えてしまう"
    リファクタリングのつもりで、仕様を変えるとバグになります。「動きを変えない」と決めて、**機能の変更は別の作業**にします。

??? failure "一度に、大きく直す"
    大きな書き換えは、途中で動かなくなり、戻れません。小さな手順に分けて、毎回動かします。

??? failure "テストも確認もなしで直す"
    壊したことに気づけません。直す前に動きを確認する方法（簡単なテスト、手順）を用意します。

??? failure "完璧を目指しすぎる"
    リファクタリングは終わりがありません。触る場所と困っている場所だけを直します。

??? failure "締め切り前に大きな整理をする"
    リリースの直前は、リスクが大きいです。ひとまず動かして、余裕ができたあとに整理します。
