# パフォーマンス設計

!!! info "詳しくは「最適化」へ"
    計測の方法、キャッシュ、メモリ確保、SIMD、マルチスレッド、描画、ロードなどの**具体的な最適化**は、[最適化](../../optimize/index.md) のカテゴリにまとめています。このページは、設計の面から見た、速さの考え方の入口です。

ゲームは<strong>毎秒 60 回（1 フレーム約 16 ミリ秒）</strong>、すべての処理を終える必要があります。1 フレームでも間に合わないと、画面がカクつきます。**パフォーマンス（速さ）は、あとから部分的に直すより、最初の設計で決まる部分が大きい**です。ただし、**やみくもに速くしようとすると、読みにくいだけで効果のないコード**になります。大事なのは、「**どこが遅いかを測ってから**、**効果の大きい順に**直す」ことと、「**最初から遅くなりにくい設計**にしておく」ことです。このページは、**メモリ確保、キャッシュ、コピーとムーブ、アルゴリズム**の 4 つの観点で、速さを設計に組み込む考え方をまとめます。

!!! tip "ポイント"
    - <strong>推測で最適化しない。</strong> **計測（プロファイラー）→ 一番遅い所を直す → また計測**。
    - 効果が大きい順は、**アルゴリズム（計算量）→ メモリの並び（キャッシュ）→ メモリ確保 → コピー → 細かい書き方**。
    - **毎フレーム何千回も呼ぶ所**だけ、気にする。1 回だけの処理は、読みやすさを優先する。
    - **連続したメモリ**（`vector`）に、**同じ種類のデータを並べる**と、速い。
    - 毎フレームの **`new` / `delete`、`vector` の作り直しを避ける**（使い回す）。
    - <strong>デバッグ ビルドで速さを測らない。</strong> 必ず **Release** で。

| 手順 | やること |
| --- | --- |
| ① 計測する | どこが遅いか（Visual Studio の「パフォーマンス プロファイラー」） |
| ② アルゴリズム | O(n²) を、O(n log n) や O(n) に |
| ③ データの並び | キャッシュに優しく（連続・同じ種類を並べる） |
| ④ メモリ確保 | 使い回す、プール、`reserve` |
| ⑤ コピー | `const&`、ムーブ、`string_view` |
| ⑥ 細かい書き方 | 最後。効果は小さいことが多い |

| 観点 | 効果の大きさ | 例 |
| --- | --- | --- |
| <strong>アルゴリズム（計算量）</strong> | とても大きい | 当たり判定を、全員総当たりから空間分割に（[O(n²)](../../basics/big-o.md#on2) → O(n)） |
| <strong>メモリの並び（キャッシュ）</strong> | 大きい | 配列の構造体を、種類ごとの配列に |
| **メモリ確保** | 中〜大 | 毎フレームの `new` を、使い回しに |
| **コピー** | 中 | 大きなオブジェクトの値渡しを、参照に |
| **細かい書き方** | 小 | `i++` と `++i` の違い、など |

## 1. 計測する

<strong>一番大事です。</strong> 人間の「ここが遅そう」という勘は、よく外れます。

| 道具 | 使い方 |
| --- | --- |
| **Visual Studio のパフォーマンス プロファイラー**（Alt + F2） | 「CPU の使用率」で、**どの関数が、全体の何 % を占めるか**を見る。**Release** ビルドで |
| **フレーム時間の表示** | 画面に、1 フレームの時間（ミリ秒）を出す（[Dear ImGui](../../libs/imgui/index.md) のグラフが便利） |
| **自作のタイマー** | `ScopedTimer`（[RAII](../patterns/raii.md)）で、区間の時間を測る |
| **Tracy / Superluminal** | ゲーム向けのプロファイラー。フレームごとの流れが見える |

```cpp
// 区間の時間を測る RAII のタイマー
class ScopedTimer {
 public:
  explicit ScopedTimer(const char* name) : name_(name), start_(std::chrono::steady_clock::now()) {}
  ~ScopedTimer() {
    auto elapsed = std::chrono::steady_clock::now() - start_;
    std::println("{}: {:.3f} ms", name_, std::chrono::duration<double, std::milli>(elapsed).count());
  }

 private:
  const char* name_;
  std::chrono::steady_clock::time_point start_;
};

void Update() {
  ScopedTimer timer("Update");   // この関数の時間を測る
  // ...
}
```

## 2. キャッシュに優しいデータの並び

CPU は、メモリから**遠くのデータを読むのが、とても遅い**ので、近くのデータを**キャッシュ**（高速な小さな置き場）に先に取り込みます。**連続して並んだデータは、一気に取り込める**ので速く、**あちこちに散らばったデータは、そのたびに遅い読み込み**が起きます（[キャッシュ効率](../../basics/cache.md)）。

### 悪い例：オブジェクトのポインタの配列

```cpp
std::vector<std::unique_ptr<Enemy>> enemies;   // 敵がヒープのあちこちに散らばる
for (auto& e : enemies) {
  e->position += e->velocity * dt;             // 1 体ごとに、遠いメモリを読みに行く
}
```

### 良い例：データを連続して並べる

```cpp
std::vector<Enemy> enemies;                    // 敵のデータが、連続して並ぶ
for (Enemy& e : enemies) {
  e.position += e.velocity * dt;               // 次のデータは、すぐ隣にある
}
```

<div class="anim" data-label="連続したメモリ：キャッシュ ラインにまとめて載る">
A B C D E F G H # 連続した配列：8 個が、近くに並ぶ
*A *B *C *D E F G H # 1 回の読み込み（キャッシュ ライン 64 バイト）で、4 個を一度に取り込む
*A *B *C *D *E *F *G *H # 次の読み込みで、残りも一度に。速い
</div>

### 構造体の配列（AoS）と、配列の構造体（SoA）

```cpp
// AoS：1 体ぶんのデータが、まとまっている
struct Enemy { Vec3 position; Vec3 velocity; int hp; std::string name; /* ... */ };
std::vector<Enemy> enemies;

// SoA：項目ごとに、別の配列
struct Enemies {
  std::vector<Vec3> position;
  std::vector<Vec3> velocity;
  std::vector<int> hp;
};
```

| 並べ方 | 向いている処理 |
| --- | --- |
| **AoS**（構造体の配列） | 1 体の全部の項目を、まとめて使う処理 |
| **SoA**（配列の構造体） | 一部の項目だけを、全員に対して処理する（「全員の位置を、速度で更新」） |

位置と速度だけが欲しい処理で、AoS だと**使わない `name` や `hp` まで一緒に読み込まれる**ので、キャッシュが無駄になります。SoA なら、必要な項目だけが連続して並びます。これを徹底した設計が、[ECS](../patterns/ecs.md) と [データ指向設計](../patterns/data-oriented.md) です。

### キャッシュに優しくするコツ

| コツ | 説明 |
| --- | --- |
| **`vector` を使う** | 連続して並ぶ。`list` や `map` は、要素がバラバラで遅い |
| **ポインタをたどる回数を減らす** | `unique_ptr<T>` の配列より、`T` の配列 |
| **構造体を小さくする** | 使わないメンバを減らす。`bool` を並べて、パディングを減らす |
| **熱いデータと冷たいデータを分ける** | 毎フレーム使うもの（位置）と、たまにしか使わないもの（名前）を分ける |
| **処理を、種類ごとにまとめる** | 同じ処理を、同じ種類のものに連続して行う（命令のキャッシュにも優しい） |
| **配列を順に読む** | ランダムに飛ばず、前から順に |

## 3. メモリ確保を減らす

`new`、`malloc`、`vector` や `string` の拡張は、**1 回が遅く、時間も一定ではない**（[アロケータ](../../stl/memory/allocator.md)）。毎フレーム何度も呼ぶと、カクつきの原因になります。

| 方法 | 説明 |
| --- | --- |
| **`reserve` で、先に容量を確保** | `push_back` の再確保をなくす（[vector](../../stl/containers/vector.md#reserve)） |
| **メンバに持って、使い回す** | `clear()` で空にしても、容量は残る。毎フレーム新しく作らない |
| **オブジェクトプール** | 作っては消すもの（弾、パーティクル）を、使い回す（[オブジェクトプール](../patterns/object-pool.md)） |
| **フレーム用のアリーナ** | 1 フレームだけ使う一時データを、積むだけの領域から取り、フレームの最後に一括解放（[std::pmr](../../stl/memory/pmr.md)） |
| **スタックを使う** | 小さくて、大きさが決まっているものは、`std::array`（スタック）。ヒープより速い |
| **文字列の連結を避ける** | `s += ...` の繰り返しは、再確保が多い。`reserve`、`std::format_to` |

```cpp
// 悪い：毎フレーム、vector を作る
void Update() {
  std::vector<int> nearby;           // 毎フレーム、確保と解放
  FindNearby(nearby);
}

// 良い：メンバに持って、使い回す
class Scene {
  std::vector<int> nearby_;          // 容量が残る
  void Update() {
    nearby_.clear();                  // 空にするだけ（解放しない）
    FindNearby(nearby_);
  }
};
```

## 4. コピーを減らす

| 方法 | 説明 |
| --- | --- |
| **`const T&` で渡す** | 大きいものを、コピーしない（[const と引数の渡し方](../foundations/const-and-passing.md)） |
| **`string_view` / `span`** | 文字列・配列を、コピーせずに見る |
| **ムーブ** | 持ち主を移す。コンテナに入れるときは `std::move` / `emplace_back`（[ムーブ](../../basics/move.md)） |
| **値で返す** | RVO・ムーブで、コピーは起きない。`const` 参照を返して、危険を作らない |
| **範囲 for は `const auto&`** | `for (auto e : enemies)` は、1 体ずつコピー |

## 5. アルゴリズムを見直す

| よくある遅さ | 直し方 |
| --- | --- |
| 全員 × 全員の当たり判定（O(n²)） | **空間分割**（グリッド、四分木、BVH）で、近いものだけ調べる |
| ループの中で、毎回 `find`（O(n)） | `unordered_map` / `set` で引く、または、先に並べる |
| ループの中で、毎回 `vector::erase`（O(n)） | `erase_if`、または「swap して `pop_back`」（[erase_if](../../stl/algorithms/erase_if.md)） |
| 毎フレーム全体を `sort` | 変わったときだけ。ほぼ整列済みなら、挿入ソート |
| 同じ計算を、毎フレーム繰り返す | **キャッシュ**する。変わったときだけ再計算（ダーティ フラグ） |
| 文字列で比較する | ID（整数）にする |

## 6. マルチスレッドと分割

1 フレームの処理が重いとき、**複数のコアに分けて並列に**行う方法もあります。ただし、**難しく、バグも増える**ので、**1 スレッドで、ここまで速くしてから**考えます（[並行処理の設計](concurrency-design.md)）。

## 最適化してはいけない場所

| 場面 | 理由 |
| --- | --- |
| 1 回だけ実行される処理（初期化） | 速くしても、効果が見えない |
| 計測で遅くないと分かっている所 | 読みにくくなるだけ |
| デバッグ ビルドの速さ | Debug は最適化されていない。製品の速さではない |

「**早すぎる最適化は、諸悪の根源**」（ドナルド・クヌース）。**まず分かりやすく書き、遅い所だけ直す**のが基本です。

## ゲームでの使いどころ

| 場面 | 設計 |
| --- | --- |
| 大量の弾・パーティクル | 連続した配列 + オブジェクトプール。種類ごとに処理 |
| 当たり判定 | 空間分割。静止物は、最初に 1 回だけ構築 |
| AI の更新 | 全員を毎フレーム更新せず、**数フレームに 1 回**、グループに分けて更新する |
| 描画のデータ | 毎フレームの描画コマンドは、フレーム用アリーナに積む |
| 文字列（名前） | 実行時には ID（ハッシュ）を使い、文字列は、デバッグ用にだけ持つ |
| ロード時間 | 起動時にまとめて確保。ロード中に作った大きな JSON を、バイナリ化（[シリアライズ](../../engine/serialization/index.md)） |

## よくあるミス

??? failure "Debug ビルドで速さを測る"
    Debug は最適化が無効で、標準ライブラリの検査も入り、数倍〜数十倍遅くなります。**Release で測ります**。

??? failure "計測せずに、「ここが遅いはず」と最適化する"
    実際のボトルネックは、別の場所にあることがほとんどです。プロファイラーで、**一番時間を使っている関数**を見ます。

??? failure "平均だけを見る"
    ゲームで大事なのは、**最悪のフレーム**（たまに起きる遅いフレーム）です。平均が 5 ms でも、たまに 50 ms の遅いフレームがあれば、カクつきます。フレーム時間の**グラフ**を見ます。

??? failure "細かい書き方を気にしすぎる"
    `i++` を `++i` にする、`inline` を付ける、といった工夫は、現代のコンパイラが自動でやります。**アルゴリズムとデータの並び**を見直すほうが、桁違いに効きます。

??? failure "速さのために、読めないコードにする"
    10% 速くなるために、メンテナンスできないコードにすると、後で必ず困ります。**ボトルネックだけ**を最適化し、理由をコメントに残します。
