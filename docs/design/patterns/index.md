# デザインパターン早見表

**デザインパターン**は、「こういう困りごとには、こういう形で書くとうまくいく」という、先人の経験をまとめた設計の型です。覚えるものではなく、困ったときに「あの型が使えるかも」と思い出すためのものです。このカテゴリでは、ゲームと C++ でよく使うパターンを選んで、「悪い例 → 何が困るか → 良い例 → いつ使う」の流れで説明しています。まず、この表で「困りごと」から、使えそうなパターンを探してください。

## 困りごとから探す

| 困りごと | 使えるパターン | ページ |
| --- | --- | --- |
| **リソースの解放を忘れる・例外でリークする** | RAII、スマートポインタ | [RAII とスマートポインタ](raii.md) |
| 何かが起きたことを相手を知らずに通知したい | オブザーバー（イベント） | [イベントシステム](event.md)、[イベントシステム＋（速さ重視）](event-plus.md) |
| キャラや画面の状態（立つ・走る・ジャンプ）が `if` だらけ | ステートマシン | [ステートマシン](state-machine.md) |
| 大量のオブジェクトを速く更新したい | ECS、データ指向設計 | [ECS](ecs.md)、[データ指向設計](data-oriented.md) |
| 弾やエフェクトを毎フレーム作っては消して遅い | オブジェクトプール | [オブジェクトプール](object-pool.md) |
| ヘッダを変えるたびに全部がビルドされる・外部ライブラリを隠したい | PImpl | [PImpl](pimpl.md) |
| 仮想関数のコストを避けたい・型ごとに共通機能を足したい | CRTP、ポリシー | [CRTP とポリシーベース設計](crtp-policy.md) |
| 種類が決まったデータに処理をどんどん足したい | ビジター（`variant`） | [ビジター](visitor.md) |
| 自作のデータ構造を範囲 for で回したい | イテレータ | [イテレータ（パターン）](iterator-pattern.md) |
| 機能を自由に重ねたい（バフ、ログ、キャッシュ） | デコレータ | [デコレータ](decorator.md) |
| 敵の行動やアルゴリズムを差し替えたい | ストラテジー | [ストラテジー](strategy.md) |
| 操作（命令）を記録・取り消し・再生したい | コマンド | [コマンドパターン](command.md) |
| 作る処理を 1 か所にまとめ、種類をデータで決めたい | ファクトリ | [ファクトリとデータ駆動](factory.md) |

## パターンの全体像

| 分類 | パターン | 目的 |
| --- | --- | --- |
| **C++ らしい基礎** | [RAII](raii.md)、[PImpl](pimpl.md)、[CRTP・ポリシー](crtp-policy.md) | リソース管理、ビルドの独立、速さ |
| 通知・状態 | [オブザーバー（イベント）](event.md)、[ステートマシン](state-machine.md)、[コマンド](command.md) | 疎結合なやり取り、状態の管理、操作の記録 |
| 構造・データ | [ECS](ecs.md)、[データ指向](data-oriented.md)、[オブジェクトプール](object-pool.md) | 大量のデータを速く |
| 振る舞いの差し替え・追加 | [ストラテジー](strategy.md)、[デコレータ](decorator.md)、[ビジター](visitor.md)、[イテレータ](iterator-pattern.md) | 機能の組み合わせ、処理の追加 |
| 作り方・つなぎ方 | [ファクトリ](factory.md)、[依存性の注入](dependency-injection.md)、[シングルトン](singleton.md) | オブジェクトの生成と依存の管理 |

## 使うときの考え方

1. **まず、パターンなしで書く**。困りごと（`if` が増えた、コピペが増えた、テストできない）が出てから、パターンを探す
2. パターンの名前をチームで共有する。「ここはステートマシンにしよう」と言えると設計の話が速い
3. パターンの形をそのまま真似しなくてよい。ゲームに合わせて、小さく簡単にする
4. 「あとで変わりそう」を理由に先にパターンを入れない（YAGNI）。変わったときに直す
