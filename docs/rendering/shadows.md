# 影のコスト

影は見た目への貢献が大きい一方で、描画コストも大きい機能です。一般的な影マップ方式では、**光の視点からシーンをもう一度描く**ので、ドロー コールと頂点処理がほぼ倍になります。さらに影マップの解像度・枚数・フィルタリングがピクセル処理と帯域幅に効いてきます。このページでは、影の何が重いのかを整理し、それぞれの対策を説明します。

!!! tip "ポイント"
    - 影マップは<strong>シーンの再描画</strong>。ドロー コールと頂点処理が増える。
    - 広い範囲を 1 枚で覆うと解像度が足りない。<strong>カスケード（CSM）</strong>で距離ごとに分ける。
    - 影用のカリング・LODをカメラ用とは別に行う。
    - 更新頻度の削減・静的な影のキャッシュで、毎フレームの描画量を減らす。
    - 点光源の影は6 面。影を落とすライトの数を制限する。
    - フィルタリング（PCF）は読み込み回数に比例して重くなる。

## 何が重いのか

| 重い場所 | 理由 |
| --- | --- |
| **シーンの再描画** | 光の視点から、影を落とす物体を全部描き直す |
| 影マップの書き込み | 深度だけだが、2048×2048 や 4096×4096 を何枚も書く |
| 影マップの読み込み | ピクセルごとに複数回サンプリングする（PCF） |
| ライトの数 | 点光源は 6 方向。スポットライトは 1 枚。ライトごとに必要 |

影の描画は深度だけを書くのでピクセルシェーダーが不要で、1 枚あたりは軽い処理です。しかし枚数が増えるので、頂点処理とドロー コールの合計が大きくなります。

## カスケード シャドウ マップ（CSM）

太陽光のような広い範囲の影を 1 枚の影マップで覆うと、カメラの近くで解像度が足りず、影の輪郭がギザギザになります。逆に近くに合わせると遠くが範囲外になります。

**CSM** はカメラの視錐台を奥行きで 3〜4 個に分割し、それぞれに別の影マップを割り当てます。近くは小さな範囲を細かく、遠くは広い範囲を粗く覆います。

| 点 | 説明 |
| --- | --- |
| 分割の位置 | 対数と線形の中間（実用分割）。近くを細かくする |
| 枚数の目安 | 3〜4 枚。多いほど品質が上がるが、描画が増える |
| 境目 | 隣のカスケードと混ぜて、切り替わりを目立たなくする |
| ちらつき | カメラの動きで影マップの範囲が動くと、輪郭がちらつく。範囲をテクセル単位に揃える |

## 減らす工夫

### 影用のカリング

カメラの視錐台でカリングするだけでは足りません。**光の視錐台**で別にカリングします。

| 工夫 | 説明 |
| --- | --- |
| 光の視錐台でカリング | カメラに映っていなくても、影が映る範囲に落ちるものは必要 |
| 小さな物体を除外 | 画面で数ピクセル以下の物体は、影も見えないので落とさない |
| 遠い物体を除外 | 影を落とす最大距離を決める |
| 影を落とさない設定 | 小物・細い草・パーティクルなどを影の描画から外す |

### 影用の LOD

影のシルエットは、メッシュの細部まで正確である必要はありません。影用に低い LOD のメッシュを使うと、頂点処理が減ります。

### 更新頻度を下げる

| 対象 | 方法 |
| --- | --- |
| 遠いカスケード | 数フレームに 1 回だけ更新する（ずらして均す） |
| 静的な物体の影 | 動かない物体だけの影マップをキャッシュし、動く物体だけを毎フレーム足す |
| 遠いライトの影 | 距離が遠いライトは、影なし・低頻度更新にする |

### ライトの影を制限する

点光源の影はキューブマップ（6 面）で描くので 6 倍のコストです。

| 工夫 | 説明 |
| --- | --- |
| 影を落とすライトを限定 | 重要なライトだけ。数十個のライトの全部に影をつけない |
| 距離で切る | カメラから遠いライトの影は無効にする |
| ライトの範囲を絞る | 範囲内にある物体だけを描く |

## フィルタリングのコスト

影の縁を柔らかくするには、影マップを複数回サンプリングして平均します（**PCF**）。

| 方式 | 読み込み回数 | 品質 |
| --- | --- | --- |
| 1 回 | 1 | ギザギザ |
| ハードウェア PCF（比較サンプラー） | 1（2×2 を自動で混ぜる） | 少し滑らか |
| 3×3 / 5×5 の PCF | 9 / 25 | 滑らか。ただし重い |
| PCSS（距離で柔らかさが変わる） | 多い（ブロッカー探索＋フィルタ） | 最も自然。重い |

比較サンプラー（`SampleCmp`）は、ハードウェアが比較と補間を行うので、1 回の読み込みでも滑らかになります。DX11 では `D3D11_FILTER_COMPARISON_MIN_MAG_LINEAR_MIP_POINT` を使います。

## 影マップの設定

| 設定 | 説明 |
| --- | --- |
| **バイアス** | 影が表面に張り付いて見える（シャドウ アクネ）のを防ぐ。大きすぎると影が浮く（ピーターパン） |
| フォーマット | 16 ビットの深度で足りることが多い。メモリと帯域が半分になる |
| 解像度 | 必要最小限。ゲームの見た目に合わせて調整する |
| スロープ バイアス | 面が斜めのときほど、バイアスを増やす |

## 影のコストを数字で見積もる

影マップは、シーンをもう一度描くので、コストの目安は、「影用の描画 ＝ 見える物の、頂点とドロー コール × 光源の数」です。

| 構成 | 描画の追加 |
| --- | --- |
| 太陽（CSM、4 枚） | カスケードごとに、シーンを再描画 → <strong>約 4 倍</strong>のドロー コール（カリングで、かなり減る） |
| 点光源 1 個（キューブ） | 6 面 → 約 6 倍 |
| スポットライト 1 個 | 1 枚 → 約 1 倍 |
| 影つきのライト 10 個（点光源） | 60 面 → 重い |

カスケードと光源ごとに、光の視錐台でカリングすると、実際に描く量は、大きく減ります（[カリング](culling.md)）。

## カスケードの分割と、ちらつきの防止

### 分割の位置：実用分割

カメラの手前を細かく、奥を粗く分けます。対数分割と線形分割の、中間（実用分割）がよく使われます。

```cpp
// 各カスケードの境目（カメラからの距離）を実用分割で求める。lambda: 0 で線形、1 で対数。0.5〜0.9 が実用的。
std::array<float, kCascadeCount + 1> SplitDistances(float near_z, float far_z, float lambda) {
  std::array<float, kCascadeCount + 1> d;
  for (int i = 0; i <= kCascadeCount; ++i) {
    const float p = static_cast<float>(i) / kCascadeCount;
    const float log_split = near_z * std::pow(far_z / near_z, p);       // 対数: 手前を細かく
    const float lin_split = near_z + (far_z - near_z) * p;              // 線形: 均等
    d[i] = lambda * log_split + (1.0f - lambda) * lin_split;
  }
  return d;
}
```

例えば、`near = 0.1`、`far = 200`、4 分割、`lambda = 0.8` なら、境目は、約 0.1、5、24、72、200 m と、手前ほど細かくなります（数値は目安）。

### テクセル スナップ：カメラが動いても、影がちらつかない

カスケードの範囲がカメラの動きに合わせて、連続的に動くと、影マップの、テクセルの境目が毎フレーム、ずれて、影の縁がちらつきます。<strong>範囲の中心を 1 テクセルの大きさの倍数にそろえて</strong>動かします。

```cpp
// 光の空間で、カスケードの中心を影マップの 1 テクセルの大きさの倍数に切り捨てる。
// radius: カスケードを囲む球の半径（回転しても、大きさが変わらないよう、球で囲む）。
const float world_units_per_texel = (2.0f * radius) / shadow_map_size;
center_light_space.x = std::floor(center_light_space.x / world_units_per_texel) * world_units_per_texel;
center_light_space.y = std::floor(center_light_space.y / world_units_per_texel) * world_units_per_texel;
```

範囲をカメラの向きで回転する四角形ではなく、球で囲んでおくと、カメラを回しても、範囲の大きさが、変わらず、スナップが有効になります（[Aliasing and Stabilization](../graphics/shadows/shadow-map-basics/aliasing-stabilize.md)）。

## 静的な影をキャッシュする

動かない物（地形、建物）の影は、毎フレーム、描き直す必要がありません。<strong>静的な影マップを 1 度作って、使い回し</strong>、動く物だけを毎フレーム、足します。

```cpp
// 静的な影マップ（建物・地形）は、光が動いたとき、または、静的な物が変わったときだけ、描き直す。
if (light_moved || static_changed) {
  RenderShadow(static_shadow_map, static_casters);
}
// 毎フレーム: 静的な影マップを動的な影マップにコピーして、動く物だけを上から描く。
context->CopyResource(dynamic_shadow_map.Get(), static_shadow_map.Get());
RenderShadow(dynamic_shadow_map, dynamic_casters);
```

太陽がゆっくり動くゲームでは、静的な影を数秒に 1 回だけ、更新するのが一般的です。コピーの帯域は、かかりますが、シーン全体の再描画（頂点とドロー コール）より、はるかに、安く済みます（遠いカスケードは、さらに、頻度を落とす）。

## よくあるミス

??? failure "カメラ用のカリング結果をそのまま影に使う"
    カメラの後ろにある物体が落とす影が欠けます。光の視錐台で別にカリングします。

??? failure "遠いカスケードも毎フレーム全部描く"
    遠くは変化が見えにくいので、数フレームに 1 回に間引きます。

??? failure "全ての点光源に影をつける"
    6 倍のコストです。重要なライトだけにします。

??? failure "影マップの範囲が動いて、影がちらつく"
    範囲の動きを**テクセル単位に揃え**ます。

??? failure "影用に高い LOD のメッシュを使い続ける"
    影用に低い LOD を選びます。
