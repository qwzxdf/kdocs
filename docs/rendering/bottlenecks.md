# 何が重いのか（ボトルネック）

描画を速くするには、<strong>まず「何が足を引っ張っているか」</strong>を、見極めます。CPU が遅いのか、GPU が遅いのか、GPU でも「頂点」「ピクセルの計算」「メモリ」のどれかで効く手法がまったく違います。ボトルネックでない所を、最適化してもフレーム時間は、ほぼ変わりません。このページは描画で重くなる原因の分類と、見分け方をまとめます。

!!! tip "ポイント"
    - フレーム時間は<strong>CPU と GPU の、遅い方</strong>で決まる（<strong>並列に動く</strong>ため）。
    - GPU の中でも頂点・ラスタライズ・ピクセル・メモリ帯域のどれかが足を引っ張る。
    - 解像度を下げて速くなる → ピクセル側（フィルレート・ピクセルシェーダー・帯域）。変わらない → 頂点側か CPU。
    - 計算（ALU）は、安い。メモリアクセスが高い（特に帯域）。
    - GPU は「待っている」ことがある（CPU の命令待ち・依存待ち）。使用率だけでは、足りない。
    - ツールで測る：PIX・RenderDoc・各社のプロファイラー（[プロファイラー](../vs/profiler.md)）。

## 1. CPU が重いか、GPU が重いか

**CPU と GPU は、並列に動きます**。CPU が次のフレームの命令を作っている間に、GPU は今のフレームを描きます。遅い方がフレーム時間を決めます。

| 状況 | 見分け方 |
| --- | --- |
| CPU が遅い | 解像度を下げても速くならない。GPU の使用率が低い。CPU のスレッドが描画の関数で時間を使っている |
| GPU が遅い | 解像度を下げると速くなる。GPU の使用率が高い。GPU の時間（タイムスタンプ）が、フレーム時間に近い |
| 同期待ち | CPU が、GPU の結果を待つ（`Map` の読み戻しなど）。どちらも使用率が低いのに、遅い |

手っ取り早い実験：ウィンドウの解像度を半分にして、フレーム時間を見る。大きく変われば、ピクセル側の問題です。

## 2. CPU 側が重い理由

| 原因 | 説明 | 対策 |
| --- | --- | --- |
| **ドロー コールが多い** | 1 回の描画命令ごとに、ドライバが検査・変換・コマンド作成をする。数千〜数万で、CPU が詰まる | バッチ・インスタンシング・GPU Driven（[ドロー コール](draw-calls.md)・[GPU Driven](gpu-driven.md)） |
| 状態の切り替え | シェーダー・テクスチャ・ブレンド設定を変えるたび、コストがかかる | ソートして、切り替えを減らす |
| カリングの判断 | 物体 1 つずつ、見えるか調べる（CPU） | 階層構造・GPU に任せる（[カリング](culling.md)） |
| 定数バッファの更新 | 毎フレーム、物体ごとに書き込み | まとめて 1 つのバッファに、書く |
| ドライバの検証 | DX11 はドライバの仕事が多い（DX12 はアプリ側に任せる） | API の機能（コマンド リスト）・DX12 |

## 3. GPU 側が重い理由

GPU の処理は、**いくつかの段階**に分かれ、どれかが詰まると全体が遅くなります。

| 段階 | 仕事 | 重くなる原因 |
| --- | --- | --- |
| 頂点処理 | 頂点の位置を計算 | 頂点数が多い。画面外・隠れた物の頂点も計算している |
| ラスタライズ | 三角形をピクセルに分解 | 三角形が小さすぎる（1 ピクセル未満で効率が悪い。[オーバードロー](overdraw.md)） |
| ピクセル処理 | 色を計算（ライティング・テクスチャ） | ピクセル数 × シェーダーの計算量。ライトが多い |
| 出力（ROP） | 深度テスト・ブレンド・書き込み | ブレンド（半透明）・MSAA・高解像度で書き込みが多い |
| メモリ帯域 | テクスチャ・バッファの読み書き | G-Buffer・高解像度の RT・大きなテクスチャ |

### フィルレートと、ピクセル数

1920×1080 は、約 207 万ピクセル、4K（3840×2160）は、約 830 万ピクセル（4 倍）です。ピクセル処理の負担は、ピクセル数に比例します。

| 解像度 | ピクセル数 | 1080p に対する倍率 |
| --- | --- | --- |
| 1280×720 | 約 92 万 | 0.44 倍 |
| 1920×1080 | 約 207 万 | 1 倍 |
| 2560×1440 | 約 369 万 | 1.8 倍 |
| 3840×2160（4K） | 約 830 万 | 4 倍 |

さらに同じピクセルを何度も塗る（オーバードロー）と、倍数で重くなります。

## 4. 計算とメモリ：どちらが足りないか

GPU は**膨大な計算能力**（ALU）を持ちますがメモリから、データを運ぶ速さ（帯域）には限りがあります。

| | 計算（ALU） | メモリ（帯域・レイテンシ） |
| --- | --- | --- |
| 近年の傾向 | 非常に速く、伸びている | 伸びが遅い |
| コスト | 安い | 高い |
| ボトルネックになりやすさ | 複雑なシェーダー | G-Buffer・大きな RT・テクスチャの読み込み |

「計算を減らす」より、「メモリアクセスを減らす」ほうが効くことが増えています。ライティングを、Deferred にすると、G-Buffer の読み書きで、帯域が増える——というように、トレードオフが現れます（[メモリ帯域幅](bandwidth.md)）。

## 5. 見分ける実験

| 実験 | 結果の読み方 |
| --- | --- |
| **解像度を下げる** | 速くなる ＝ ピクセル側（シェーダー・帯域・フィルレート） |
| ピクセルシェーダーを単純にする（定数の色） | 速くなる ＝ ピクセルシェーダーが、重い |
| テクスチャを、1×1 に | 速くなる ＝ テクスチャの帯域・キャッシュが足りない |
| ドロー コールを半分に | 速くなる ＝ CPU（命令）か、頂点 |
| 頂点を減らす（LOD） | 速くなる ＝ 頂点側 |
| ライトの数を減らす | 速くなる ＝ ライティングが、重い |
| ポストエフェクトを切る | 速くなる ＝ 画面全体の効果が、重い |

1 つずつ、変えて、フレーム時間を比べます（[計測](../optimize/measure.md)）。

## 6. ツール

| ツール | 内容 |
| --- | --- |
| **PIX on Windows** | DX のフレームのキャプチャ。各描画命令の、GPU 時間・状態 |
| RenderDoc | フレームのキャプチャ。描画命令・テクスチャ・シェーダーの確認 |
| GPU ベンダーのツール（NVIDIA Nsight・AMD Radeon GPU Profiler・Intel GPA） | GPU 内部の詳細な、カウンター（帯域・占有率・キャッシュ） |
| タイムスタンプ クエリ（自作） | `ID3D11Query`（`D3D11_QUERY_TIMESTAMP`）で、区間の GPU 時間を測る |
| Visual Studio のプロファイラー | CPU 側（[プロファイラー](../vs/profiler.md)） |

```cpp
D3D11_QUERY_DESC desc = {D3D11_QUERY_TIMESTAMP, 0};
device->CreateQuery(&desc, &start_query);
context->End(start_query);
```

GPU の時間は、非同期に取得されます（数フレーム後に結果を読む）。

## 7. 優先順位の考え方

| 順番 | 考え方 |
| --- | --- |
| **1. 全体でどれが重いか** | CPU か GPU か |
| 2. 一番重い段階 | 頂点・ピクセル・帯域のどれか |
| 3. 効果が大きく、簡単なもの | カリング・LOD・解像度・フォーマットから |
| 4. 大きな構造の変更 | Deferred・Clustered・GPU Driven（効果大だが手間も大） |
| 5. 直したら、また測る | ボトルネックは、移動する |

## よくあるミス

??? failure "GPU が遅いのに、ドロー コールを減らす"
    **CPU がボトルネックでない**と効果はほぼありません。

??? failure "使用率が高いから、GPU が限界と思う"
    「忙しい」と「効率的」は別です。待っている時間も使用率に含まれることがあります。

??? failure "Debug ビルドで測る"
    Release で測ります（[コンパイラとビルド](../basics/compiler.md)）。

??? failure "VSync をつけたまま、測る"
    フレームが、60 FPS に固定されて、余裕が分かりません。切って測ります。

??? failure "平均だけ見て、スパイクを見逃す"
    最悪のフレームを見ます（[フレーム時間の設計](../optimize/frame-budget.md)）。
