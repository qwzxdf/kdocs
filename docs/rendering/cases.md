# 場面別の直し方

ここまでのページで説明した手法を**症状から引ける**ようにまとめます。どの手法がどんな場面で効くのかを一覧で確認するためのページです。

!!! tip "ポイント"
    - 症状から**ボトルネックの種類**を決め対応する手法を選ぶ。
    - 手法の詳細は各ページを見る。

## ゲームでの使いどころ

| 場面 | 直し方 |
| --- | --- |
| 草・木・弾を大量に描く | インスタンシング |
| 2D のスプライトが多い | アトラス + スプライト バッチ |
| 動かない街・地形 | 静的バッチ + 視錐台カリング + LOD |
| 画面いっぱいのエフェクトで、重くなる | 半透明の範囲を減らす。解像度を下げる |
| UI が重い | UI をまとめて 1 つのバッチに。変更がなければ描画結果を使い回す（キャッシュ） |
| モバイル・低スペック | テクスチャの圧縮、解像度の調整、シェーダーの簡略化 |

## 症状から探す

最適化で最初にやるべきことは手法を選ぶことではなく、**ボトルネックの種類を特定すること**です。CPU が遅いのか GPU のピクセル処理かメモリ帯域かで効く手法がまったく違います。見分けるための簡単な実験が「解像度を下げてみる」ことで、速くなるなら GPU のピクセル側、変わらないなら CPU 側か頂点側が原因です。

以下の表は実験の結果と症状から、効く手法とそのページを引けるようにしたものです。

| 症状 | ボトルネック | 効く手法 | ページ |
| --- | --- | --- | --- |
| **解像度を下げても速くならない** | CPU | バッチ・インスタンシング・GPU Driven | [ドロー コール](draw-calls.md)・[GPU Driven](gpu-driven.md) |
| **解像度を下げると速くなる** | GPU（ピクセル） | 低解像度・TAA・シェーダーの軽量化 | [低解像度](low-res-effects.md)・[TAA](taa-upscaling.md)・[シェーダー](shader-cost.md) |
| **ライトを増やすと極端に重い** | GPU（ライティング） | Deferred・Tiled・Clustered | [Forward と Deferred](forward-deferred.md)・[Tiled と Clustered](light-culling.md) |
| **G-Buffer の書き込みが重い** | 帯域幅 | フォーマット・Visibility Buffer | [帯域幅](bandwidth.md)・[Visibility Buffer](visibility-buffer.md) |
| **三角形が非常に多い** | GPU（頂点） | LOD・カリング・Meshlet | [LOD](lod.md)・[Mesh Shader](mesh-shaders.md) |
| **半透明で重くなる** | GPU（ピクセル・帯域） | 縮小バッファ・枚数削減 | [パーティクル](particles.md) |
| **影を付けると重い** | CPU・GPU（頂点） | カスケード・影用カリング・キャッシュ | [影](shadows.md) |
| **VRAM が足りない** | VRAM | 圧縮・ストリーミング | [テクスチャ](texture-streaming.md) |
| **ポストプロセスが重い** | 帯域幅 | パスをまとめる・縮小 | [ポストプロセス](postprocess.md) |
| **フレーム時間が不安定** | 全体 | 動的解像度・予算の設計 | [TAA・アップスケーラ](taa-upscaling.md)・[フレーム時間](../optimize/frame-budget.md) |

## 事例で流れを追う

症状から原因を特定し直して効果を確かめるまでの流れを 3 つの場面で見ます。数字は考え方を示すための例（目安）です。

### 事例 1：森でドロー コールが 8,000 回

| 手順 | 内容 |
| --- | --- |
| 症状 | 森の場面で 24 ms（約 40 FPS）。他の場面は 12 ms |
| 切り分け | 解像度を半分にしても、24 ms のまま → <strong>CPU が原因</strong> |
| 計測 | プロファイラーで、描画の記録が 14 ms を占める。ドロー コールは約 8,000 回（木 3,000、草 4,000、岩 1,000） |
| 原因 | 木や草を 1 本ずつ描いている |
| 直し方 | 同じメッシュをインスタンスで、まとめる。木 5 種類 + 草 3 種類 + 岩 4 種類 = 12 回に |
| 結果 | 描画の記録が 14 ms → 1 ms。フレームは 11 ms に |
| 次の一手 | 視錐台と距離で、カリングして見えない木をインスタンスから、外す（[カリング](culling.md)） |

### 事例 2：ライトを 200 個にしたら、極端に重い

| 手順 | 内容 |
| --- | --- |
| 症状 | ライトを 20 個から 200 個に増やすと GPU が、18 ms から 55 ms に |
| 切り分け | 解像度を下げると速くなる → <strong>GPU のピクセル処理</strong> |
| 計測 | ライティングのパスが重い。フォワード描画で各ピクセルが、全 200 個のライトをループしている |
| 原因 | 全ピクセルが画面全体の全ライトを計算している |
| 直し方 | ディファードにして、<strong>クラスタード方式</strong>で各ピクセルに影響するライトだけを渡す |
| 結果 | ライティングが、40 ms → 6 ms |
| 次の一手 | G バッファの帯域が、次の壁になる。フォーマットを軽くする（[帯域幅](bandwidth.md)） |

### 事例 3：魔法のエフェクトで、60 FPS が 35 FPS に

| 手順 | 内容 |
| --- | --- |
| 症状 | 魔法の煙を出すとフレームが、9 ms から 28 ms に |
| 切り分け | 解像度を下げると、大きく速くなる → GPU のピクセル処理か帯域 |
| 計測 | オーバードローの可視化で、煙の部分が真っ赤（10 重ね以上）。1 枚が画面の 3 分の 2 を覆っている |
| 原因 | 大きな半透明の板をフル解像度で、10 枚以上、重ねている。1080p で 20 M ピクセル以上、ブレンド（読み書き）している |
| 直し方 | 煙を半分の解像度の縮小バッファに描いて、最後に合成。板の数を 10 枚から 5 枚に |
| 結果 | 煙のコストが約 1/8 に。フレームは 11 ms に |
| 次の一手 | 見た目の差を確認する。縁がにじむなら深度を考慮した拡大（[パーティクル](particles.md)） |

3 つに共通するのは <strong>① 切り分け → ② 計測 → ③ 原因 → ④ 直す → ⑤ 測り直す</strong>の順です。勘で直さず数字で確かめます。

## 全体のよくあるミス

??? failure "ボトルネックを調べずにシェーダーを直す"
    CPU 側が遅いのにシェーダーを最適化しても、速くなりません。まず、CPU と GPU のどちらが遅いかを解像度の変更やプロファイラーで確かめます。

??? failure "全オブジェクトを毎フレーム 1 つずつカリング判定する"
    オブジェクトが数万になると、判定自体で CPU が重くなります。空間分割で階層的に判定します。

??? failure "ドロー コールの数だけを見る"
    ドロー コールが少なくても、1 回が非常に重ければ遅いです。GPU 側のプロファイラーで、実際の時間を見ます。

??? failure "テクスチャが大きすぎる"
    必要以上に大きく圧縮もしていないとメモリ帯域とメモリ使用量の両方で、不利です。

??? failure "最適化のつもりで、見た目が壊れる"
    カリングを強くしすぎて、画面の端でオブジェクトが消える LOD の切り替えが目立つなどです。見た目も必ず確認します。
