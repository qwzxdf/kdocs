# Why Synchronization

<div class="page-badges" markdown>
<span class="rank rank-must">必須</span>
</div>

CPU と GPU は、<strong>別々の、プロセッサー</strong>で、<strong>それぞれ、非同期に</strong>、動きます。CPU が、`Draw` を、呼んでも、GPU が、描くのは、<strong>あとで</strong>です。さらに、GPU の、内部でも、複数の、命令が、重なり合って、実行されます。このため、「いつ、リソースを、触ってよいか」「いつ、結果を、読んでよいか」を、考える、必要が、あります。これが、同期です。DirectX 11 は、ドライバーが、大部分を、自動で、行い、DirectX 12 は、アプリが、明示的に、行います。

!!! tip "ポイント"
    - CPU が、命令を、<strong>積む</strong>のと、GPU が、<strong>実行する</strong>のは、別の時刻。GPU は、数フレーム遅れて、実行することが、ある。
    - 同期が、必要な、場面は、3 つ: <strong>CPU が、GPU の、使用中の、データを、書き換える</strong>、<strong>同じリソースを、書いてから、読む</strong>、<strong>GPU の、結果を、CPU が、読む</strong>。
    - D3D11: ドライバーが、自動で、行う（そのぶん、実行時の、オーバーヘッドと、予測しにくい、待ち）。
    - D3D12: <strong>フェンス</strong>（CPU ↔ GPU）と、<strong>リソース バリア</strong>（GPU の中）で、明示する。
    - 同期の、間違いは、「たまに、画面が、乱れる」「環境で、クラッシュする」という、<strong>再現しにくい</strong>バグになる。

## CPU と GPU は、非同期

```text
CPU:  Draw ─ Draw ─ Draw ─ Present ─ Draw ─ Draw ─ Present …     ← 命令を、積んでいく（速い）
GPU:        └──── 実行 ────────┘     └──── 実行 ──── …           ← 実際に、描く（遅れて実行）
```

CPU は、命令を、<strong>キュー</strong>に、積むだけで、すぐ、次へ、進めます。GPU は、キューの、命令を、順に、実行します。CPU が、先に、進み、GPU が、遅れて、追いかける、構図です。

## 同期が、必要な、3 つの、場面

### ① CPU が、GPU の、使用中の、データを、書き換える

```text
フレーム N:  CPU が、定数バッファに、行列を、書く → Draw を、積む
フレーム N+1: CPU が、同じ定数バッファを、上書き
GPU: まだ、フレーム N の Draw を、実行していない → 上書き後の、値で、実行してしまう
```

GPU が、まだ、フレーム N の、描画を、実行していないのに、CPU が、フレーム N+1 の、データで、定数バッファを、上書きすると、フレーム N の、描画が、<strong>間違った値</strong>で、実行されます。

| 対策 | 内容 |
| --- | --- |
| D3D11 | `Map(WRITE_DISCARD)` が、ドライバーに、新しい領域を、割り当てさせる（古い領域は、GPU が、使い終わるまで、残る） |
| D3D12 | フレームごとに、別の領域を、使い、<strong>フェンス</strong>で、GPU の完了を、確認してから、再利用する |

### ② 同じリソースを、書いてから、読む

```text
パス A: テクスチャ T に、描く（RTV として、書き込み）
パス B: テクスチャ T を、読む（SRV として、読み取り）
```

パス A の、書き込みが、<strong>完了する前に</strong>、パス B が、読むと、書きかけの、内容を、読みます。また、GPU の、キャッシュに、残った、書き込みが、メモリに、反映されていない、可能性も、あります。

| 対策 | 内容 |
| --- | --- |
| D3D11 | ドライバーが、自動で、順序を、保証する。ただし、同時に、束ねる（RTV と SRV）と、読む側が、黙って、外れる |
| D3D12 | <strong>リソース バリア</strong>で、状態を、遷移（`RENDER_TARGET` → `PIXEL_SHADER_RESOURCE`）。UAV の、連続は、UAV バリア |

### ③ GPU の結果を、CPU が、読む

```text
GPU: 計算の、結果を、バッファに、書く
CPU: そのバッファを、読む → GPU が、まだ、終えていない
```

| 対策 | 内容 |
| --- | --- |
| D3D11 | `STAGING` に、コピーして、`Map(READ)`。`Map` が、GPU の、完了を、待つ（止まる） |
| D3D12 | READBACK ヒープに、コピーして、<strong>フェンスで、完了を、確認</strong>してから、`Map` |

いずれも、毎フレーム、完了を、待つと、CPU が、止まるので、数フレーム、<strong>遅れて、読み</strong>ます。

## フレーム イン フライト

CPU が、GPU の、完了を、毎フレーム、待つと、<strong>CPU と GPU が、交互に、止まり</strong>、半分ずつしか、使えません。CPU が、数フレーム、先に、進める、<strong>フレーム イン フライト</strong>にすると、両方が、並列に、動きます。

```text
毎フレーム待つ:    CPU [記録]       [記録]       [記録]
                   GPU       [実行]       [実行]       [実行]    ← 交互（半分ずつ遊ぶ）

フレーム イン フライト:  CPU [記録][記録][記録][記録]
                         GPU    [実行][実行][実行][実行]         ← 並列
```

そのぶん、<strong>フレームごとに、別の、リソース</strong>（定数バッファ、動的な、頂点バッファ）が、要り、<strong>入力の、遅延</strong>が、1 フレーム分、増えます。

## 同期の、道具

| 道具 | 同期する、もの | API |
| --- | --- | --- |
| フェンス | CPU ↔ GPU、キュー ↔ キュー | D3D12: `ID3D12Fence`（`Signal`・`Wait`） |
| リソース バリア | GPU の中の、読み書きの、順序、リソースの、状態 | D3D12: `ResourceBarrier` |
| クエリ（イベント） | GPU の、完了の、通知 | D3D11: `D3D11_QUERY_EVENT` |
| `Map` の、フラグ | CPU の書き込みと、GPU の読み取り | D3D11: `WRITE_DISCARD`、`NO_OVERWRITE` |

## 読み書きの、衝突

<strong>同じリソースを、同時に、書き込みと、読み取りに、使えません</strong>。

| API | 起きること |
| --- | --- |
| D3D11 | 同じリソースを、RTV と SRV に、同時に、束ねると、<strong>読む側が、黙って、外される</strong>（結果は、黒いテクスチャ）。デバッグ レイヤーが、警告を、出す |
| D3D12 | バリアで、状態を、切り替えないと、未定義の、動作（画面の乱れ、クラッシュ） |

どちらも、「書き終えてから、読む」の、順序を、アプリが、意識する、必要が、あります。D3D11 は、「束縛を、外す」、D3D12 は、「バリアで、状態を、遷移する」と、いう、表現の違いです。

## 解放の、タイミング

GPU が、まだ、使っている、リソースを、解放すると、クラッシュします。

| API | 対処 |
| --- | --- |
| D3D11 | ドライバーが、参照を、数えて、GPU の使用が、終わるまで、実際の、解放を、遅らせる。<strong>パイプラインに、束ねたままの、リソースは、解放が、遅れる</strong>（`ClearState` で、外す） |
| D3D12 | <strong>アプリが、フェンスで、完了を、確認</strong>してから、解放する。解放の、遅延リストを、持つ |

## 同期の、コスト

| 同期 | コスト |
| --- | --- |
| フェンスで、CPU が、GPU を、待つ | CPU が、止まる（フレームの、待ち時間） |
| 毎フレームの、全完了待ち | CPU と GPU が、直列になり、フレームレートが、半減 |
| バリアの、入れすぎ | GPU の、パイプラインの、フラッシュ（待ち）が、増える |
| `Map(READ)` の、即時の、読み | CPU が、GPU の、完了まで、止まる |

同期は、<strong>必要な、最小限</strong>に、します。多すぎると、並列性が、失われ、少なすぎると、画面が、乱れます。

## よくあるミス

??? failure "ときどき、画面が、乱れる、ちらつく（再現が、不安定）"
    GPU が、使用中の、データを、CPU が、書き換えている。または、バリアが、足りない。フレームごとに、別の領域に、書き、完了を、フェンスで、確認する。

??? failure "毎フレーム、完了を、待って、フレームレートが、低い"
    フレーム イン フライト（2〜3）にして、同じ、スロットを、前に、使った、フレームだけを、待つ。

??? failure "GPU の結果を、すぐ、CPU で、読んで、フレームが、止まる"
    数フレーム遅れて、読む（リング）。

??? failure "リソースを、解放して、後で、クラッシュする"
    GPU が、まだ、使っている。D3D12 は、フェンスで、完了を、待ってから、解放する。

    - [x] D3D11 は、ドライバーが、自動。D3D12 は、フェンスとバリアで、明示
