# Why Synchronization

<div class="page-badges" markdown>
<span class="rank rank-must">必須</span>
</div>

CPU と GPU は <strong>別々のプロセッサー</strong>で それぞれ非同期に動きます。CPU が `Draw` を呼んでも GPU が、描くのは あとでです。さらに、GPU の内部でも複数の命令が重なり合って実行されます。このため「いつリソースを触ってよいか」「いつ結果を読んでよいか」を考える必要があります。これが同期です。DirectX 11 はドライバーが大部分を自動で行い DirectX 12 は、アプリが明示的に行います。

!!! tip "ポイント"
    - CPU が命令を <strong>積む</strong>のと GPU が <strong>実行する</strong>のは、別の時刻。GPU は数フレーム遅れて実行することがある。
    - 同期が必要な場面は 3 つ: CPU が GPU の使用中のデータを書き換える、同じリソースを書いてから読む、GPU の結果を CPU が、読む。
    - D3D11: ドライバーが自動で、行う（そのぶん実行時のオーバーヘッドと予測しにくい待ち）。
    - D3D12: フェンス（CPU ↔ GPU）と リソース バリア（GPU の中）で、明示する。
    - 同期の間違いは「たまに画面が乱れる」「環境でクラッシュする」という 再現しにくいバグになる。

## CPU と GPU は非同期

```text
CPU:  Draw ─ Draw ─ Draw ─ Present ─ Draw ─ Draw ─ Present …     ← 命令を、積んでいく（速い）
GPU:        └──── 実行 ────────┘     └──── 実行 ──── …           ← 実際に、描く（遅れて実行）
```

CPU は命令を <strong>キュー</strong>に積むだけですぐ次へ進めます。GPU はキューの命令を順に実行します。CPU が先に進み GPU が遅れて、追いかける構図です。

## 同期が必要な 3 つの場面

### ① CPU が GPU の使用中のデータを書き換える

```text
フレーム N:  CPU が、定数バッファに、行列を、書く → Draw を、積む
フレーム N+1: CPU が、同じ定数バッファを、上書き
GPU: まだ、フレーム N の Draw を、実行していない → 上書き後の、値で、実行してしまう
```

GPU がまだフレーム N の描画を実行していないのに CPU が、フレーム N+1 のデータで、定数バッファを上書きするとフレーム N の描画が <strong>間違った値</strong>で実行されます。

| 対策 | 内容 |
| --- | --- |
| D3D11 | `Map(WRITE_DISCARD)` がドライバーに新しい領域を割り当てさせる（古い領域は、GPU が使い終わるまで残る） |
| D3D12 | フレームごとに別の領域を使い フェンスで、GPU の完了を確認してから、再利用する |

### ② 同じリソースを書いてから読む

```text
パス A: テクスチャ T に、描く（RTV として、書き込み）
パス B: テクスチャ T を、読む（SRV として、読み取り）
```

パス A の書き込みが 完了する前にパス B が読むと書きかけの内容を読みます。また、GPU のキャッシュに残った、書き込みがメモリに反映されていない、可能性もあります。

| 対策 | 内容 |
| --- | --- |
| D3D11 | ドライバーが自動で順序を保証する。ただし、同時に束ねる（RTV と SRV）と読む側が黙って外れる |
| D3D12 | リソース バリアで状態を遷移（`RENDER_TARGET` → `PIXEL_SHADER_RESOURCE`）。UAV の連続は UAV バリア |

### ③ GPU の結果を CPU が読む

```text
GPU: 計算の、結果を、バッファに、書く
CPU: そのバッファを、読む → GPU が、まだ、終えていない
```

| 対策 | 内容 |
| --- | --- |
| D3D11 | `STAGING` にコピーして `Map(READ)`。`Map` が GPU の完了を待つ（止まる） |
| D3D12 | READBACK ヒープにコピーして フェンスで完了を確認してから `Map` |

いずれも、毎フレーム、完了を待つと CPU が止まるので、数フレーム、遅れて読みます。

## フレーム イン フライト

CPU が GPU の完了を毎フレーム、待つと <strong>CPU と GPU が交互に止まり</strong>、半分ずつしか使えません。CPU が数フレーム、先に進める フレーム イン フライトにすると両方が並列に動きます。

```text
毎フレーム待つ:    CPU [記録]       [記録]       [記録]
                   GPU       [実行]       [実行]       [実行]    ← 交互（半分ずつ遊ぶ）

フレーム イン フライト:  CPU [記録][記録][記録][記録]
                         GPU    [実行][実行][実行][実行]         ← 並列
```

そのぶん フレームごとに別のリソース（定数バッファ、動的な頂点バッファ）が要り 入力の遅延が 1 フレーム分、増えます。

## 同期の道具

| 道具 | 同期するもの | API |
| --- | --- | --- |
| フェンス | CPU ↔ GPU、キュー ↔ キュー | D3D12: `ID3D12Fence`（`Signal`・`Wait`） |
| リソース バリア | GPU の中の読み書きの順序、リソースの状態 | D3D12: `ResourceBarrier` |
| クエリ（イベント） | GPU の完了の通知 | D3D11: `D3D11_QUERY_EVENT` |
| `Map` のフラグ | CPU の書き込みと GPU の読み取り | D3D11: `WRITE_DISCARD`、`NO_OVERWRITE` |

## 読み書きの衝突

<strong>同じリソースを同時に書き込みと読み取りに使えません</strong>。

| API | 起きること |
| --- | --- |
| D3D11 | 同じリソースを RTV と SRV に同時に束ねると 読む側が黙って外される（結果は、黒いテクスチャ）。デバッグ レイヤーが警告を出す |
| D3D12 | バリアで状態を切り替えないと未定義の動作（画面の乱れ、クラッシュ） |

どちらも、「書き終えてから読む」の順序をアプリが意識する必要があります。D3D11 は「束縛を外す」、D3D12 は「バリアで状態を遷移する」という表現の違いです。

## 解放のタイミング

GPU がまだ使っているリソースを解放するとクラッシュします。

| API | 対処 |
| --- | --- |
| D3D11 | ドライバーが参照を数えて、GPU の使用が終わるまで実際の解放を遅らせる。<strong>パイプラインに束ねたままのリソースは解放が遅れる</strong>（`ClearState` で、外す） |
| D3D12 | アプリがフェンスで完了を確認してから、解放する。解放の遅延リストを持つ |

## 同期のコスト

| 同期 | コスト |
| --- | --- |
| フェンスで CPU が GPU を待つ | CPU が止まる（フレームの、待ち時間） |
| 毎フレームの全完了待ち | CPU と GPU が、直列になりフレームレートが半減 |
| バリアの入れすぎ | GPU のパイプラインのフラッシュ（待ち）が増える |
| `Map(READ)` の即時の読み | CPU が、GPU の完了まで止まる |

同期は <strong>必要な最小限</strong>にします。多すぎると並列性が失われ少なすぎると画面が乱れます。

## よくあるミス

??? failure "ときどき画面が乱れる、ちらつく（再現が不安定）"
    GPU が使用中のデータを CPU が書き換えている。または、バリアが足りない。フレームごとに別の領域に書き完了をフェンスで確認する。

??? failure "毎フレーム、完了を待ってフレームレートが低い"
    フレーム イン フライト（2〜3）にして同じスロットを前に使ったフレームだけを待つ。

??? failure "GPU の結果をすぐ CPU で読んでフレームが止まる"
    数フレーム遅れて読む（リング）。

??? failure "リソースを解放して後でクラッシュする"
    GPU がまだ使っている。D3D12 はフェンスで完了を待ってから解放する。
