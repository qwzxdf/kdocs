# Baking Workflow

<strong>ベイクはシーンの静的な光を、事前に計算してテクスチャへ書き出す作業</strong>です。時間がかかるので設定を段階的に上げながら、確認します。法線マップと併用するための「方向情報」も、一緒にベイクできます。このページではベイクの流れと、方向情報を説明します。

!!! tip "ポイント"
    - 手順：UV2 を用意 → 静的なオブジェクトを指定 → ベイク → 確認 → 調整。
    - 最初は低品質で全体を確認してから、品質を上げる。
    - 方向情報を一緒に焼くと、法線マップの凹凸が反映される。
    - ベイクは時間がかかるので、自動化・並列化する。

## ベイクの流れ
| 手順 | 内容 |
| --- | --- |
| ① UV2 の生成・パッキング | 全メッシュの UV2 を、ライトマップ アトラスに配置 |
| ② ベイク | 各テクセルのワールド位置・法線から、パス トレースで放射照度を計算 |
| ③ デノイズ | 少ないサンプルで速く計算し、デノイザでノイズを除去 |
| ④ 圧縮・出力 | <strong>BC6H（HDR）</strong>などに圧縮 |
| ⑤ 実行時に読み込む | シーンと一緒にライトマップをストリーミング |


最初に全メッシュの UV2 を生成して、ライトマップ アトラスに配置します。次に、アトラスの各テクセルがワールドのどの位置のどの法線に対応するかを求め、そこからパス トレーシングで放射照度を計算します。サンプル数が少なければ短時間で終わりますが、ノイズが残ります。そこで、デノイザ（Intel Open Image Denoise、NVIDIA OptiX、AMD の Radeon Image Filter など）でノイズを除去します。少ないサンプルで速く計算し後でデノイズする方法が、いまの標準です。最後に、BC6H のような HDR 向けの圧縮形式に圧縮して出力し、実行時にシーンと一緒にストリーミングします。

ベイクには数分から数時間かかります。GPU ベイク（GPU レイトレース）を使うと、CPU より大幅に短縮できます。

## 方向情報（法線マップとの併用）

通常のライトマップが持つのは、「その点に届く光の総量」（スカラー、色は RGB）だけです。法線マップで細かい凹凸を付けても、ライトマップの明るさは法線に応じて変わらないので、間接光の陰影が平坦に見えてしまいます。たとえば、レンガの壁に法線マップで凹凸を付けても、レンガの出っ張りと引っ込みの間接光が同じ明るさになります。

これを解決するのが<strong>方向情報</strong>です。光の来る方向も一緒に保存しておき、法線マップの法線と組み合わせて、明るさを補正します。主な方式は 4 つあります。

スカラーのみは放射照度だけを保存します。最も軽いですが法線マップは間接光に効きません。Directional ライトマップは、主な光の方向をもう 1 枚のテクスチャに保存します。法線との内積で明るさを補正します。SH ライトマップは L1 SH（4 係数）を保存して、法線で SH を評価します。そして、Radiosity Normal Mapping（Valve が『Half-Life 2』で使った方式）は、正三角形状に配した 3 つの基底方向のそれぞれについて放射照度を保存し、法線マップの法線で 3 つを補間します。

```hlsl
float3 basis0 = lightmap0.Sample(linear_sampler, uv).rgb;
float3 basis1 = lightmap1.Sample(linear_sampler, uv).rgb;
float3 basis2 = lightmap2.Sample(linear_sampler, uv).rgb;
float3 w = saturate(float3(dot(n_ts, kBasis0), dot(n_ts, kBasis1), dot(n_ts, kBasis2)));
w *= w;
w /= (w.x + w.y + w.z);
float3 irradiance = basis0 * w.x + basis1 * w.y + basis2 * w.z;
```

3 つの基底方向は接空間で表されます（法線に近い方向を 3 方向から取り囲むように置く）。法線 n_ts と各基底方向の内積が大きいほど、その基底の放射照度が強く効きます。2 乗して正規化しているのは、重みを鋭くして法線の向きに敏感にするためです。

方向情報を持たせると法線マップの凹凸に応じた陰影が、間接光にも加わります。代償はテクスチャが 3 枚に増えること（メモリと読み込み回数）です。モバイルなどでは Directional（2 枚）や、スカラー 1 枚で妥協する選択もあります。

## ベイクとは

<strong>ベイク</strong>は 光のシミュレーションを、制作時に実行して結果をライトマップ（テクスチャ）に、焼き込む作業です。実行時のゲームでは重すぎてできない、高品質な光の計算（何度も反射、ソフトな影）を時間をかけて行えます。

## ベイクの手順

```text
① 静的なオブジェクトに、ライトマップ UV（UV2）を、作る     （[Lightmap UVs (UV2)](uv2.md)）
② 静的なライトを、「ベイク」に、設定する
③ ベイカーを、実行（光の、シミュレーション。数分〜数時間）
④ 結果（ライトマップ、プローブ）を、保存して、ゲームに、組み込む
```

## 光のシミュレーション：レイトレーシング

ライトマップの <strong>各画素</strong>（面の上の、1 点）についてその点に届く、光の総量をレイトレーシングで、求めます。

```cpp
// ライトマップの 1 画素（面上の位置 p、法線 n）の、明るさを、パス トレーシングで、推定する（概略）。
float3 BakeTexel(const Scene& scene, const float3& p, const float3& n, int samples) {
  float3 sum = 0;
  for (int i = 0; i < samples; ++i) {                                // 数百〜数万サンプル
    float3 dir = CosineSampleHemisphere(n, Rand2());                  // 法線の側の、半球から、余弦重みで、方向を選ぶ
    sum += TracePath(scene, p + n * 1e-3f, dir, /*max_bounces*/ 4);   // その方向から、来る光（反射を、数回、追う）
  }
  return sum / samples;                                                // 拡散の、間接光（アルベドは、実行時に掛ける）
}
```

各画素から 余弦重みづけ（[Monte Carlo Integration](../theory/monte-carlo.md)）で多数のレイを飛ばし反射を数回、追跡して光を集めます。サンプルが多いほどノイズが減ります（数千〜数万サンプル）。時間はかかりますが制作時なので、問題ありません。

## ベイクの設定

| 設定 | 内容 | 大きくすると |
| --- | --- | --- |
| ライトマップの解像度（画素密度） | 1 m あたりの画素数 | 細かい影。メモリ・ベイク時間が増える |
| サンプル数 | 1 画素あたりの、レイの数 | ノイズが減る。ベイクが遅い |
| バウンス数 | 光が何回、反射するか | 間接光が明るく自然。時間が増える（効果は 2〜3 回で、頭打ち） |
| ノイズ除去（デノイズ） | ベイク後に、ノイズを消す | 少ないサンプルでも、なめらか |
| 間接光の強さ | 間接光の、倍率 | 間接光が強く（アーティストの、調整） |

### バウンス数の効果

| バウンス | 内容 | 見た目 |
| --- | --- | --- |
| 0 | 直接光のみ | 影が、真っ黒 |
| 1 | 1 回反射 | 日陰が、ほのかに明るい。カラー ブリーディング |
| 2〜3 | 複数回の反射 | 室内が自然に、明るい。効果は頭打ち |
| 4 以上 | わずかな、変化 | ほぼ変わらない（時間の、無駄） |

<strong>多くの場面で 2〜3 バウンス</strong>で、十分です（[Visual Effect](../theory/visual-effect.md) の、等比級数）。

## ベイカーの種類

| ベイカー | 内容 |
| --- | --- |
| エンジン内蔵（Unity の Progressive Lightmapper、Unreal の Lightmass） | エンジンに、組み込まれたベイカー。設定が簡単 |
| 外部ツール（Blender の Cycles、V-Ray、Arnold など） | DCC ツールの、レンダラーでベイク。テクスチャとして書き出しエンジンへ |
| 自作（DXR など） | GPU レイトレーシングで自分で、ベイカーを作る。独自のエンジンに組み込みやすい |

自作のエンジンで <strong>簡単にベイクする</strong>には、GPU レイトレーシング（DXR）で、ライトマップの各画素からレイを、飛ばす方法が現実的です（[Ray-Traced GI](../rt-gi/index.md)）。

## 保存する形式

| 形式 | 内容 |
| --- | --- |
| HDR テクスチャ（`R16G16B16A16_FLOAT`、`BC6H`） | 明るさの範囲が広い（HDR）。BC6H で圧縮（サイズが 1/4〜1/6） |
| RGBM / RGBE（8 ビットの、形式） | 8 ビット RGBA に、HDR を詰める（スケールを、アルファに）。古い環境向け |
| LDR（`R8G8B8A8`） | 明るさの範囲が狭い。簡易 |

```text
BC6H（HDR の、圧縮形式）: 4×4 画素を、16 バイトに圧縮（1 画素 = 1 バイト）。DirectX 11 が、対応。
```

<strong>DirectX 11 の BC6H</strong> は、HDR のライトマップを圧縮するのに、最適です（RGB16F の 1/8 の、サイズ）。

## ベイクの落とし穴

| 問題 | 内容 | 対策 |
| --- | --- | --- |
| 継ぎ目の黒い線 | UV2 の余白が、足りないパディングがない | 余白を、広く（2〜4 画素）、ブリード（[Lightmap UVs (UV2)](uv2.md)） |
| ノイズ | サンプルが少ない | サンプルを増やす、デノイズ |
| 真っ黒な面 | メッシュの法線が反転、面が重なっている | 法線の向きを確認、UV2 の重なりを確認 |
| 光漏れ | 壁のすき間（メッシュが壁を完全に、閉じていない） | メッシュを閉じる壁に厚みを、持たせる |
| ベイクが遅い | 解像度、サンプル、バウンスが多すぎる | まず、低品質で確認（プレビュー）。最終だけ高品質 |
