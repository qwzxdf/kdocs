# DLSS

決め打ちの規則で履歴を使う方式は、動きの激しい場面や細い線で、残像やちらつきが出やすいです。DLSS（Deep Learning Super Sampling）は、<strong>ニューラル ネットワークに「履歴をどう使うか」を学習させる</strong>ことで、この弱点を抑えます。NVIDIA の RTX GPU が必要です。ここでは NVIDIA が公開している DLSS の Programming Guide（2026 年 3 月 31 日付）を読んで、組み込みで間違えやすい所を説明します。このガイドが扱うのはアップスケーリング（Super Resolution）で、フレーム生成などは扱っていません。

!!! tip "ポイント"
    - 入力は、低解像度のカラー、動きベクトル、深度、露出、ジッターです。動きベクトルが不正確なことが、アーティファクトの一番の原因です。
    - 呼び出す位置は、ポストプロセスの先頭で、トーン マッピングの前です。
    - 描画解像度は、自分で決めずに、SDK に聞いた最適値をそのまま使います。
    - DLSS はメインの描画ターゲットのアップスケールだけに使います。影や反射のような二次バッファには使いません。
    - TAA のパスだけを DLSS に差し替えます。TAA が有効なときに動いていた周辺の処理は、そのまま動かします。

## 必要なもの {#requirements}

ガイドの要件は、NVIDIA の RTX GPU（GeForce・Titan・Quadro）と、新しいドライバーです。DLSS 2.4.11 以降は、2022 年 3 月 3 日以降に出たドライバー（たとえば 512.15）が最低限です。API は DirectX 11、DirectX 12、Vulkan 1.1 以降に対応します。

エンジン側には、次のものが要ります。

- フレームごとに、生のカラー バッファ（HDR か LDR）、16 か 32 ビットの正確な動きベクトル、深度、露出（HDR のとき）を渡せること
- サブピクセルのジッターを加えられて、少なくとも 16 フェーズ（32 以上が望ましい）の分布が取れること
- ゲームごとの Project ID で NGX と DLSS を初期化すること
- テクスチャと形状の LOD を負の方向にずらせること

出力の解像度は、最小が 32×32 です。それより小さいと初期化が失敗します。ウィンドウを最小化して小さい解像度にするような場面では、DLSS を呼びません。最大の指定はありませんが、7680×4320 を超える解像度は十分に試されていません。

## 実行モードと描画解像度 {#modes}

実行モードには、Performance、Balanced、Quality、Ultra Performance と、DLAA があります。DLAA は、入力と出力を同じ解像度（倍率 1.0）にして、アンチエイリアスだけを行うモードで、ゲーム内の UI でも別の項目として出すよう求められています。ガイドの表に載っている倍率は、次のとおりです。

- Ultra Performance: 3.0 倍
- Performance: 2.0 倍
- Balanced: 1.724 倍
- Quality: 1.5 倍
- DLAA: 1.0 倍

描画解像度は、この倍率から自分で計算せず、`NGX_DLSS_GET_OPTIMAL_SETTINGS` に聞きます。出力の幅・高さとモードを渡すと、最適な描画解像度と、許される範囲（最小・最大）が返ります。最適値は、そのまま次の `NGX_API_CREATE_DLSS_EXT()` に渡します。モードによっては使えない構成もあるので、ゲームの設定画面には、有効なモードだけを出して、ほかは隠します。

動的解像度を使うときは、範囲の中で、評価の呼び出しごとに `InRenderSubrectDimensions` を変えます。範囲を外れると `NVSDK_NGX_Result_FAIL_InvalidParameter` で失敗します。動的解像度に対応しない構成では、最小と最大が同じ値で返ります。出力解像度を変えたら、DLSS を作り直します。

動的解像度で守る点が、ほかに 2 つあります。1 つは、描画解像度が変わるたびにミップ バイアスを更新することです。毎フレームは無理なら、近似値や、数段階の候補で代用して、テクスチャの鮮明さを見ながら調整します。もう 1 つは、描画解像度の縦横比を出力と同じに保つことです。投影行列は、描画サイズではなく表示サイズの縦横比で作ります。

```cpp
// 描画サイズが違っても、画面全体に拡大したときの見え方が同じになるように、
// 縦横比は表示サイズから求める（描画サイズの比は使わない）。
float aspect_ratio = display_size.x / display_size.y;
```

Preset L と M を動的解像度と一緒に使うときは、もう 1 つ注意があります。内部のバッファを作成時の最大サイズで確保するので、作成時より大きい入力を渡すと、再確保が走って、フレーム時間が大きく跳ねます。作成時には、動的な範囲の最大解像度を渡します。

## ジッター {#jitter}

ジッターは、ガイドによると、ハルトン列にするのが最良です。DLSS の学習データにもハルトン列を使っているためです。TAA に別の列を使っていても、DLSS が有効なときはハルトン列に切り替えることが勧められています。ほかの列でも動きますが、NVIDIA は試していません。

フェーズ数は、次の式で出します。

```text
フェーズ数 = 基準のフェーズ数 × (出力解像度 / 描画解像度)^2
```

基準は 8 が目安です。1080p で描いて 2160p に出すなら、1080p の 1 ピクセルは 2160p の 4 ピクセル分なので、フェーズも 4 倍の 32 になります。ガイドの表の最小値は、Ultra Performance が 72、Performance が 32、Balanced が 24、Quality が 18、DLAA が 8 です。

ジッターは、投影行列の[2][0]と[2][1]に足します。

```cpp
// 毎フレーム、列の現在のフェーズの値を加える。
// カメラ空間でずらす（ワールド空間でずらしてから投影するのではない）。
projection.m[2][0] += jitter_x;
projection.m[2][1] += jitter_y;
```

評価の呼び出しでは、その同じ量を `InJitterOffsetX` と `InJitterOffsetY` に渡します。値の条件は 4 つあります。-0.5 から +0.5 の範囲であること。出力ではなく、描画のターゲットのピクセル単位であること。動きベクトルに加えたかどうかにかかわらず、投影行列に加えた量であること。座標と向きは動きベクトルと同じで、0 が「ずらしなし」であること。

ジッターの向きや量が実際とずれると、画面が揺れる、遠くの物体が解像されない、画面に網目が見える、静止物がぼやける、といった症状が出ます。

## 動きベクトル {#motion-vectors}

ガイドは、動きベクトルの不正確さをアーティファクトの一番の原因として挙げています。動きベクトルは、現在のフレームの各ピクセルについて、前のフレームでの位置への向きを表します。ピクセルの位置に足すと、前のフレームでの位置になります。

形式は `RG32_FLOAT` か `RG16_FLOAT` で、X が R、Y が G です。単位は、描画解像度でのピクセル数で、左上が [0, 0] です。小数も使えます。整数にすると、サブピクセルの動きが失われます。例として、1080p で物体が画面の左端から右端に動いたとき、右端のピクセルの X 成分は -1080.0 になります。

エンジンが独自の形式で持っているなら、DLSS を呼ぶ前に展開します。UV 空間の値や、動きの向きが逆の値は、`InMVScaleX` と `InMVScaleY` で補正できます。補正が要らないときは 1.0 にします。0 にしてはいけません。

フラグも 2 つあります。

- `NVSDK_NGX_DLSS_Feature_Flags_MVLowRes`: 動きベクトルを描画解像度で渡すか（既定）、表示解像度で渡すかを決める。描画解像度のベクトルは、DLSS が内部で膨張するので、自分で膨張させる必要がない。表示解像度のベクトルは、自分で膨張させる。ガイドは、前者を勧めている
- `NVSDK_NGX_DLSS_Feature_Flags_MVJittered`: 動きベクトルにジッターが入っているときに 1 にする。DLSS が、評価で渡されたジッターを内部で引く。0 のときは、ベクトルをそのまま使う

見落としやすいのは、アニメーションする植物と空です。物体が全部、正しいベクトルを持っているかを確認します。ガイドには、確認用のデバッグ オーバーレイがあり、開発用のライブラリで CTRL+ALT+F12 を押すと、動きベクトルなどを重ねて表示できます。製品版のライブラリにはありません。

細い形状は、低解像度ではラスタライズで抜けて、穴になります。その物体の動きベクトルだけを、保守的ラスタライズ（Direct3D 11.3 と 12 の機能）で描くと、DLSS が正しく履歴を引き継げる可能性が上がります。ガイドも、これですべてのちらつきが直るわけではない、と書いています。

## 深度 {#depth}

DLSS は、近い面を 0.0、遠い面を 1.0 と仮定します。リバース Z なら、`NVSDK_NGX_DLSS_Feature_Flags_DepthInverted` を 1 にします。形式は、1 チャンネルの任意の形式か、深度ステンシルの形式です。ポストプロセスで G バッファを読むときは、最近傍でアップサンプルすることが勧められています。

## 露出 {#exposure}

HDR で処理するときは、毎フレームの露出の値が要ります。この値は、掛けると中間グレーが期待の明るさになる値で、トーン マッピングに渡す値と同じです。ガイドの簡単な計算は次のとおりです。

```text
露出 = 中間グレー / (平均輝度 × (1.0 - 中間グレー))
```

中間グレーは 0.18 が一般的です。値は、1×1 のテクスチャに入れて、`pInExposureTexture` で渡します。GPU で計算した値を、CPU に戻さず渡すためです。R16F のような形式が勧められています。

露出が間違っていると、動く物体のゴースト、ぼやけ、縞（バンディング）、全体の暗さや明るさの違い、動く物体のエイリアシング、明るさが変わるときの遅れ、が出ます。DLSS のデバッグ オーバーレイには、露出の確認用のパターンがあります。値が合っていれば、sRGB 8 ビットで明るさ 187 付近を中心にしたパターンが見えます。値が小さすぎると全体が明るく、大きすぎると全体が暗く見えます。

エンジンが、フレームに事前露出の係数を掛けてあり、トーン マッピングで割り戻しているなら、その値を `InPreExposure` で毎フレーム渡します。DLSS が履歴を多用するため、渡さないと二重に露出されたことになり、露出が間違っているときと同じ症状が出ます。これは一般的な使い方ではないので、先にジッターと動きベクトルを疑うよう、ガイドは勧めています。

自動露出もあります。`NVSDK_NGX_DLSS_Feature_Flags_AutoExposure` を立てると、DLSS が内部で計算します。ガイドは露出テクスチャの方を勧めていて、自動露出は、バージョンや GPU によって約 0.02 ms の処理時間が増えます。なお、露出のパラメーターが使えるのは Preset J と K だけで、Preset L は常に自動露出を使います。

## ミップ バイアス {#mip-bias}

ガイドの式は次のとおりです。

```cpp
// 描画解像度が小さいほど log2 が負になる。
// さらに 1.0 を引いて、表示解像度でのテクスチャの鮮明さに近づける。
// epsilon は、素材ごとの調整用（既定は 0）。
float dlss_mip_bias = native_bias + std::log2(render_width / display_width) - 1.0f + epsilon;
```

Performance モードの比率 0.5 なら、バイアスは -2.0 になります。XeSS の推奨は -1、FSR 2 の式は DLSS と同じ形で -1.0 を引く形でした。同じ名前の値でも、アップスケーラによって式が違います。

負のバイアスは、時間方向の安定性を損なって、ちらつきやモアレを出すことがあります。気になる素材では、バイアスを弱めます。ただし `log2(描画の幅 / 表示の幅)` を超えて正の側には寄せません。弱めるほど、ぼやけます。エンジンに全体のバイアスの下限があるなら、DLSS が有効なときは外します。ネイティブ解像度で負のバイアスをすでに使っているなら、epsilon で調整します。

LED 画面や株価のティッカーのように、高周波のパターンのテクスチャでは、バイアスを素材ごとに上書きして、既定のままにします。ずらすと、DLSS の再構成がアーティファクトを出します。

## 色の範囲と LDR・HDR {#color}

DLSS は、LDR（SDR）と HDR の両方の色を処理します。LDR のほうが速いですが、条件があります。値の範囲が 0.0 から 1.0 であること。内部が 8 ビットに量子化されるので、入力が sRGB のような知覚的に線形な符号化であること。線形空間の色を LDR で渡すと、バンディングや色のずれが出ること。条件を満たすなら `NVSDK_NGX_DLSS_Feature_Flags_IsHDR` を 0 に、満たさないなら 1 にします。

## 呼び出す位置 {#placement}

DLSS の評価は、ポストプロセスの中で、トーン マッピングの前に行います。画質のためには、できるだけポストプロセスの先頭に置きます。そうすると、ほかのポスト エフェクトは、増えた解像度で動くので、描画解像度を前提にした処理を直します。

TAA を DLSS に差し替えるときの落とし穴があります。TAA を無効にすると、エンジンのジッター、深度、動きの描き方が変わることがあり、DLSS が壊れます。TAA のパスだけを DLSS にして、TAA が有効なときに動くほかの処理は、同じように動かします。物体のハイライトのような二次的なパスにも、ジッターを加えます。

## リソースの状態 {#resource-states}

入力のバッファは、読み取りの状態にします。D3D12 では `D3D12_RESOURCE_STATE_NON_PIXEL_SHADER_RESOURCE` で、Vulkan では `VK_IMAGE_USAGE_SAMPLED_BIT` で作ります。出力のバッファは UAV の状態にします。D3D12 では `D3D12_RESOURCE_FLAG_ALLOW_UNORDERED_ACCESS`、Vulkan では `VK_IMAGE_USAGE_STORAGE_BIT` を付けて作ります。この設定を間違えると、出力が黒くなるだけで、何が悪いかは示されません。VRAM が足りないときは、評価の最中にリソースが追い出されてクラッシュすることがあるので、評価の前に、リソースが常駐していることを確かめます。

## シーンの切り替え {#scene-transitions}

カット シーンのように、画面が大きく変わるフレームでは、評価のパラメーターの `InReset` を 0 以外にします。DLSS が履歴を捨てて、新しい入力から始めます。立てないと、前の場面の残像が出ます。逆に、不要なときに立てると、ちらつきや強いエイリアシングが出ます。

## その他の機能 {#extras}

### プリセット {#presets}

プリセットは、倍率やコンテンツに合わせてモデルの調整を変えるもので、倍率ごとに設定します。ガイドの説明は次のとおりです。

- Preset K: DLAA、Balanced、Quality の既定。Preset L より軽い
- Preset J: K に近い。ゴーストが少し減る代わりに、ちらつきが増える。K のほうが勧められる
- Preset L: Ultra Performance の既定。J・K より鮮明で安定し、ゴーストも少ないが、重い。RTX 40 シリーズ以降で最も速い
- Preset M: Performance の既定。L に近い画質で、速さは J・K に近い。RTX 40 シリーズ以降で最も速い
- Preset A〜D は削除され、E と F は非推奨、G・H・I は予約で、使わない

既定は、DLSS のバージョンが変わると変わります。OTA（配信による更新）を有効にしたタイトルで、モデルを明示的に選んでいれば、そのモデルが維持されます。既定のままなら、更新で既定のモデルが変わることがあります。

### アルファのアップスケール {#alpha}

DLSS は、既定では RGB の 3 チャンネルです。`NVSDK_NGX_DLSS_Feature_Flags_AlphaUpscaling` で、RGBA の 4 チャンネルを試験的に扱えます。RGB にアルファを掛けた形（プリマルチプライド）で渡し、実行時間は 15〜25% 増えます。

### シャープネス {#sharpness}

モデル自体が鮮明に出るように学習されています。追加で鮮明にしたいなら、DLSS SDK に含まれる NVIDIA Image Scaling SDK を使い、ユーザーが強さを変えるスライダーを付けることが勧められています。以前の SDK のシャープ化と柔らかくする処理は、非推奨です。

### VR と複数のビュー {#multi-view}

ビューごとに DLSS のインスタンスを作ります。VR で両目を同じ描画ターゲットに描くなら、サブ矩形で領域を分けます。出力側のサブ矩形を使うには、作成時に `InEnableOutputSubrects` を true にします。

## 版ごとの機能（このガイドが扱わない部分） {#versions}

このガイドは、アップスケーリングだけを扱っていて、フレーム生成・Ray Reconstruction・Multi Frame Generation については何も書いていません。以下は、このページの以前の版にあった一般的な知識で、上の資料では確かめていません。

- DLSS 2 でアップスケーラが実用になり、ゲームごとの学習が不要になった
- DLSS 3 のフレーム生成は、RTX 40 世代以降で、描画フレームの間に補間フレームを作る。見かけのフレーム数は増えるが、入力から画面への遅延は減らない。NVIDIA Reflex と併用する
- DLSS 3.5 の Ray Reconstruction は、レイトレースのノイズ除去をニューラル ネットワークで置き換える
- DLSS 4 は、モデルが Transformer 型になり、1 つの描画フレームから複数のフレームを作る Multi Frame Generation が加わった

ガイドの変更履歴には、Transformer モデルに合わせた Preset J の変更が書かれています。

## よくあるミス {#mistakes}

??? failure "動きベクトルの向きや単位が違って、画面が滲む"
    動きベクトルは、現在のピクセルから前のフレームの位置へ向かい、描画解像度のピクセル数で持ちます。UV 空間や逆向きなら、`InMVScaleX` と `InMVScaleY` で補正します。

??? failure "動きベクトルが抜けて、残像が出る"
    アニメーションする植物、空、粒子の動きベクトルが抜けています。デバッグ オーバーレイで、すべての物体にベクトルがあることを確かめます。

??? failure "ジッターが範囲外、または実際と食い違う"
    ジッターは -0.5 から +0.5 で、描画ターゲットのピクセル単位です。投影行列に足した量と、評価で渡す量を同じにします。

??? failure "露出や事前露出が合わない"
    ゴースト、明るさのずれ、バンディングが出ます。事前露出の係数があるエンジンでは `InPreExposure` を渡します。

??? failure "TAA を切ったら DLSS が壊れる"
    TAA を無効にすると、ジッターや動きの描き方が変わることがあります。TAA のパスだけを差し替えて、周辺の処理は TAA が有効なときと同じように動かします。

??? failure "リソースの使用フラグが足りず、出力が真っ黒になる"
    入力に読み取りの状態、出力に UAV の状態と使用フラグを付けます。間違えても、エラーは出ず、黒くなるだけです。

??? failure "リセットを立てず、場面の切り替えで残像が出る"
    カット シーンの最初のフレームで `InReset` を 0 以外にします。

## これだけ覚える {#summary}

- DLSS は RTX 専用で、ニューラル ネットワークで履歴を使う。入力の正確さが画質を決める
- 描画解像度は SDK に聞く。ジッターはハルトン列で、フェーズ数は倍率の 2 乗に比例する
- ミップ バイアスは `log2(描画の幅 / 表示の幅) - 1.0` を目安にして、ちらつく素材は弱める
- トーン マッピングの前、ポストプロセスの先頭で呼ぶ。TAA のパスだけを差し替える
- 場面が切り替わるフレームでは `InReset` を立てる
