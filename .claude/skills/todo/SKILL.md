# /todo

リポジトリ直下の `TODO.md` を読み、未完了（`- [ ]`）の項目を実行する。作業のルールは `CLAUDE.md` に従う（特に「作業の進め方」「文章の書き方」「サンプルコード」）。

## 引数の解釈

- なし: `TODO.md` の「2. 直す」の未完了を、上から 1 つ選ぶ。終えたら、次の項目へ続ける
- 番号（`2-3-1`、`3-1-1` など）: その項目だけを実行する
- 名前（`io`、`chrono`、`DX ガイド` など）: 項目の文に合う未完了を探して実行する。複数合うときは、上から 1 つ
- `list`: 未完了の項目を、番号つきで一覧する。何も変更しない

迷う（どれにも合わない、複数の候補が同じくらい合う）ときは、一覧を出して止まる。

## 実行の流れ（1 項目ごと）

1. 項目の内容を読み、関係するページ・ツールを確認する（`tools/` に使えるものがないか見る。例: `fix_commas.py`、`fix_bold.py`、`verify_samples.py`）
2. 実行する。STL のページを書き直すときは、次を守る
    - 1 ページずつ、そのページの具体的な話を書く。同じ文章を機械的に並べない
    - 導入は動機から入る。「ポイント」「このページを読む前に」「ゲームでの使いどころ」「よくあるミス」を、`stl/numeric/gcd.md` の濃さで書く
    - 出力のあるサンプルは `int main` まで書き、直後に「実行結果」を置く
3. 検証する
    - サンプルを書いたら `python tools/verify_samples.py <変えたファイル>` を実行する。不一致は、ページの間違いか、環境の差かを見分けて直す（環境差は、本文で説明する）
    - `mkdocs build --strict` を通す（`.venv/Scripts/mkdocs.exe build --strict`。数分かかる）
    - 検査スクリプト（`tools/` の `check_anchors.py` など。作成済みなら）を実行する
4. 新しいページ・図を足したなら、`ratings.yml`（描画のみ）、`autolinks.yml`、`.pages`、関係する `index.md` を更新する
5. `TODO.md` を更新する: 終えた項目を `- [x]` にして日付を書く。見つけたやり残しは、該当する節に `- [ ]` で足す。「4. 完了したこと」にも 1 行足す
6. 変えたファイルだけを `git add` して commit し、`main` に push する（`git add -A` は使わない。無関係の変更が入る）。コミット メッセージの最後に、そのとき渡される attribution の指示を付ける
7. 次の項目へ進む（引数なしのとき）。1 回の呼び出しで多くの項目を進めすぎず、区切りのよい所で、進めた内容と残りを短く報告する

## 守ること

- 途中で確認は取らない。ただし、次は止まって聞く: 書き方の変更を全体に広げるとき（CLAUDE.md の「まず見本の 1 ページ」）、Compiler Explorer など外部のサービスに送るとき（ユーザーの指示があったときだけ）、元に戻しにくい操作
- 検証が 1 つでも失敗したら push しない。直してからやり直す
- 手計算の実行結果を書かない。`verify_samples.py` で確かめた値を使う（手元の MSVC が未対応の機能は、本文に「コンパイラ対応」を書く）
- 実行できなかった検証（スクリプトが無い、未対応の機能など）は、報告に正直に書く
